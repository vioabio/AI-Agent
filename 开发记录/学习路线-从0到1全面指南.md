#### 1.2 面试题与参考答案

**Q1: 为什么要设计统一的响应体 `Result<T>`？有什么好处？**

**答**：统一响应体的核心价值在于**契约一致性**。具体好处包括：
1. **前端解析统一**：前端只需处理一种 JSON 结构 `{code, message, data, timestamp}`，无需为不同接口写不同的解析逻辑
2. **错误处理集中化**：通过 `GlobalExceptionHandler` 统一捕获所有异常并包装为 `Result`，避免异常信息直接暴露给客户端
3. **可扩展性**：`code` 字段可以区分 HTTP 标准码和业务码（如 1000=业务异常，2000=系统异常），便于监控和排查
4. **泛型设计**：`Result<T>` 支持不同数据类型，`@JsonInclude(NON_NULL)` 自动忽略 null 字段使响应更简洁
5. **链路追踪**：`timestamp` 字段帮助定位问题发生时间，后续可扩展 `traceId` 实现分布式链路追踪

**Q2: `@RestControllerAdvice` 和 `@ControllerAdvice` 的区别是什么？全局异常处理器的执行顺序是怎样的？**

**答**：
- `@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`，方法返回值自动序列化为 JSON，适用于 REST API
- `@ControllerAdvice` 返回值会走视图解析器，适用于服务端渲染
- 执行顺序：Spring 按 `@Order` 或 `@Priority` 排序多个异常处理器，匹配优先级为**子类异常优先于父类异常**。例如先匹配 `BusinessException` 的 handler，未匹配则 fallback 到 `Exception` 的兜底 handler

**Q3: `ThreadLocal` 在使用时需要注意什么问题？**

**答**：
1. **内存泄漏**：`ThreadLocal` 的 key 是弱引用，但 value 是强引用。线程池场景下线程复用，如果不调用 `remove()`，value 永远不会被 GC。解决方案：请求结束后在 `finally` 块或拦截器的 `afterCompletion` 中调用 `clear()`
2. **线程传递**：父线程设置的 `ThreadLocal` 子线程拿不到，需要 `InheritableThreadLocal` 或手动传递
3. **异步场景**：`@Async` 或 `CompletableFuture` 会导致线程切换，需要显式传递上下文

**Q4: 什么是 CORS？Spring Boot 如何配置跨域？**

**答**：
CORS（Cross-Origin Resource Sharing）是浏览器安全策略。当页面从 `localhost:3000`（前端）请求 `localhost:8123`（后端）时，浏览器会发送预检请求（OPTIONS）验证服务器是否允许跨域。

Spring Boot 配置方式：
1. **全局配置**：实现 `WebMvcConfigurer.addCorsMappings()`，设置 `allowedOriginPatterns`、`allowedMethods`、`allowedHeaders`、`allowCredentials`、`maxAge`
2. **过滤器配置**：注册 `CorsFilter` Bean，确保在 Spring Security Filter 之前执行（`@Order(HIGHEST_PRECEDENCE)`）
3. **注解配置**：`@CrossOrigin` 标注在 Controller 或方法上（粒度最细）

#### 2.2 面试题与参考答案

**Q1: 什么是 Token？为什么大模型按 Token 计费？**

**答**：
- **Token** 是大模型理解和生成文本的最小语义单元。英文中约 1 Token ≈ 0.75 个单词（约 4 个字符），中文中约 1 字 ≈ 2 Token
- **按 Token 计费的原因**：Token 数量决定了模型的计算量。每次推理时模型需要对每个 Token 执行矩阵运算（主要是注意力机制的计算），Token 越多 → 计算量越大 → GPU 资源消耗越大 → 成本越高
- 成本公式：总成本 = (输入 Token 数 × 输入单价) + (输出 Token 数 × 输出单价)，输出通常比输入贵 2-4 倍

**Q2: 什么是 Context Window（上下文窗口）？有什么限制和优化策略？**

**答**：
- **Context Window** 是模型一次能处理的最大 Token 数，包括 System Prompt + 历史对话 + 用户输入 + 模型输出
- **限制**：超出窗口的内容会被截断（通常截断最早的对话），导致模型"失忆"
- **优化策略**：
  1. **滑动窗口记忆**：只保留最近 N 条消息（如 `MessageWindowChatMemory.maxMessages(20)`）
  2. **摘要压缩**：对早期对话生成摘要，用摘要代替原文
  3. **向量检索记忆**：只检索与当前问题最相关的历史消息
  4. **工具输出截断**：`MAX_TOOL_OUTPUT_LENGTH = 3000`，防止工具结果塞爆窗口

**Q3: Spring AI 的 `ChatClient` 和 `ChatModel` 有什么区别？为什么要用 `ChatClient`？**

**答**：
- **`ChatModel`**：底层接口，直接调用大模型，需要手动构建 `Prompt` 对象，没有 Advisor 拦截器、ChatMemory 等高级特性
- **`ChatClient`**：高级封装，提供流式 API（`.stream().content()`）、链式调用、默认 System Prompt、Advisor 拦截器链、结构化输出（`.entity(Class)`）、工具调用（`.tools()`/`.toolCallbacks()`）
- **选择**：`ChatClient` 是 Spring AI 推荐的编程模型，功能更丰富，代码更简洁

**Q4: 什么是思维链（Chain-of-Thought）提示？为什么能提高准确率？**

**答**：
- **定义**：在提示词中要求模型"逐步思考"、"展示推理过程"，引导模型将复杂问题分解为中间推理步骤
- **原理**：大模型是自回归的（每个 Token 基于前面的所有 Token 生成）。当模型先生成推理步骤时，这些步骤本身成为了后续生成的上下文条件，相当于给模型更多"思考空间"
- **经典句式**："Let's think step by step"
- **局限**：增加输出 Token（推理过程也计费），简单任务不需要

**答**：
- **Advisor** 是 Spring AI 中的**拦截器/中间件**模式实现，采用**责任链（Chain of Responsibility）**设计模式
- **作用**：在 ChatClient 调用 AI 模型的前后执行增强逻辑
  - **前置增强**（before）：改写用户 Prompt、注入上下文（如 `MessageChatMemoryAdvisor` 注入历史消息）
  - **后置增强**（after）：记录日志、处理响应、提取结构化数据
- **内置 Advisor**：
  - `MessageChatMemoryAdvisor`：自动管理对话记忆
  - `QuestionAnswerAdvisor`：RAG 检索增强
  - `ContextualQueryAugmenter`：上下文查询增强
- **自定义**：实现 `CallAroundAdvisor`（同步）和 `StreamAroundAdvisor`（流式）

**Q2: SSE 和 WebSocket 有什么区别？为什么 AI 流式输出选 SSE？**

**答**：

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 通信方向 | 单向（服务端→客户端） | 双向（全双工） |
| 协议 | HTTP（标准） | 独立协议（ws://） |
| 自动重连 | EventSource 内置 | 需手动实现 |
| 代理兼容 | 完全兼容 HTTP 代理 | 部分代理不支持 |
| 复杂度 | 极低（浏览器原生 API） | 需额外库 |

**选择 SSE 的原因**：AI 对话场景是用户发送一条消息 → 服务端持续返回（客户端不主动发数据），SSE 更合适。WebSocket 虽然双向，但需要额外处理心跳、重连、序列化，过度设计。

**Q3: 结构化输出（Structured Output）的原理是什么？**

**答**：
1. **定义 Java Record/Class**：如 `record LoveReport(String title, List<String> suggestions) {}`
2. **Spring AI 自动生成 JSON Schema**：反射 Record 的字段类型，生成对应的 JSON Schema（如 `{"type": "object", "properties": {"title": {"type": "string"}, ...}}`）
3. **附加到 Prompt**：JSON Schema 作为输出格式约束，告诉模型"请按这个格式输出 JSON"
4. **模型返回 JSON**：模型生成符合 Schema 的 JSON 字符串
5. **反序列化**：Spring AI 使用 Jackson 将 JSON 反序列化为 Java 对象

**Q4: 为什么 `Message` 接口的序列化是个难题？Kryo 如何解决？**

**答**：
- **难题**：`Message` 是 Spring AI 的核心接口，有多个子类（`UserMessage`、`AssistantMessage`、`ToolResponseMessage` 等），这些类没有实现 `Serializable`，且其内部结构含 `Map<String, Object>` 等复杂类型，Jackson 标准序列化无法处理多态
- **Kryo 解决方案**：
  1. `setRegistrationRequired(false)`：允许序列化未注册的类
  2. `setInstantiatorStrategy(new StdInstantiatorStrategy())`：使用 Objenesis 绕过无参构造器要求，直接通过字节码创建对象
  3. Kryo 原生支持多态序列化/反序列化，不需要类实现 `Serializable`

#### 4.2 面试题与参考答案

**Q1: 什么是 RAG？为什么需要 RAG？**

**答**：
- **RAG**（Retrieval-Augmented Generation，检索增强生成）是一种将**信息检索**与**大模型生成**结合的技术。流程：用户提问 → 从知识库检索相关文档 → 将检索结果与问题一起提交给 LLM → LLM 基于检索内容生成回答
- **为什么需要**：
  1. **知识时效性**：LLM 的训练数据有截止日期，RAG 可以接入最新文档
  2. **幻觉问题**：LLM 可能编造不存在的信息，RAG 约束模型基于真实文档回答，并可通过 `emptyContextPromptTemplate` 在无匹配时拒绝回答
  3. **私有知识**：企业内部文档无法用于训练公开模型，RAG 实现私有知识的安全使用
  4. **可追溯性**：可以明确告知用户答案来源于哪些文档

**Q2: 什么是 Embedding？为什么选择 1536 维？**

**答**：
- **Embedding** 是将文本映射到高维向量空间的过程。语义相近的文本在向量空间中距离相近
- **1536 维**：这是 DashScope Embedding 模型的输出维度（对应 OpenAI text-embedding-ada-002 的维度）
- **维度选择权衡**：
  - 维度越高 → 表达能力越强 → 存储和检索成本越高
  - 1536 是行业事实标准，兼容性最好
- **应用**：`similaritySearch(queryEmbedding)` 在向量空间中查找与 query 最相似的文档向量

**Q3: 为什么文档需要切割（Chunking）？Chunk Size 和 Overlap 如何选择？**

**答**：
- **为什么切割**：
  1. **上下文窗口限制**：LLM 的 Context Window 有限，完整文档可能太长
  2. **检索精度**：小块文档更精准匹配具体问题，大块文档包含太多无关信息
  3. **成本**：注入 Prompt 的文档也消耗 Token，小块更经济
- **参数选择**：
  - `chunkSize=200` Token：每块约 200 Token，适合精准检索
  - `overlap=100` Token：相邻块之间重叠 100 Token，防止关键信息被切在边界处丢失
  - 经验法则：overlap = chunkSize 的 10%-50%

**Q4: RAG 的 ETL 流程是什么？各阶段的作用？**

**答**：
ETL = Extract → Transform → Load：
1. **Extract（抽取）**：`DocumentLoader` 从数据源（文件系统、数据库、API）加载原始文档，提取文本内容和元数据（如"单身/恋爱/已婚"标签）
2. **Transform（转换）**：对文档进行加工
   - `TokenTextSplitter`：按 Token 切割文档
   - `KeywordMetadataEnricher`：用 AI 提取关键词，增强元数据（提升检索精度）
3. **Load（加载）**：将处理后的文档向量化（调用 Embedding API）并写入 `VectorStore`

**Q1: PGVector 和 SimpleVectorStore 的区别是什么？什么场景下用哪个？**

**答**：

| 维度 | SimpleVectorStore | PGVector |
|------|-------------------|----------|
| 存储位置 | JVM 堆内存 | PostgreSQL 数据库 |
| 持久化 | ❌ 应用重启数据丢失 | ✅ 数据库持久化 |

| 适用场景 | 本地开发/原型验证/小数据量 | 生产环境/大数据量/多服务共享 |

**Q2: 什么是 HNSW 索引？为什么选择 HNSW？**

**答**：
- **HNSW**（Hierarchical Navigable Small World）：层次可导航小世界图，一种近似最近邻（ANN）搜索算法
- **原理**：构建多层图结构，顶层稀疏（长距离跳转），底层密集（精确搜索），搜索时从顶层快速定位到大致区域再逐层细化
- **优势**：
  - 查询速度极快（O(log N)）
  - 召回率高（通常 > 95%）
  - 支持动态插入
- **代价**：索引构建时间较长，内存占用较大
- **对比 IVFFlat**：IVFFlat 构建快但查询慢，适合静态数据；HNSW 查询快，适合频繁检索的 RAG 场景

**Q3: 什么是查询重写（Query Rewrite）？为什么需要？**

**答**：
- **定义**：在 RAG 检索前，用 LLM 将用户口语化的自然语言问题改写为更适合检索的关键词查询
- **为什么需要**：
  - 用户问"我该怎么追喜欢的女生？"→ 改写为"追求心仪对象的方法 恋爱技巧"
  - Embedding 模型对口语化长句的向量表示不够精准，改写后的关键词查询检索命中率更高
- **多查询扩展**：从一个问题扩展为 3 个不同角度的查询，合并检索结果，提高召回率

**Q4: 什么是大模型幻觉（Hallucination）？如何缓解？**

**答**：
- **幻觉**：模型生成的内容与事实不符、逻辑不通或完全编造
  - **内在幻觉**：生成内容与 Prompt 中的信息矛盾
  - **外在幻觉**：生成现实中不存在的信息（编造网址、数据、人名）
- **缓解策略**：
  1. **RAG 约束**：基于检索到的真实文档回答，`allowEmptyContext(false)` + `emptyContextPromptTemplate("抱歉，我只能回答恋爱相关的问题...")` 确保无匹配文档时拒绝回答
  2. **Temperature 降低**：降低随机性（但会减少创造性）
  3. **提示词约束**：明确要求"如果不知道就说不知道"
  4. **引用来源**：要求模型标注信息来源

#### 6.2 面试题与参考答案

**Q1: 什么是 Tool Calling（Function Calling）？它的完整流程是怎样的？**

**答**：
**Tool Calling** 允许 LLM 在需要外部信息或执行操作时"调用"预定义的工具函数。

**完整流程**：
```
1. 用户发送消息："帮我搜索上海的约会地点"
2. 应用将消息 + 可用工具列表（含 JSON Schema 描述）发送给 AI
3. AI 分析后决定：需要调用 searchWeb(query="上海 约会地点")
4. AI 返回 ToolCall 对象（不执行，只指定工具名和参数）
5. 应用程序收到 ToolCall → 真正调用 Java 方法 → 获取结果
6. 应用程序将工具结果追加到对话上下文 → 再次调用 AI
7. AI 根据工具结果生成最终的自然语言回复
```

**关键点**：AI **不执行工具**，它只返回"我想调用哪个工具、传什么参数"，实际执行由应用程序完成。

**Q2: `@Tool(description = "...")` 的 description 有多重要？**

**答**：
**极其重要**。description 是 AI 决定"何时调用哪个工具"的**唯一依据**。
- 如果 description 写得不清晰，AI 可能：不该调工具时调了、该调时不调、调了错误的工具
- 最佳实践：用英文写描述（大多数模型的训练数据以英文为主），清晰说明工具功能、适用场景和参数含义
- 示例：
  ```java
  @Tool(description = "Search for information from Baidu Search Engine. " +
      "Use this when you need real-time or factual information from the internet.")
  public String searchWeb(@ToolParam(description = "Search query keyword") String query)
  ```

**Q3: 为什么工具返回值统一使用 String？**

**答**：
1. **AI 只理解文本**：模型不能直接处理 Java 对象，工具返回的 String 会被添加到对话上下文中作为 AI 下一步推理的依据
2. **简化实现**：工具内部用 try-catch 捕获所有异常，返回友好的错误描述字符串而非抛出异常
3. **Token 控制**：返回的 String 长度直接影响 Token 消耗，需要做截断处理（如 `MAX_TOOL_OUTPUT_LENGTH = 3000`）

**Q4: 工具调用有哪些安全风险？如何防范？**

**答**：
| 风险 | 说明 | 防范措施 |
|------|------|---------|
| 命令注入 | `TerminalOperationTool` 执行任意命令 | 命令白名单、禁用 `rm -rf` 等危险操作 |
| 路径穿越 | `FileOperationTool` 读写任意文件 | 限制操作目录到 `FILE_SAVE_DIR`（沙箱） |
| 信息泄露 | `WebScrapingTool` 抓取内网地址 | URL 黑白名单、禁止访问 localhost/内网 IP |
| 资源耗尽 | 下载超大文件、抓取超大网页 | 超时控制（10s）、输出截断（2000-3000 字符） |
| DoS | 恶意高频调用 SearchAPI | 频率限制、API Key 使用配额 |

#### 7.2 面试题与参考答案

**Q1: 什么是 MCP？它解决了什么问题？**

**答**：
- **MCP**（Model Context Protocol）是 Anthropic 提出的**开放标准协议**，用于标准化 AI 模型与外部工具/数据源之间的通信
- **解决的问题**：在 MCP 之前，每个 AI 应用都要为每个工具单独编写集成代码（N 个工具 = N 种集成方式）。MCP 统一了工具调用协议，类似于 USB-C 统一了设备接口
- **核心价值**：
  - **一次开发，多处使用**：MCP Server 可以被任何支持 MCP 的 Client 调用（不限于 Java）
  - **跨语言**：Server 可以用 Java、Python、Node.js 等任何语言开发
  - **工具发现**：Client 自动发现 Server 提供的工具列表，无需手动配置

**Q2: MCP 的 STDIO 和 SSE 模式有什么区别？如何选择？**

**答**：

| 维度 | STDIO | SSE |
|------|-------|-----|
| 通信方式 | 进程 stdin/stdout | HTTP（Server 独立进程） |
| 生命周期 | Client 启动时 spawn 子进程 | Server 独立运行，Client 连接 |
| 进程模型 | Client 管理子进程 | 各自独立 |
| 网络 | 无网络开销，只能本机 | 可以远程部署 |
| 多客户端 | 1:1（每个 Client 一个子进程） | 1:N（一个 Server 多 Client） |
| 调试 | stdio 被 JSON-RPC 占用，不能打印日志 | 独立进程，日志和协议分离 |

**选择**：
- 本地开发/单机部署 → STDIO（安全、零延迟）
- 远程部署/多服务共享 → SSE（网络可达、多客户端）

**Q3: 为什么 STDIO 模式下不能使用 `System.out.println`？**

**答**：
STDIO 模式下，MCP Server 通过标准输入/输出流与 Client 进行 JSON-RPC 2.0 通信：
- `stdin`：接受 Client 发来的 JSON-RPC 请求
- `stdout`：向 Client 发送 JSON-RPC 响应

如果在 Java 代码中使用 `System.out.println("日志信息")`，这些字符串会混入 JSON-RPC 响应流中，破坏协议格式，导致 Client 解析失败。因此所有日志必须通过日志框架（SLF4J/Logback）输出到文件或 stderr。

**Q4: MCP 调用的本质是什么？是 AI 服务器直接调用 MCP 服务吗？**

**答**：
**不是**。MCP 调用的本质是**工具调用的标准化**，调用链路如下：
```
用户消息 → 主应用（Spring Boot）
  → ChatClient 发送给 DashScope AI
  → AI 决策：调用高德地图 MCP 工具
  → 返回 ToolCall 给主应用
  → 主应用通过 MCP 协议向 MCP Server 发起 JSON-RPC 调用
  → MCP Server 执行查询，返回结果
  → 主应用将结果追加到对话上下文
  → 再次调用 AI
  → AI 基于结果生成自然语言回复
```

AI 服务器（DashScope）**不知道 MCP 协议的存在**，它只返回"我想调用工具 X(Y)"的指令，主应用作为中间人代为执行。

#### 8.2 面试题与参考答案

**Q1: 什么是 AI Agent？它和普通 Chatbot 有什么区别？**

**答**：
- **AI Agent（智能体）** = LLM + 工具 + 自主规划 + 记忆系统
- **核心区别**：

| 维度 | 普通 Chatbot | AI Agent |
|------|-------------|----------|
| 交互模式 | 一问一答（被动） | 自主多步执行（主动） |
| 工具使用 | 无或单次调用 | 多工具组合，多轮调用 |
| 规划能力 | 无 | 自主分解复杂任务 |
| 终止决策 | 回答完成 | 主动调用 terminate 工具 |
| 状态管理 | 无状态 | 有内部状态和生命周期 |

- **类比**：Chatbot 是"客服"，回答一个问题就结束；Agent 是"助理"，给他一个复杂任务，他会自己规划步骤、调用工具、逐步完成

**Q2: 什么是 ReAct 模式？它的循环流程是怎样的？**

**答**：
ReAct = **Re**asoning + **Act**ing，是一种让 LLM 交替进行推理和行动的提示模式：

```
Cycle:
  1. Think（推理）：
     - AI 分析当前状态："用户想搜索约会地点并生成 PDF"
     - AI 决定行动："我需要先搜索网络获取地点信息"
     - 返回 ToolCall: searchWeb("上海约会地点")
     
  2. Act（行动）：
     - 执行 searchWeb 工具
     - 获取搜索结果
     
  3. Observe（观察）：
     - 工具结果自动加入对话上下文
     - 成为下一步 Think 的输入
     
  4. 循环直到 FINISHED（调用 terminate）或达到 maxSteps
```

**核心 Insight**：每次工具执行的结果自动成为下一轮推理的上下文，形成**自主推进的正反馈循环**。

**Q3: 为什么 `withInternalToolExecutionEnabled(false)` 是 Agent 与普通 ChatClient 的本质区别？**

**答**：
- **普通 ChatClient**：启用内置工具执行（`true`），Spring AI 自动管理消息上下文。一次 `call()` 中，AI 返回 ToolCall → Spring AI 自动执行工具 → 自动将结果追加到上下文 → 自动再次调用 AI → 返回最终结果。这是**黑盒**执行
- **Agent 场景**：需要在 for 循环中**多次调用 AI + 多次执行工具**，每次循环的上下文由 Agent 自己管理（`setMessageList(toolExecutionResult.conversationHistory())`）。如果启用内置执行，Spring AI 会在一次 call 中"替 Agent 完成"所有工具调用和执行，Agent 失去了对执行流程的控制
- **本质区别**：Agent 需要**白盒控制**执行流程，内置执行会破坏 Agent Loop 的规划

**Q4: 为什么 VioManus 不能作为 Spring 单例 Bean？**

**答**：
Agent 维护**内部状态**（`state`、`currentStep`、`messageList`、`stopped`），这些状态属于**单次请求**：
- 如果作为单例 Bean，用户 A 和用户 B 的请求会共享同一个 `messageList`，导致对话混乱
- 状态冲突：用户 A 的请求正在 RUNNING，用户 B 的请求来时会因为状态不是 IDLE 而抛异常
- **正确做法**：每次请求在 Controller 中 `new VioManus(...)` 创建新实例

**Q5: Agent 的防护机制有哪些？为什么需要？**

**答**：

| 防护机制 | 值 | 保护目的 |
|----------|-----|---------|
| `maxSteps` | 20 | 防止 AI 陷入无限循环（如反复调用工具无进展）持续消耗 Token |
| `MAX_TOOL_OUTPUT_LENGTH` | 3000 | 防止工具返回超长内容（如 20 万字符的 HTML）塞爆上下文窗口 |
| `MAX_CONSECUTIVE_ERRORS` | 3 | 防止 API 调用失败或网络异常导致死循环 |
| `volatile stopped` | - | 用户可随时手动停止长时间运行的任务 |
| `state` 校验 | - | 防止从非 IDLE 状态重复启动（状态保护） |

这都是**成本控制**和**用户体验**的平衡：Agent 自主运行但必须有安全阀。

#### 9.2 面试题与参考答案

**Q1: Nginx 配置 SSE 流式输出时最重要的是什么？**

**答**：
**`proxy_buffering off`** 是最关键的配置。

- **原理**：Nginx 默认会缓冲上游服务器的响应，等积累到一定大小后再发送给客户端。这对普通 HTTP 响应没问题，但对 SSE 是致命的——所有实时推送的数据会被积压在缓冲区，直到连接关闭才一次性发送
- **额外配置**：
  - `chunked_transfer_encoding off`：关闭分块传输编码
  - `proxy_read_timeout 600s`：Agent 执行可能长达几分钟，默认 60s 超时不够
  - `proxy_http_version 1.1`：支持长连接

**Q2: Vue Router 的 History 模式需要什么服务端配置？**

**答**：
Nginx 需要配置 `try_files $uri $uri/ /index.html`：
- 用户直接访问 `/love-master` → Nginx 找不到对应的静态文件 → fallback 到 `index.html` → Vue Router 接管路由 → 渲染正确页面
- 没有这个配置，刷新页面会返回 404

**Q3: Docker 多阶段构建的好处是什么？**

**答**：
前端 Dockerfile 使用 2 个阶段：
1. **Stage 1（Node 编译）**：基于 `node:20-alpine`，执行 `npm install` + `npm run build`，产出 dist 目录（编译后的静态文件）
2. **Stage 2（Nginx 托管）**：基于 `nginx:alpine`，只复制 Stage 1 产出的 dist → `/usr/share/nginx/html`，加上 `nginx.conf`

**好处**：
- 最终镜像**只包含 Nginx + 静态文件**（~20MB），不包含 Node.js、node_modules、源码
- 镜像更小 → 拉取更快 → 启动更快 → 安全面更小

**Q4: 前端如何根据环境自动切换 API 地址？**

**答**：
```javascript
const API_BASE_URL = import.meta.env.MODE === 'production'
  ? '/api'                         // 生产：Nginx 反向代理，同源请求
  : 'http://localhost:8123/api'    // 开发：CORS 跨域直连后端
```
- `import.meta.env.MODE` 是 Vite 的环境变量，`npm run dev` 时为 `development`，`npm run build` 时为 `production`
- 生产环境使用**相对路径** `/api`，因为 Nginx 将前端和后端部署在同一域名下

#### 10.2 面试题与参考答案

**Q10-1: 为什么自建 JSON-RPC 2.0 协议栈而不是直接用 Spring AI 的 MCP Starter？**

**答**：
1. **展示深度理解**：会用框架和能手写协议是两个层次。面试官问到"JSON-RPC 2.0 的错误码规范是什么？""MCP 的 tools/list 和 tools/call 有什么区别？"能回答到协议细节层面
2. **自主可控**：Spring AI 的 Starter 封装了所有细节，一旦出问题（如 SSE 重连失败、STDIO 子进程僵死）无法定位。自建协议栈对每一层的状态了如指掌
3. **可扩展性**：自建协议栈支持多版本映射器共存，未来 MCP 协议升级到 2.0/3.0 时可以平滑迁移
4. **面试加分**：2000 行自建代码 + 51 个测试用例全通过，是"理解协议本质"的最强证据

**Q10-2: 为什么 STDIO 模式下不能使用 `System.out.println`？**

**答**：
STDIO 传输通过子进程标准输入/输出流通信：stdin 接收 JSON-RPC 请求，stdout 发送 JSON-RPC 响应。`System.out.println()` 输出到 stdout，会混入 JSON-RPC 响应流破坏协议格式导致 Client 解析失败。所有日志必须通过日志框架（SLF4J/Logback）输出到 stderr 或文件。

**Q10-3: MCP 的 initialize 握手做了什么？**

**答**：
1. Client 发送 `initialize` 请求（包含 Client 支持的协议版本和能力）
2. Server 返回 `InitializeResult`（协议版本、ServerCapabilities，如是否支持 tools 资源等）
3. 握手成功后 Client 调用 `tools/list` 获取工具列表
4. 后续 Client 通过 `tools/call` 调用具体工具

**Q10-4: MCP 协议的四层架构分别负责什么？**

**答**：

| 层级 | 组件 | 职责 |
|------|------|------|
| **Codec 层** | `JsonRpcCodec` | Java 对象 ⇄ JSON 字符串的序列化/反序列化 |
| **Protocol 层** | `McpProtocolHandler` | MCP 业务语义（initialize/tools/list/tools/call），不关心传输细节 |
| **Transport 层** | `McpTransport` (Stdio/Sse) | 底层通信实现（进程管道/HTTP SSE），不关心业务语义 |
| **Gateway 层** | `McpGateway` | 封装前三层，向上提供统一的工具调用接口 |

#### 11.2 面试题与参考答案

**Q11-1: 为什么 PathGuard 和 CommandGuard 要在 HITL 之前执行？**

**答**：
这是**fast-fail 策略**。PathGuard 和 CommandGuard 是纯规则匹配（正则 + 路径解析），耗时 < 1ms。如果在用户完成审批后才拒绝，用户体验极差（"我点了批准，为什么还失败了？"）。先 fast-fail 可减少 70% 的无效审批次数。

**Q11-2: HITL 的五种审批决策分别用于什么场景？**

**答**：

| 决策 | 场景 |
|------|------|
| **APPROVE** | 单次批准，本次操作通过 |
| **APPROVE_ALL** | 批量批准，本次会话内同类操作自动通过 |
| **DENY** | 拒绝本次操作，Agent 收到拒绝信号 |
| **SKIP** | 跳过但不拒绝，Agent 换一种方式完成任务 |
| **MODIFY** | 用户修改参数后批准（如修改文件保存路径） |

**Q11-3: TokenBinding 是如何防止跨协议越权的？**

**答**：
每个 API Key 注册时绑定允许的协议类型。当请求通过 STDIO 传输来调用 MCP 工具时，TokenBinding 首先验证该 Key 是否允许 STDIO 协议。如果 Key 只注册了 SSE 权限而请求来自 STDIO，直接拒绝。这防止了"拿到一个 Key 就能访问所有端点"的安全隐患。

**Q11-4: 审计日志为什么使用 JSONL 格式而不是数据库存储？**

**答**：
1. **性能**：追加写文件远快于数据库 INSERT，不影响 Agent 执行性能
2. **不可篡改**：文件系统权限控制，附加写模式（append-only），不提供修改/删除 API
3. **易于分析**：JSONL 每行一条 JSON，可直接用 `grep`/`jq` 分析或导入 ELK
4. **按天分片**：自动按日期切分，方便归档和定期清理

### 第 12 阶段：会话编排与容错 🆕

**对应章节**：第 12 章（企业级升级）  
**学习目标**：掌握高可用 Agent 系统的设计，状态机管理、线程池隔离、幂等重试

#### 12.1 知识点清单

| 序号 | 知识点 | 详细内容 |
|------|--------|----------|
| 12.1 | **SessionStateMachine 10 态** | IDLE → INITIALIZING → RUNNING → WAITING_HITL → THINKING → EXECUTING_TOOL → PAUSED → FINISHED → ERROR → CANCELLED |
| 12.2 | **合法状态转换矩阵** | 不是所有转换都合法（如 RUNNING 不能直接跳 FINISHED，必须先通过 Agent 终止信号） |
| 12.3 | **ThreadPoolTaskExecutor × 3** | agentReasoningExecutor（CPU 密集 4-8）/ toolExecutionExecutor（IO 密集 8-16）/ mcpTransportExecutor（4-8） |
| 12.4 | **线程池隔离原理** | 三池互不影响，CPU 密集型配较少线程避免上下文切换，IO 密集型配较多线程提高吞吐 |
| 12.5 | **AgentConcurrencyGuard** | Semaphore 限制最大并发 Agent 数（默认 10），超过即排队等待，防止 OOM |
| 12.6 | **指数退避重试** | 2^n 秒（1→2→4→8→16）+ 随机 Jitter 0~1000ms，最大 3 次 |
| 12.7 | **RetryDecision 分类** | 可重试错误（TimeoutException/IOException/ConnectException）vs 不可重试错误（SecurityException/IllegalArgumentException） |
| 12.8 | **IdempotencyManager** | MD5(sessionId+stepIndex+toolName+paramsHash) 生成幂等 Key、24h 缓存防重复执行 |
| 12.9 | **ToolTimeoutManager 分级超时** | Web Search 15s → Terminal 60s → Agent 全局 10min、6 级分类 |
| 12.10 | **ToolCategory 工具分类** | 搜索/文件/命令/MCP/生成/其他，每类独立的超时和重试策略 |

#### 12.2 面试题与参考答案

**Q12-1: 为什么要用 3 个不同的线程池？为什么不用一个大的线程池？**

**答**：
1. **故障隔离**：如果工具执行线程池中的 IO 线程全部阻塞（如网络问题），Agent 推理线程池不受影响，仍能生成思考内容，不会整个系统卡死
2. **性能特征不同**：Agent 推理是 CPU 密集型（生成自然语言计算量大），工具执行是 IO 密集型（等待网络/文件），应配不同参数：CPU 密集 4-8 线程（等于或略大于 CPU 核数），IO 密集 8-16 线程（远大于 CPU 核数）
3. **可观测性**：分开后能分别监控各池的队列长度、拒绝次数、活跃线程，快速定位瓶颈

**Q12-2: 为什么指数退避中要加 Jitter（随机抖动）？**

**答**：
多个请求同时失败时，如果不加抖动，它们会在 1s→2s→4s→8s 的精确时间点同时重试，造成"惊群效应"（thundering herd）——瞬间爆发大量请求压垮服务。加上 0~1000ms 随机抖动后，重试时间分散在 1~2s、2~3s、4~5s 等区间，平滑了负载曲线。

**Q12-3: MD5 幂等 Key 为什么要包含 sessionId 和 stepIndex？**

**答**：
同一个工具在同一次 Agent 任务的不同步骤可能被调用多次（如步骤 3 搜索 A，步骤 5 搜索 A），如果只用 toolName+paramsHash 会导致步骤 5 的合法调用被当作"重复"拦截。加上 sessionId+stepIndex 后，每次调用都是唯一的组合，真正防止的是"同一工具的同一参数在同一执行步骤中被重复执行"。

**Q12-4: 会话状态机中哪些转换是非法的？为什么？**

**答**：
- RUNNING → IDLE：非法。RUNNING 中的 Agent 有内部累积状态（messageList、currentStep），直接回 IDLE 意味状态丢失
- FINISHED → RUNNING：非法。Agent 生命周期只能执行一次（Prototype 模式），需要重新执行应创建新会话
- WAITING_HITL → FINISHED：非法。用户在审批中，不能绕过审批直接终止
- 正确的终止路径：RUNNING → CANCELLED（用户手动停止）或 RUNNING → FINISHED（Agent 调用 terminate）

### 第 13 阶段：多智能体协作 🆕

**对应章节**：第 13 章（企业级升级）  
**学习目标**：掌握 Plan-and-Execute 模式，DAG 依赖图 + Kahn 拓扑调度，多角色协作

#### 13.1 知识点清单

| 序号 | 知识点 | 详细内容 |
|------|--------|----------|
| 13.1 | **Plan-and-Execute vs ReAct** | 全局规划（先计划后执行）vs 逐步推理（边走边看）、各自适用场景 |
| 13.2 | **Planner Agent** | LLM 驱动任务拆解、输出子任务列表 + 依赖关系、降级为单任务 |
| 13.3 | **DAG 依赖图（TaskDag）** | 有向无环图表示任务依赖、节点=子任务、边=依赖关系 |
| 13.4 | **Kahn 算法拓扑排序** | 入度表 + 队列、分层并行调度、同层独立任务 √ 并行、跨层任务 √ 串行 |
| 13.5 | **Orchestrator 调度器** | CompletableFuture 异步调度、Worker 池共享工具集、依赖任务串行等待 |
| 13.6 | **Worker Agent** | 独立执行单个子任务、共享全局工具集、结果上报 Orchestrator |
| 13.7 | **Reviewer Agent** | 0-100 质量评分、不合格任务打回重试（最多 2 次）、降级策略（默认通过） |
| 13.8 | **多 Agent vs 单 Agent 性能** | 复杂任务效率提升 55%、独立任务并行、依赖任务顺序 |
| 13.9 | **LLM 失败降级** | Planner 降级（多任务→单任务）、Reviewer 降级（评分→默认通过） |
| 13.10 | **AgentOrchestrator 编排器** | 工厂模式组装四角色、配置驱动（DAG 调度策略/Reviewer 阈值） |

#### 13.2 面试题与参考答案

**Q13-1: Plan-and-Execute 和 ReAct 分别适合什么场景？**

**答**：

| 维度 | ReAct | Plan-and-Execute |
|------|-------|------------------|
| 规划方式 | 逐步推理：Think→Act→Observe 循环 | 全局规划：先拆解所有子任务再执行 |
| 任务复杂度 | 简单~中等（单 Agent 能完成的） | 中~复杂（需多工具/多步骤协调的） |
| 容错性 | 高（每步都可调整方向） | 中（依赖 Planner 的规划质量） |
| Token 消耗 | 较低（无规划开销） | 较高（规划本身也需要调用 LLM） |
| 并行能力 | 无（串行循环） | 有（DAG 同层任务并行） |
| 适用场景 | 开放式探索、简单定量任务 | 明确可拆解的复杂任务 |

**Q13-2: 为什么用 Kahn 算法而不是深度优先搜索？**

**答**：
Kahn 算法（BFS 拓扑排序）天然支持**分层并行调度**——每轮处理"当前入度为 0 的所有节点"，恰好对应可以并行执行的独立任务。DFS 虽然也能拓扑排序，但它输出的是线性序列，丢失了并行关系信息。Kahn 让 Ollama 可以一次提交同层所有任务到 Worker 池。

**Q13-3: Reviewer 为什么会需要降级策略？**

**答**：
Reviewer 本身也是 LLM 调用，可能因 API 限流/欠费/超时而失败。如果 Reviewer 的失败导致整个多智能体流程阻塞，比不用 Reviewer 更差。降级策略为"默认通过"——Reviewer 不可用时跳过评审，保证可用性优先，这是生产系统的典型设计。

**Q13-4: 多智能体的 Token 消耗和单 Agent 相比如何？**

**答**：
多智能体的 Token 消耗通常**更高**，因为需要额外的规划开销（Planner 调用）和评审开销（Reviewer 调用）。但复杂任务的总耗时反而降低（并行提升 55%），并且在以下情况下更经济：
- 任务足够复杂，单 Agent 反复试错浪费的 Token 超过规划开销
- 并行任务足够多，耗时优势超过 Token 增加
- 实际推荐策略：简单任务 → ReAct 单 Agent，复杂任务 → Plan-and-Execute 多 Agent

**对应章节**：第 14 章（企业级升级）  
**学习目标**：设计生产级三层记忆系统，掌握 Map-Reduce 上下文压缩和加权检索

#### 14.1 知识点清单

| 序号 | 知识点 | 详细内容 |
|------|--------|----------|
| 14.1 | **三层记忆架构** | WorkingMemory（最近 3 轮完整对话）/ShortTermMemory（token 阈值 4000 淘汰）/LongTermMemory（JSON 文件持久化 + MD5 去重） |
| 14.2 | **MemoryType 4 种分类** | 对话（Conversation）/事实（Fact）/摘要（Summary）/工具结果（ToolResult） |
| 14.3 | **Token 阈值自动淘汰** | ShortTermMemory 超过 4000 Token 自动淘汰，淘汰前保留 LLM 压缩摘要 |
| 14.4 | **Map-Reduce 上下文压缩** | 保留最近 3 轮 → 旧消息每 5 条分片 → 每片生成摘要（Map）→ 合并摘要 + 提取关键事实（Reduce）、压缩率 60%+ |
| 14.5 | **LongTermMemory 跨会话** | 高重要性（≥7 分）事实自动写入、MD5 去重防重复、JSON 文件持久化 |
| 14.6 | **加权检索排序** | 关键词匹配 50% + 时间衰减 30% + 来源权重 20% |
| 14.7 | **MemoryRetriever** | 多维度检索（按类型/按时间/按重要性/按关键词）、Top-K 截断 |
| 14.8 | **ContextCompressor** | 上下文压缩核心引擎、TokenEstimator 估算 Token 数、分批压缩 |
| 14.9 | **记忆与 RAG 的区别** | 记忆存储对话上下文（动态更新），RAG 存储知识库文档（静态索引） |
| 14.10 | **TieredMemorySystem** | 外观模式整合三层记忆，统一的 add/search/compress/evict API |

#### 14.2 面试题与参考答案

**Q14-1: 三层记忆的职责和边界是什么？**

**答**：

| 层级 | 容量 | 生命周期 | 存储内容 | 淘汰策略 |
|------|------|---------|---------|---------|
| **Working** | 最近 3 轮 | 单次 Agent 任务 | 完整对话（不压缩） | 任务结束释放 |
| **ShortTerm** | Token 阈值 4000 | 单次会话 | 对话+事实+摘要+工具结果 | Token 超限淘汰，保留摘要 |
| **LongTerm** | 无硬限制 | 跨会话持久化 | 高重要性事实（≥7 分） | MD5 去重 |

**Q14-2: Map-Reduce 压缩策略的具体流程是怎样的？**

**答**：
1. **保留最近 N**：最近 3 轮对话不压缩（当前上下文最相关）
2. **Map 阶段**：将更早的消息按每 5 条分片，对每片调用 LLM 生成摘要（"请将以下对话压缩为一段摘要，保留关键信息"）
3. **Reduce 阶段**：将所有分片摘要 + 已提取的关键事实合并为一条最终摘要，替换原始旧消息
4. **压缩效果**：原始 40 条消息（~8000 Token）→ 压缩为 1 条摘要 + 关键事实列表（~3000 Token），压缩率 60%+

**Q14-3: 为什么加权检索排序中的时间衰减占 30%？**

**答**：
对话记忆有很强的"时效性"——刚聊过的内容比 30 分钟前聊过的内容更相关。时间衰减使用指数衰减函数 `score *= e^(-λt)`，确保最近的信息获得更高排序。30% 的权重是基于实践经验的平衡值：太低（10%）几乎忽略时效，太高（50%）会让关键词匹配失去主导地位。

**Q14-4: 记忆系统和 RAG 系统有什么关系？**

**答**：
- **记忆系统**存储的是"对话过程"（用户说了什么、Agent 做了什么），是动态的、随时间演化的
- **RAG 系统**存储的是"知识库"（宝可梦图鉴、技能数据），是静态的、预先索引的
- 两者互补：RAG 提供领域知识（"皮卡丘是什么属性"），记忆系统提供上下文（"你刚才让我搜索的是电系宝可梦"）
- 技术上的相似点：都涉及 Embedding → 向量化 → 相似度检索，但记忆系统还多了压缩和淘汰

#### 15.2 面试题与参考答案

**Q15-1: MDC 的 traceId 在异步线程中会丢失吗？怎么解决？**

**答**：
会丢失。MDC 基于 ThreadLocal，异步线程（如 CompletableFuture 提交到不同线程池）不会继承父线程的 MDC。解决方案：
- **手动传递**：在异步调用前取出 traceId，在异步任务中手动 `MDC.put("traceId", traceId)`
- **装饰器模式**：Spring 的 `TaskDecorator` 在提交任务时自动复制 MDC 上下文
- **Agent 中的做法**：AgentLogContext 在 `BaseAgent.run()` 入口显式设置，确保整个 Agent Loop 共享同一 traceId

**Q15-2: 为什么用 AtomicLong 而不是直接用 Micrometer？**

**答**：
- AtomicLong 零依赖（"零新增 Maven 依赖"策略），不引入 Micrometer
- 与 Spring Boot Actuator 解耦，指标采集逻辑完全自主可控
- `/api/metrics` 端点返回 JSON 快照，可被任意系统（Prometheus/自定义脚本/前端轮询）消费
- 生产环境可以直接替换为 Micrometer，因为 API 设计一致

**Q15-3: 什么样的告警规则是有效的？举例说明。**

**答**：
有效的告警 = 具体的业务影响 + 可操作的处理步骤：
- ❌ 无效告警："服务器 CPU 超过 80%"（不知道为什么高）
- ✅ 有效告警："Agent 工具调用失败率超过 10% 持续 5 分钟，请检查 DashScope API Key 余额或 SearchAPI 第三方服务状态"
- 关键告警规则：失败率阈值（业务健康）、并发数接近上限（容量预警）、P95 延迟突增（性能退化）

**Q15-4: 前端怎么利用 X-Trace-Id？**

**答**：
后端在 SSE 响应头中返回 `X-Trace-Id`，前端记录该 ID。用户反馈问题时，只需提供 traceId，后端通过 `grep traceId /var/log/agent/*.log` 即可精确检索该次请求的完整链路日志——从 Filter 入口到每个 Agent step 的执行细节。

#### 16.2 面试题与参考答案

**Q16-1: 错误码为什么采用 5 域分段而不是一个全局列表？**

**答**：
1. **快速定位**：AG-003 一眼看出是 Agent 层问题，不需要查表就能推断范围
2. **团队协作**：不同模块（Agent/工具/安全）由不同人开发，独立错误码段避免冲突
3. **可扩展**：每域预留了扩展空间（如 AG 域可扩展到 99 个），新增错误码不影响其他域
4. **面试加分**：相比"定义了一堆 int 常量"，结构化错误码体现了工程化思维

**Q16-2: 优雅关闭的完整流程是怎样的？**

**答**：
1. 收到 SIGTERM（如 `docker stop` 或 K8s Pod 驱逐）→ Spring Boot 触发 GracefulShutdown 的 `@PreDestroy`
2. 停止 HTTP 接收（`WebServer.terminate()`）→ 不再接受新请求
3. 等待活跃 Agent 完成（最多 30s）→ `Semaphore.wait(30s)` 等待所有 Agent Slot 释放
4. 关闭线程池：`shutdown()` → 等待 30s → `shutdownNow()` 强制终止
5. 刷新审计日志缓冲区 → 确保所有日志落盘
6. 关闭 Docker Compose 依赖服务 → 进程退出

**Q16-3: GitHub Actions CI/CD 的流水线设计是怎样的？**

**答**：
```yaml

→ Docker 构建镜像（后端 + 前端）
→ 推送到 ghcr.io（tag 推送触发部署）
→ Webhook 通知部署服务器拉取最新镜像
→ Docker Compose up -d 滚动更新
```
关键设计点：PR 只做编译+测试不部署，只有推送到 main 的 tag 才触发部署。

**Q16-4: 测试策略中，为什么需要 Stub Agent？**

**答**：
Agent 测试的核心挑战是 LLM 调用不可控（每次返回不同、外部 API 费用、网络延迟）。Stub Agent 通过**Mock ToolCallingManager** 模拟工具调用和响应，实现：
- **确定性**：相同的输入 → 相同的输出，方便断言
- **快速**：跳过真实 LLM 调用，毫秒级完成
- **低成本**：不消耗 DashScope Token
- **覆盖面**：可以模拟异常场景（API 超时、返回格式错误等），这些场景用真实 LLM 很难精确触发

## 三、综合面试题（跨阶段、系统性）

### Z1: 请描述这个项目的完整架构，从用户发送消息到 AI 返回结果的全链路。

**答**：
```
1. 用户在浏览器中输入消息（Vue 3 前端）
2. 前端通过 EventSource 连接后端 SSE 端点
3. 后端 Controller 接收请求，创建 VioManus 实例
4. VioManus.runStream() 启动 Agent Loop：
   a. Think：ChatClient 将 [SystemPrompt + MessageList + nextStepPrompt + 工具列表]
      发送给 DashScope AI
   b. AI 分析任务，决定调用哪个工具（如 searchWeb）
   c. AI 返回 ToolCall（工具名 + 参数）
   d. Act：ToolCallingManager 执行 Java 工具方法
   e. 工具结果追加到 MessageList
   f. 如果调用了 terminate → state = FINISHED → 退出循环
   g. 否则回到步骤 a，继续下一轮 Think
5. 每步结果通过 SseEmitter 实时推送到前端
6. 前端 EventSource.onmessage 接收数据，更新 UI
```

### Z2: 这个项目中使用了哪些设计模式？分别在什么场景？

| 设计模式 | 应用位置 | 说明 |
|----------|---------|------|
| **模板方法** | `BaseAgent.run()` / `ReActAgent.step()` | 父类定义执行骨架，子类填充 `think()`/`act()` |
| **策略模式** | `ToolCallback[]` 可插拔工具 | 不同工具组合构造不同能力的 Agent |
| **状态模式** | `AgentState` 枚举 | IDLE→RUNNING→FINISHED/ERROR 生命周期状态转换 |
| **责任链** | `Advisor` 拦截器链 | 多个 Advisor 依次处理请求/响应 |
| **工厂方法** | `Result.success()`/`Result.error()` | 统一响应体创建 |
| **单例模式** | Spring Bean（`@Component`） | 无状态组件（LoveApp、工具类） |
| **原型模式** | VioManus 每次请求 new | 有状态 Agent 不能共享 |

### Z3: 项目中如何处理错误和异常？有哪些层次的容错？

**答**：
1. **HTTP 层**：`GlobalExceptionHandler` 捕获 11 种异常类型 + 兜底 Exception → 统一返回 `Result.error()`
2. **业务层**：`BusinessException` 携带 code + message，异常链保留根因
3. **AI 层**：`doOnError` 保护流式调用、Embedding API 欠费降级为空向量库
4. **Agent 层**：
   - `MAX_CONSECUTIVE_ERRORS = 3` → 自动终止
   - 工具内部 try-catch → 返回错误描述字符串而非抛异常
   - `volatile stopped` → 用户手动停止
5. **部署层**：`@Autowired(required = false)` + `@Lazy` 实现渐进式可用，可选组件未就绪不影响核心功能

### Z4: 如果要你优化这个项目的 Token 消耗，你会从哪些方面入手？

**答**：
1. **System Prompt 精简**：当前 `VioManus.SYSTEM_PROMPT` 较长，每次 Think 都发送，可用更简练的版本
2. **滑动窗口记忆**：`MessageWindowChatMemory.maxMessages(20)` 已经实现，可进一步减少到 10
3. **工具输出截断**：`MAX_TOOL_OUTPUT_LENGTH = 3000` 已在做，可以更激进（1000-1500）
4. **工具描述精简**：`@Tool(description)` 描述也会消耗 Token，保持简洁
5. **任务复杂度路由**：简单对话 → LoveApp（Token 少），复杂任务 → VioManus（Token 多）
6. **maxSteps 动态调整**：简单任务 5 步足够，不必固定 20
7. **模型选择**：简单任务用便宜模型（qwen-turbo），复杂推理用强模型（qwen-max）

## 🎯 企业级升级高频面试题与参考答案 🆕

### Q1：你们项目的 MCP 协议是怎么实现的？和直接用 Spring AI Starter 有什么区别？

> "我们的 MCP 不是简单调 Spring AI 的 starter，而是自建了 JSON-RPC 2.0 协议栈。底层实现了完整的 JsonRpcRequest/Response/Error 对象模型，包含 13 个结构化错误码——从 JSON-RPC 标准的 -32700（解析错误）到业务扩展的 -32013（权限不足）。中间层定义了 McpProtocolHandler 接口，规范了 initialize → tools/list → tools/call → shutdown 的完整生命周期。传输层做了抽象设计——McpTransport 接口统一了 connect/send/close，StdioTransport 通过 ProcessBuilder 启动子进程并用 synchronized 保证线程安全，SseTransport 手动实现了 RFC 6202 的 SSE 事件流解析。最上层是 McpGateway 门面，封装了会话管理和工具发现/调用的全部细节。整套协议栈约 2000 行代码，51 个测试用例覆盖全链路。"

### Q2：你们的安全是怎么设计的？怎么防止 Agent 越权调用？

> "我们实现了四层安全防护体系。第一层认证鉴权：基于 Spring HandlerInterceptor 的 API Key 验证，支持 X-API-Key Header 和 Bearer Token，通过 TokenBinding 将令牌与协议 ID 绑定，防止跨协议越权。第二层 HITL 审批：三级危险分级——HIGH（终端命令等）需要用户显式批准，MEDIUM（文件写入等）首次自动授权后记住，SAFE（搜索等）直接通过，支持 APPROVE/APPROVE_ALL/DENY/SKIP/MODIFY 五种决策。第三层执行围栏：PathGuard 三重防护（绝对路径外逃检测 + '..' 穿越拦截 + 符号链接逃逸检测），CommandGuard 内建 9 条危险命令正则匹配（sudo、rm -rf /、mkfs、dd、fork bomb、curl|sh 等）。第四层审计追溯：JSONL 按天持久化 + 11 个敏感字段自动脱敏（password/token/key/secret 等） + traceId 全链路关联。PathGuard 和 CommandGuard 在 HITL 之前执行 fast-fail，减少了 70% 的无效审批次数。"

### Q3：Agent 执行失败了怎么办？你们怎么保证可靠性？

> "从三个层面保证。首先是容错：工具调用采用指数退避重试（2^n 秒 + 随机 Jitter 0~1000ms），区分可重试错误（TimeoutException/IOException/ConnectException）和不可重试错误（SecurityException/IllegalArgumentException），最大 3 次。其次是幂等：基于 MD5(sessionId + stepIndex + toolName + paramsHash) 生成幂等 Key，24 小时缓存防止重复执行。第三是资源隔离：3 个专用线程池——agentReasoningExecutor（CPU 密集 4-8）、toolExecutionExecutor（IO 密集 8-16）、mcpTransportExecutor（4-8），通过 Semaphore 限制最大并发 Agent 数（默认 10），防止 OOM。分级超时按工具类别精确控制：搜索 15s、终端 60s、Agent 全局 10 分钟。"

### Q4：多智能体协作是怎么设计的？为什么不用单 Agent？

> "我们采用 Plan-and-Execute + DAG 依赖图模式。Planner 接收用户请求，调用 LLM 拆解为子任务列表并构建 DAG 依赖图。Orchestrator 用 Kahn 算法拓扑排序分层——同一层内的独立任务通过 CompletableFuture 并行提交到 Worker 池执行，跨层任务串行保证依赖关系。Worker 共享全局工具集，每个 Worker 独立执行单个子任务。Reviewer 对所有结果做 0-100 质量评分，不合格任务打回重试最多 2 次。对比单 Agent 的 ReAct 模式，Plan-and-Execute 的优势在于先全局规划再执行，避免走弯路。DAG 调度使独立任务并行、依赖任务顺序执行，复杂任务效率提升 55%。LLM 失败有完整降级策略：Planner 降级为单任务、Reviewer 降级为默认通过。"

### Q5：长对话的上下文怎么管理？记忆不会爆炸吗？

> "记忆系统采用三层架构。工作记忆保留最近 3 轮完整对话不压缩。短期记忆按 4 种类型（对话/事实/摘要/工具结果）存储，Token 阈值 4000 自动淘汰，淘汰前保留压缩摘要。长期记忆通过 JSON 文件持久化 + MD5 去重实现跨会话记忆，高重要性（≥7）的事实自动写入。上下文压缩使用 Map-Reduce 策略：保留最近 3 轮 → 旧消息每 5 条分片 → 每片生成摘要（Map）→ 合并所有摘要（Reduce）+ 提取关键事实。智能检索使用加权排序——关键词匹配 50% + 时间衰减 30% + 来源权重 20%，保证召回的相关性。"

### Q6：怎么追踪一次 Agent 任务的完整执行过程？

> "可观测性覆盖三个层面。链路追踪：每个 HTTP 请求在 ObservabilityFilter 中生成或继承 traceId，注入 SLF4J MDC，贯穿 Agent 全生命周期——BaseAgent.run() 创建 AgentLogContext、ToolCallAgent.act() 注入 stepType，所有日志自动携带 traceId。前端通过响应头 X-Trace-Id 获取，可用于问题排查。结构化日志：AgentLogContext 提供 fluent API + toJson() 输出，包含 traceId/spanId/sessionId/agentType/stepType/durationMs/outcome 等完整字段。指标监控：AgentMetrics 基于 AtomicLong 收集 9 项指标（执行次数/工具调用成功率/活跃 Agent 数/Token 消耗等），通过 /api/metrics 端点暴露 JSON 快照，可直接对接 Prometheus + Grafana。"

### Q7：你们的错误码体系怎么设计的？

> "采用 5 域分段管理——AG（Agent 层 5 个）、TL（工具层 5 个）、MCP（协议层 5 个）、SEC（安全层 6 个）、SES（会话层 3 个），共 24 个结构化错误码。每个错误码包含 domain/code/message 三段信息，支持 of() 反向查找。这种设计让问题定位可以从错误码直接判断出错的模块层级，比如 AG-003 就是 Agent 连续错误超限，SEC-005 就是命令被安全策略拦截。"

### Q8：如果要你重新设计这个项目，你会怎么做？

> "首先我会坚持当前的分层架构——Agent 编排层 → MCP Gateway → 安全层 → 可观测性层，每一层职责清晰、可独立测试。改进点有三个：一是引入真正的 MCP 协议市场对接（如提交到 MCP.so），让工具生态更丰富；二是将 HITL 审批从前端 UI 打通，实现真正的 Human-in-the-Loop 交互；三是增加多租户支持和配置热更新（Nacos），提升 SaaS 化能力。技术选型上，当前的 '零新 Maven 依赖' 策略适合面试展示深度，但生产环境可以按需引入 Resilience4j（熔断）、Micrometer（指标）、Redis（会话持久化）等成熟组件。"

**第 1 步：需求澄清与约束**
```
功能需求：
- 用户通过自然语言下达任务，Agent 自主规划、执行、返回结果
- 支持多种工具（搜索、文件、代码执行、第三方 API）
- 支持多种 AI 模型（可切换、按任务路由）
- 多租户隔离

非功能需求：
- 延迟：简单问答 < 2s，Agent 任务 < 10min
- 安全：API Key 认证、工具执行沙箱、审计追溯
- 可靠：工具调用重试、幂等设计、优雅降级
- 可观测：全链路 traceId、指标监控、告警
```

**第 2 步：架构图（白板画出）**
```
┌──────────────────────────────────────────────────────────┐
│                     API Gateway                           │
│            (鉴权 / 限流 / 路由 / rate limiting)            │
└───────────────────────┬──────────────────────────────────┘
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  Chat App    │ │  Agent Engine │ │ Multi-Agent  │
│  (RAG 对话)  │ │  (ReAct 循环) │ │ Orchestrator│
└──────┬───────┘ └──────┬───────┘ └──────┬───────┘
       │                │                │
       └────────────────┼────────────────┘
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  Tool Registry│ │ MCP Gateway  │ │ Memory System│
│  (本地工具)   │ │ (外部工具)    │ │ (三层记忆)   │
└──────────────┘ └──────────────┘ └──────────────┘
```

**第 3 步：核心组件设计**
- **Agent Engine**：ReAct 循环（Think → Act → Observe），可扩展 Plan-and-Execute
- **Tool Registry**：统一的 Tool 接口，`@Tool(description)` 注册，支持本地工具 + MCP 远程工具
- **MCP Gateway**：JSON-RPC 2.0 协议通信，STDIO/SSE 双传输模式
- **Memory System**：Working/ShortTerm/LongTerm 三层，Map-Reduce 压缩
- **Security**：API Key → HITL → PathGuard/CommandGuard → Audit 四层

**第 4 步：关键技术决策**

| 决策点 | 方案 | 理由 |
|--------|------|------|
| 同步 vs 流式 | SSE 流式 | 用户体验优先，实时可见 |
| 单 Agent vs 多 Agent | 按任务路由 | 简单任务不浪费资源 |
| 内存记忆 vs 持久化 | 三层架构 | 兼顾性能和持久性 |
| 自建协议栈 vs 用框架 | 生产用框架，面试展示自建 | 理解本质 |

**第 5 步：扩展性考虑**
- 水平扩展：无状态 Agent（每次 new 实例）→ 可任意扩容
- 模型热切换：策略模式，改配置切换 DashScope ⇄ OpenAI ⇄ Ollama
- 新工具接入：MCP 协议标准化，一行配置即可

### X2: 技术对比 — LangChain4j vs Spring AI，两个项目分别用了，为什么？

**答**：

> 这是我刻意设计的技术选型，两个 AI 框架各用一个项目来实践。

| 维度 | LangChain4j (AI-TuKu) | Spring AI (VIO AI Agent) |

### X3: AI-TuKu 项目核心面试题 — DDD 四层架构如何落地？

**Q**：你的 AI-TuKu 项目中说用了 DDD 四层架构，具体是怎么分层的？每层放什么？

**答**：

```
interfaces/ (接口层)
├── controller/        # REST API
├── websocket/         # WebSocket 端点
└── dto/               # 数据传输对象（与前端交互）

application/ (应用层)
├── service/           # 应用服务（编排多个领域服务）
├── event/             # 应用事件处理
└── assembler/         # DTO ⇄ Entity 转换

domain/ (领域层) — 核心业务逻辑
├── model/             # 领域实体、值对象、聚合根
├── service/           # 领域服务（纯业务逻辑）
└── repository/        # 仓储接口（只定义，不实现）

infrastructure/ (基础设施层)
├── repository/impl/   # 仓储实现（MyBatis-Plus Mapper）
├── config/            # 数据库/Redis/ES 配置
├── ai/                # LangChain4j AI 服务实现
└── external/          # 腾讯云 COS 等外部服务
```

> **关键原则**：依赖方向是 interfaces → application → domain ← infrastructure。domain 不依赖任何框架——理论上可以把这个模块抽出去换个框架（Spring Boot → Quarkus）而业务逻辑不变。

### X4: AI-TuKu 项目核心面试题 — 两级缓存怎么设计的？

**Q**：你的 Caffeine → Redis → MySQL 两级缓存命中率 ~70%，怎么设计的？

**答**：

```
读取路径：
1. 请求到达 → 查 Caffeine（本地缓存，纳秒级）
2. Caffeine miss → 查 Redis（分布式缓存，毫秒级）
3. Redis miss → 查 MySQL + 回填 Redis + 回填 Caffeine
4. 返回数据

写入路径：
1. 更新 MySQL（先写数据库保证数据不丢）
2. 删除 Redis 缓存（Cache-Aside 模式，而非更新）
3. 发送 Kafka 消息通知其他实例删除本地 Caffeine
```

| 缓存层 | 数据 | TTL | 容量 | 淘汰策略 |
|--------|------|-----|------|---------|
| **Caffeine** | 热门图片列表、首页数据、用户基本信息 | 5min | 10000 条 | LRU + Window-TinyLFU |
| **Redis** | 图片详情、搜索结果缓存、Session | 30min | 无硬限制 | TTL 自动过期 |

> **为什么删除而不是更新**：并发场景下 A 更新 DB → B 更新 DB → B 更新 Cache → A 更新 Cache，最终 Cache 是 A 的旧值。改为"删除 Cache"，下一次读请求自然回填最新值。

### X5: 实时协同编辑的 WebSocket + Disruptor 架构

**Q**：AI-TuKu 中实时协同编辑的 WebSocket + Disruptor 是怎么设计的？

**答**：

```
用户 A 编辑图片 → WebSocket 发送编辑事件
  → Disruptor RingBuffer (256K 事件) 异步发布
  → EventHandler 消费：
    1. 广播给同一图片的其他协作者（WebSocket 推送）
    2. 写入操作日志（用于冲突解决）
    3. 异步持久化到 MySQL（批量写入，减少 IO）
```

**为什么用 Disruptor 而不是 BlockingQueue？**
- 传统 `BlockingQueue` 有锁竞争，高并发下吞吐量受限
- Disruptor 使用环形缓冲区 + CAS 无锁设计，吞吐量提升 3 倍
- 完美匹配 WebSocket "一对多广播"场景

**协同冲突解决**：操作转换（OT）简化版——每个编辑操作携带 `baseVersion`，服务端检测 `baseVersion == currentVersion`，不匹配则拒绝并要求客户端先拉取最新版本。

### X6: 行为面试 — 技术选型的决策过程

**Q**：在 VIO AI Agent 项目中，你为什么选择"零新增 Maven 依赖"策略？

**答**：

1. **展示深度 > 堆砌宽度**：手写 JSON-RPC 2.0 协议栈 2000 行 + 51 个测试，比一行 `implementation 'spring-ai-starter-mcp-server'` 有说服力得多
2. **跨框架可迁移**：今天在 Spring Boot 实现的协议栈，明天可以搬到 Quarkus 或纯 Java 项目，核心逻辑 80% 不变
3. **维护成本**：Maven 依赖越多，版本冲突可能性越大（项目修复过版本冲突）。零外部库 = 零版本冲突

> 当然，生产环境我会按需引入成熟组件（Redis/Resilience4j/Micrometer），不会坚持自建。

### X7: 场景排查 — Agent 执行超时

**Q**：线上用户反馈 Agent 执行了 3 分钟还没结果，你怎么排查？

**答**：

```
1. 前端获取 traceId（响应头 X-Trace-Id）
2. grep traceId 查结构化日志：
   $ grep "traceId=abc123" /var/log/agent/*.log | jq '.'
3. 从日志还原 Agent 执行链路：
   - step 0: 生成思考 → OK (50ms)
   - step 1: 调用 searchWeb("宝可梦") → OK (2s)
   - step 2: 调用 webScraping("https://xxx") → TIMEOUT (15s)
   - step 3: 重试 webScraping → TIMEOUT (15s)
   - step 4: 重试 webScraping → TIMEOUT (15s)
   - step 5: 达到 MAX_CONSECUTIVE_ERRORS → 终止
4. 结论：目标网站响应慢导致连续超时
5. 优化：增加网站健康检查，不可用时自动跳过
```

### X8: 场景排查 — Token 消耗突增

**Q**：某天发现 Token 消耗比平时高了 3 倍，怎么排查？

**答**：

1. `GET /api/metrics` → 对比发现平均每任务 Token 从 8000 → 32000
2. 查审计日志 → 某类任务反复 20 步 maxSteps（正常 4-6 步）
3. 回溯对话 → 用户输入模糊 → Planner 拆解混乱 → Worker 反复重试
4. 解决：Planner 增加不确定性判断 → 高于阈值时反问澄清而非直接规划
5. 配置预警：单任务 Token > 20000 自动告警
