# 第 3 阶段：简历快照与原文证据溯源

日期：2026-11-05。完成本地实现、离线测试和实际 Chrome 演示验证；尚未执行真实数据库迁移或生产部署。

## 1. 用户可见的变化

候选人详情的“关键证据”中，只有能在对应原文中唯一定位的项目才显示“查看原文”。点击后打开分析时保存的正文并高亮，正文的空白、换行、中文和 emoji 均保留；已经填写的审核意见不会丢失。若采集库已有更新正文，会明确提示这是历史分析版本。

未命中原文、出现多次、概括性摘要、旧分析没有来源元数据、或来源校验失败时，都不会猜测定位。原 `evidence_summary: list[str]` 保留，模型输出仍为既有六字段；本阶段没有引入新模型调用、RAG 或向量数据库。

原文位置一致只证明引用来自该文本，**不证明它语义上足以支持 AI 结论**。

## 2. 后端数据流

1. 网关在请求前冻结正文摘要，返回结果时附加独立 `analysis_run_id` 与 `analyzed_text_hash`；它们不进入模型六字段契约。
2. 写分析缓存时，校验待保存正文与输入摘要一致，并显式绑定岗位和分析版本。
3. 在同一事务中插入不可变正文、分析结果记录、可核验引用，再更新缓存的当前分析指针。后续缓存写入失败会一起回滚。
4. 引用以 Unicode 码点半开区间标记，quote 必须唯一且与原文完全一致，身份与范围参与引用 ID。
5. 详情接口先完成候选人/岗位/批次可见性判断，再按服务端选中的运行指针读取；重新验证身份、岗位、版本、结果摘要、正文摘要和完整引用集合。
6. 对已有来源绑定的新记录，先按真实岗位收紧范围，再选择最新分析，避免同一候选人的另一岗位较新结果混入当前详情。无来源的历史记录保留旧兼容策略，不假装有准确岗位来源。

正文的规范化版本为 `exact-codepoints-v1`，实际上不做 trim、CRLF 改写或 Unicode 归一化，因此无需从重排文字反推原文位置。前端通过 `Array.from` 对齐 Python 的码点计数，引用页面直接渲染原始文本，不在重排后的结构化正文上截取偏移。

新增实体：

| 表 | 内容 |
| --- | --- |
| `candidate_resume_snapshots` | 候选人归属、原文、SHA-256、规范化版本、创建时间 |
| `candidate_resume_analysis_runs` | 分析运行、岗位与版本、快照、结果及摘要、来源类型 |
| `candidate_resume_evidence_refs` | 运行/快照归属、摘要序号、原文范围、quote 与来源片段 ID |

现有分析缓存增加可空 `analysis_run_id/analyzed_text_hash`。旧数据保持 NULL，读取详情不写入数据，不自动“补造”历史来源。

快照身份在调用前以摘要冻结，实体在结果落库时写入；**调用中进程崩溃的持久化恢复仍由第 5 阶段处理**。应用提供追加和幂等写入，不覆盖同一运行/快照；这不是防数据库管理员篡改的存储。读侧会拒绝能检测到的不一致。

## 3. Provider 与历史兼容边界

默认 OpenAI 兼容路径将完整正文提交到接口，可直接绑定原始正文。

现有 Coze 适配器会压缩空白并截断到 4000 字符。本阶段仅在处理后正文与原文完全一致时绑定来源；经过变换的 Coze 结果保留原业务功能，**不提供未经证明的原文引用**。没有为了展示引用而改变旧 Coze 输入规则。映射、变换后输入快照或长文本策略属于后续工作。

旧记录、新接口返回值与旧前端兼容：

- 新字段为 `analysis_run_id / analysis_snapshot / evidence_refs / evidence_status`。
- 无来源的旧记录返回 NULL / 空数组 / legacy，旧证据字符串不变。
- invalid 状态不返回指针、快照或引用；前端只展示“原文引用校验未通过”。
- `analysis_snapshot.is_current` 比较最新已保存的主记录正文，主记录缺失时比较详情正文；不表示已检查手机上是否有更新。
- 当前 API 返回选中分析的快照，没有新增任意历史快照 ID 读取入口或全部分析历史浏览功能。
- 既有候选人身份合并若改变缓存归属，不会重写不可变历史快照；无法匹配时引用失效并等待显式重评/迁移，不跨身份复制来源。

## 4. 数据库迁移与演示版本

新增迁移 `migrations/versions/20261105_04_resume_evidence.py`，前置为 `20261105_03`。它创建三张表并为缓存增加两列，**不回填历史分析**。MySQL 表使用 InnoDB，原文采用 LONGTEXT。

已有真实库在启动新应用、采集或报表前，应先核对环境、历史 revision 和备份，再按既有部署流程执行 `python -m alembic upgrade head` 至 `20261105_04`。本次没有执行该真实库命令。缺少新结构时采集 schema 检查直接提示迁移，不在运行时偷偷创建证据表；新库仍需准备既有采集基础表及完整迁移流程。

本地演示改用 `artifacts/hr_demo/demo-v4.sqlite3`，保留 v2/v3，不修改旧演示审核。全新本地 SQLite 由演示入口显式初始化，96 条扩充虚构记录带有 `synthetic_fixture` 来源；原有 3 条精简记录继续用于验证 legacy 展示。当前演示岗位仍是历史财务/营销场景，AI/FDE 演示统一保留至第 7 阶段。

正常回退优先切回旧代码并保留新增结构与历史数据。若要删除本阶段结构，需先停新写入、备份原文及运行数据，再评审降级至 `20261105_03`；降级会丢弃新列与三张表的数据，不自动执行。

## 6. 复现浏览器验证

安装既有前后端依赖，并确保本机 Chrome 可用后，分别启动：

```powershell
# 仓库根目录，终端一
.\.venv\Scripts\python.exe -m uvicorn scripts.run_hr_demo:build_demo_app --factory --host 127.0.0.1 --port 18081

# web/hr-review，终端二
$env:HR_API_PROXY_TARGET="http://127.0.0.1:18081"
$env:VITE_HR_DEMO="true"
node.exe node_modules/vite/bin/vite.js --host 127.0.0.1 --port 15174 --strictPort

# web/hr-review，终端三
node.exe scripts/check-evidence-demo.mjs
```

检查脚本仅接受回环主机，并确认前端有“仅包含虚构数据”标识；仅写本地演示登录会话和截图，不提交审核。它不是远程生产探测入口，也尚未作为远程 CI 的浏览器步骤运行。
