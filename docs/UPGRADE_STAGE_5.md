## 2. 核心语义

### 入队与版本

入队事务同时保存完整不可变原文快照与任务；不用等待模型返回才保存输入。调用方必须提供实际评分契约及完整推理指纹；队列再次绑定契约，生成有效 pipeline 指纹。幂等键包含候选人、岗位、快照和有效 pipeline。

同一输入/版本重复提交只产生一个任务；后续批次可引用它，但不重置尝试次数、deadline 或预算。跨批次复用的调用占用归首次入队批次，后续批次不重复计费。关闭采集的批次不再接受新任务或新引用，已有引用的幂等重试仍可返回原任务。

新正文或版本入队后更新当前任务指针，并清空其当前发布结果；旧结果保留在历史。未启动的旧任务转 `superseded`，不消耗调用；仍持有有效租约的旧任务可以保存历史结果，但不能发布为当前结果。重新提交旧幂等键也不能把指针倒退。

“最新”指队列最新接受的入队请求；未来采集适配器还须校验采集顺序/版本，不能把乱序的历史输入当新采集提交。

### 租约与事务

```text
pending -> running -> succeeded
              |-> retry_wait -> running
              |-> failed / cancelled / superseded
```

每次领取递增 token，心跳不换 token。读取输入、心跳、失败或完成都检查 running 状态、owner、token、租约和总 deadline。租约到期先标记旧尝试 abandoned，再按退避时间重领；旧 Worker 的晚到提交被拒绝。

结果、原文引用、任务完成和当前结果指针在同一事务提交；任一写入失败全部回滚。相同租约重复提交相同结果幂等，不能更换已完成结果。任务至少一次执行；不承诺外部请求 exactly-once。

当前实现用短事务中的共享 control 行锁串行化队列状态变更，模型工作在锁外执行。MySQL 使用 `SELECT ... FOR UPDATE`，接口依据 [SQLAlchemy 官方文档](https://docs.sqlalchemy.org/en/20/core/selectable.html#sqlalchemy.sql.expression.GenerativeSelect.with_for_update)；SQLite 使用 `BEGIN IMMEDIATE`，写入并发限制见 [SQLite 事务文档](https://www.sqlite.org/lang_transaction.html)。没有使用或宣称验证过 SKIP LOCKED。默认时钟来自数据库 UTC，合成测试才注入虚拟时钟。

### 预算、限流与重试

- 每次实际派发回调前，事务内同时占用任务、首次入队批次和共享分钟额度。队列满时拒绝新任务并要求上游暂停；幂等查询仍可返回已有任务。
- 请求数不退还；token/费用按预留保守占用，不因失败、进程退出或未知 usage 退还。报告值超过预留时补记超额，后续调用被预算限制；已发生的超额不能撤销。
- 费用使用同一币种的整数微单位，价格版本和币种在 control 行固定。演示 `USD / synthetic-fixed-v1` 只是测试身份，不是供应商价格。未知实际 usage 保持 null，不填 0。
- 共享请求/token 限流使用数据库 UTC 的固定分钟窗口，时钟倒退不清空额度。它不是滑动窗口或供应商完整风控模型，分钟边界可能产生突发；真实接入需按供应商规则设置余量。
- 429、超时、暂时不可用和普通 Worker 错误受最大次数、deadline、指数退避和稳定 jitter 限制；429 同时尊重 Retry-After。无效输出、身份/输入错误和预算耗尽不自动反复调用。
- 操作员只能提前已有可重试任务的调度时间，不能重置次数、预算或 deadline；429 等待不能绕过。动作写入操作员 ID 事件，终态任务不得直接恢复为全新预算。

当前“一次派发”就是一次合成回调。**不能把现有内部多次重试的网关直接接为回调，却仍按一次请求记账。** 真实 provider 接入必须让每次 SDK 请求/重试都经过预留并上报 usage，统一已有重试层与队列重试层，这部分仍未实现。

### 并发和状态

线程池支持 1–4 个本地回调；实际队列还受共享在途上限约束。SQLite 演示强制单 Worker。线程池的双回调并发通过独立 stub 测试，不是 MySQL 领取并发测试。

失去租约后仍占用本地物理线程槽，直到回调真正返回。调度 horizon 只停止派发，不能杀死线程或撤回外部请求；生产适配器必须设置 SDK 请求超时。DB 的租约在途数也不代表已中断旧网络请求，跨进程实际在途需要超时/取消及供应商限制共同验收。

批次分开返回 `collection_completed`、`analysis_pending`、`analysis_completed`、`analysis_succeeded` 和 `all_succeeded`。completed 表示终态数，包括失败/取消/被替代，不代表全部分析成功。状态读取不执行隐式重试，过期回收在调度领取时进行。

## 6. 第三轮：单次 SDK 请求与持久化回执

### 实现范围

新增 `queued_request_plan.py`、`queued_openai.py` 和 `20261105_07_request_accounting.py`：

- 入队时冻结模型、完整 system prompt、输出上限、请求超时、合成输入预留、币种/费率/价格版本、SDK 版本及适配实现摘要，保存到 `analysis_request_plans`。计划摘要参与任务身份；预算必须覆盖计划预留，价格身份必须匹配队列。
- 新适配器直接发出一次 Chat Completions SDK 请求，不调用既有内部重试网关；SDK `max_retries=0`，重试只由队列负责。每个租约只允许开始一次请求，HTTP 重定向关闭。
- `analysis_request_receipts` 在请求前保存规范请求摘要，在响应或异常后保存脱敏回执；只含状态、HTTP 码、耗时、usage、保守占用及摘要，不含简历、提示词、原始错误或响应 ID。共新增两表，累计 10 张队列/请求相关表，无历史回填。
- 回执和超额占用同事务记录，重复同一回执不重复记账，已完成回执不可更换。任务结果必须在回执持久化之后提交；契约或引用仍需原有校验。
- 请求已经开始后，取消/租约失效不阻止原 owner 补记该次回执和预算占用；此入口不能更新当前分析指针或发布结果。晚到 usage 不会因 Worker 丢弃结果而被直接丢掉。

本轮使用**已安装的 OpenAI Python SDK 2.54.0**，通过实际 HTTP 请求连接临时本地假服务，响应为预置 JSON；没有真实模型推理。SDK 行为核对了本机实现及 OpenAI Docs 的 [Python SDK 说明](https://developers.openai.com/api/reference/python)。关闭内置重试、保留 Retry-After 并限制总尝试次数的取舍也参照 [官方限流文档](https://developers.openai.com/api/docs/guides/rate-limits)。没有迁移现有生产网关或替换模型。

### 状态、usage 与预算

401/403 为认证终态；429 区分暂时限流与明确的额度/计费拒绝。可重试的 408/409/429/5xx 沿用队列退避；尊重 Retry-After 秒数、毫秒或 HTTP 日期。有效等待超过当前支持的 3600 秒时进入 `retry_delay_exceeded`，不会把长等待截短后提前请求。未知或非法等待值才回到普通退避。

usage 缺失或仅部分存在时，未知字段保留 null；没有把未知当成 0。已知分项超过预留时补记保守占用；全量 usage 和模型身份均通过校验时才计算该计划下的估算费用。完整费用存在未知项时，总估算仍为 null。模型返回身份不符时费用未知且不发布结果，不擅自套用另一个模型的费率。

HTTP 200 的 `received` 仅代表收到了响应，**不代表评分有效**。无效 JSON、分数不合约、拒绝或截断会使任务失败，但已报告 usage 仍入账。缺失 usage 的合约有效结果可以保留，同时继续占用预留，费用保持未知。

费用按整数微单位向上取整；预留不退款，实际超额只能阻止后续请求，不能撤销已经发生的消耗。这里的价格、token 数和输入预留全部是合成夹具；`synthetic-utf8-reservation-v1` 只是本地输入单位约定，**不是真实 tokenizer，也不证明真实输入 token 上界**。

每次请求的 SDK timeout 不超过当前队列 deadline 的剩余时间；这仍是 HTTP 阶段超时，不是杀死远端工作的硬截止机制。总 deadline 的结果提交拦截和晚到记账仍由队列执行。SDK/实现版本与计划不符、输入预留不足时，在请求前拒绝派发；此时尝试预留仍保守保留，HTTP 数可以少于已领取尝试数。
