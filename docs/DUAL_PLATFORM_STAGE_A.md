## 无招聘者账号时如何推进

当前可运行现有 AI/FDE 虚构简历演示及队列集成演示，见[本机启动文档](HR_LOCAL_START.md#无招聘者账号的运行方式)。不需要手机、招聘平台账号或真实模型密钥，使用隔离 SQLite 和预置合成输出。

后续按以下顺序开发，而不是等待申请账号：

1. **B：统一来源契约与存储。** 使用明确标记为虚构的 Liepin/BOSS 事件，验证来源隔离、幂等、同名不合并及人工记录保留。
2. **C：双平台适配器。** 先实现夹具回放入口、规范化与只读命令边界；真实 CLI 字段差异和正文权限标注为待核验，不伪装成已抓取数据。
3. **D：本地闭环。** 合成平台事件 → 来源/快照 → 单个父分析批次 → 队列/合成模型 → HR 审核；明确展示模拟来源。现有演示尚不具备这套双平台导入链路。
4. **真实账号验收。** 用户获得合法招聘者权限后，分别核验两个平台，再以小批量真实数据替换夹具；不改变后端审核流程，不自动启用外部沟通。

普通求职者账号不作为招聘者接口替代。也可以后续增加本人获授权的简历文件导入入口，但当前尚未实现，不将其描述为现成功能。未经真实平台验收前，只交付“模拟双平台闭环”，不宣称可直接批量采集。

## 操作步骤

在项目根目录执行。现有虚拟环境需已安装本项目，使 `liepin_rpa` 可导入。

```powershell
cd D:\jianlizhuanqu
# 首次安装或在干净环境恢复固定依赖；需要网络。
.\.venv\Scripts\python.exe -m scripts.setup_recruiting_toolchain --install

# 日常自检，不安装依赖、不登录平台。
.\.venv\Scripts\python.exe -m scripts.setup_recruiting_toolchain

# 先登录猎聘；完成后再处理 BOSS，真实采集首版串行。
.\.venv\Scripts\python.exe -m scripts.recruiting_login --platform liepin
.\.venv\Scripts\python.exe -m scripts.recruiting_login --platform boss
```

猎聘入口为 <https://lpt.liepin.com/>；BOSS 入口为 <https://www.zhipin.com/>，进入招聘者侧后由本人完成登录与验证。密码、验证码和 Cookie 不需要发送给开发者，也不写入配置。

命令返回 `awaiting_manual_verification` 表示浏览器已就绪、等待人工确认，**不代表登录完成**。`reopened_owned_browser` 表示为已有专用进程重新打开窗口。重复执行显式登录命令会新开同一专用 profile 的窗口；正在验证时无需重复执行。

本机端口：BOSS `19470`，猎聘 `19471`。`doctor` 仅使用独立本地环境做 help 检查，预留 `19480` / `19481`，不会打开浏览器。额外账号需要先分配端口，当前不接受任意账号别名。

本地状态在 `artifacts/recruiting/`：工具报告 `toolchain-report.json`，账号目录 `accounts/<平台>/primary/`，上游快照 `upstream/<commit>/`。这些目录被 Git 忽略，不能作为公开 CI 产物上传。停用时手动关闭对应专用窗口，不删除登录资料、不影响日常浏览器。

## 本机问题与处理

最初上游启动路径在本机没有显示可见窗口；仅检查进程或调试端口也无法判断用户是否看到了页面。现改为 Windows 原生可见窗口启动，并在显式重试时为已有专用 profile 打开新窗口。

GUI 启动保留必要的真实 Windows 用户环境，CLI 的 Node HOME 仍隔离。端口已占用时核对浏览器可执行文件、profile 与调试端口；不符合时停止，不关闭占用者。脚本仅对本项目 PowerShell 启动入口使用进程级 `ExecutionPolicy Bypass`，不修改系统执行策略。

如果仍无窗口，可在项目根目录重新执行对应 `recruiting_login` 命令，并检查任务栏 Chrome/Edge。出现 `owned_browser_launch_or_verification_failed` 或 `visible_browser_port_not_ready` 时保留现场排查，不通过结束所有 Chrome 进程解决。

## 登录后的 A 阶段验收

1. 人工确认招聘者后台与目标职位入口；分别记录已登录、岗位是否可访问。
2. 先确定每个平台的小样本查看额度，再执行只读列表及少量正文预览，避免意外消耗权益。
3. 记录实际候选 ID、请求引用与返回 ID 的关系、正文类型、结构化字段和缺失项；真实材料仅保存在受控本地目录，提交兼容夹具前脱敏。
4. 明确哪些入口仅返回摘要，哪些能读取在线正文或图片；学历名称不能自动推断为统招学历。
5. 形成两平台实际能力清单，再推进 B 的来源身份/存储与 C 的只读适配器。

不启用消息、索要简历、拒绝、日历或外部推送。登录完成后仍需核验正文权限，不能仅凭后台页面判定可采集。
