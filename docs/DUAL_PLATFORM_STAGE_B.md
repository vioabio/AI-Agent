# 双平台 B 阶段：来源事件与幂等存储

日期：2026-11-07。前置：[A 阶段工具与账号状态](DUAL_PLATFORM_STAGE_A.md)。总体方案：[双平台接入方案](DUAL_PLATFORM_COPILOT_INTEGRATION_PLAN.md)。

## 已实现范围

本轮完成 B 阶段的基础存储：统一事件契约、平台/账号范围、来源身份、不可覆盖的采集观察及父批次映射。提供完全不依赖手机、招聘账号或模型密钥的虚构数据运行入口。

**尚未完成整个 B–D 闭环**：新事件不会直接派发模型、写旧候选表或进入 HR 页面；CLI 适配器、完整资格规则、旧正文唯一约束兼容、正式导入与队列投影仍待开发。真实平台字段稳定性也未验收。

## 可以直接运行

在项目根目录执行：

```powershell
.\.venv\Scripts\python.exe -m scripts.run_sourcing_fixture
```

每次创建新的隔离 SQLite，位置为 `artifacts/recruiting/fixture-ledger/<随机目录>/sources.sqlite3`，同目录生成 `report.json`。不读取生产 `.env`，不接受外部数据库地址，不打开浏览器、不请求平台或模型、不写 HR 表。命令不启动网页服务、不占用端口。

预期结果：1 个父任务、2 个平台子任务、5 个独立来源身份、5 条观察事件；另一次原事件重放返回 `replayed`。三个完整文本为 `text_ready`，一个列表摘要为 `insufficient_content`，一个没有稳定 ID 的记录为 `identity_unverified`。

`text_ready` 只表示原文及来源标识满足下一步处理条件，**不表示资格规则、匹配评分或真实身份已经验证**。文本全部为虚构，CLI 版本明确标为 fixture，不冒充真实采集输出。原有 HR 演示仍按[本机启动文档](HR_LOCAL_START.md)运行。

## 契约与身份边界

`SourceObservation` 采用严格、禁止未知字段的契约，可从有限大小 JSON 解析。记录模式、事件/任务、平台/账号、内部岗位、平台候选/简历 ID、请求引用、显示名、带时区采集时间、版本、内容类型、完整性及正文。

- 模式区分 `fixture` 与 `live`，存储绑定必须匹配；fixture 仅允许 SQLite。真实采集入口本轮没有实现。
- 身份键包含模式、平台、账号、ID 类型及来源 ID。优先候选 ID，其次简历 ID；仅简历 ID 时为保守的简历级身份，不能证明不同简历 ID 属于同一人。
- 没有来源 ID 时生成本次观察范围的临时身份；不同观察不自动合并，不把列表序号当成稳定 ID。
- 姓名与正文不参与身份合并，账号间、平台间不自动关联；新来源身份尚未绑定旧手机档案。
- 请求引用和返回的简历 ID 分别保存。同一候选 ID 的正文变化追加新事件，不修改旧事件。
- 只有 `api_text` 且明确 `full` 才具备文本就绪条件。列表摘要不能标为完整正文，图片没有转写时不能附造文本；OCR 尚未实现。
- 时间必须带时区并归一为 UTC，正文与 JSON 总体积有上限。事件不接受 Cookie、Token 或任意未知字段。上游回执封装与事实证据结构在适配器阶段补充；当前载荷 hash 是规范化事件摘要，不是已核验的上游回执证明。

## 事务、幂等和预算

`SourceStore.create_run` 显式接收岗位、两个以内的平台账号范围和父预算，配置一旦创建不可替换。平台列表顺序可变，预算、账号、岗位不能变。每个平台首版只允许一个账号。

每个父任务仅预留一个 `analysis_batch_id`，两个平台共用父预算；**当前没有创建分析队列批次，也没有执行额度扣费**。D 阶段负责实际队列预算，不能给两个平台分别复制整份额度。

`SourceStore.append` 在事务内核验父任务、岗位和账号范围，再追加身份与观察。SQLite 使用 `BEGIN IMMEDIATE`，MySQL 对父任务加行锁。事件幂等范围为模式、父任务、平台、账号及事件 ID：

1. 同一事件、同一规范化内容返回 `replayed`，不重复创建记录。
2. 同一事件 ID 携带不同正文、时间或其他内容，报 `event_payload_conflict`，保留第一次记录。重试发送方应复用最初回执，不重新生成采集时间。
3. 原文更新使用新事件 ID，身份保留、历史追加；新父任务中的观察同样追加历史。

当前没有提供删除/覆盖接口，也没有浏览器多进程租约。账户租约与 fencing 留到实际执行器阶段。

## Schema 与迁移

新增 revision **`20261107_09`**，父版本 `20261105_08`，只新增四张表：

| 表 | 作用 |
| --- | --- |
| `sourcing_runs` | 内部岗位、模式、配置、父预算与未来分析批次映射 |
| `sourcing_platform_runs` | 平台、账号及平台岗位引用 |
| `candidate_source_identities` | 来源身份与预留候选指纹 |
| `sourcing_observations` | 规范化载荷、摘要、关联、采集时间及就绪条件 |

MySQL 使用 `utf8mb4_bin`，避免大小写不同的标识被当成相同值，载荷列为 LONGTEXT。本轮未对真实库执行迁移；fixture 使用新库 metadata 初始化，另有 Alembic 隔离 SQLite 升降级及 MySQL SQL 生成检查。

已有环境使用新存储前，先备份、在隔离环境验证，再通过现有 Alembic 配置升级到 `20261107_09`。旧分析 Worker 的最低版本仍是 `20261105_08`。不要为体验 fixture 给真实库执行升级。正常停用保留账本；downgrade 会删除这四张新表，只能用于明确的维护回退。

## 旧正文唯一约束审查与剩余工作

旧候选表的 `experience_hash` 全局唯一仍保留，新账本不向该表投影。同正文的双平台观察可以独立保存，但正式审核尚未支持这条新导入链路。

后续须联动审查 `db.py` 的 `upsert_contacted_candidate_record`、`get_candidate_record_by_experience_hash`、历史身份匹配/合并、`_backfill_resume_experience_hashes`，以及 `analysis_projection.project_current_result`。区分内容去重、来源身份、旧手机身份及人工抑制范围，处理查询歧义，禁止只删唯一索引。

`record_candidate_source_locator` 仍固定写 `liepin`，正式导入前须参数化并保持旧手机默认行为。规则服务还需身份去重、冷却、人工抑制及岗位资格要求，不能仅凭 `text_ready` 入队。

后续顺序：补旧存储兼容及明确来源绑定，再完成 C 的虚构输出回放/双平台归一化，最后接 D 的父预算、队列和 HR 来源展示。实际招聘者账号可在本地开发完成后再申请并核验。
