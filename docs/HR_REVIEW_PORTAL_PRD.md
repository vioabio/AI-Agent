## 1. 背景

当前项目已经完成猎聘候选人的自动搜索、详情采集、上海求职意向过滤、岗位独立 Coze 分析、正式分享链接/收藏、去重沟通、MySQL 落库及日报生成链路。

现阶段的主要缺口是：HR 无统一界面查看可行动候选人、提交人工判断并更新后续招聘进度。人工反馈需要通过代码或数据库操作写入，审核效率低、多人协作不可追溯，日报也无法清晰区分“AI 初筛结果”和“HR 实际推进状态”。

本需求建设一个独立的 HR Web 工作台，将自动化初筛结果、人工审核、招聘进度和日报预览连接成完整闭环。

## 2. 产品目标

### 2.1 核心目标

1. HR 可以在浏览器中查看系统筛选出的候选人及完整判断依据；
2. HR 可以提交审核结论、招聘阶段和文字反馈；
3. 系统保留每次人工操作的完整审计记录，不覆盖历史 AI 事实；
4. 多名 HR 可以安全协作，避免并发提交互相覆盖；
5. 工作台概览和日报预览读取 MySQL 最新状态；
6. 后续日报生成时使用与工作台相同的数据口径；
7. 新功能不得影响手机采集进程、锁、checkpoint、run_state、Coze 路由和自动沟通安全规则。

### 2.2 成功指标

- 可行动候选人可以全部在工作台中被查询；
- HR 审核提交成功率不低于 99.9%；
- 每次状态变更均能追溯到审核人、时间、旧状态、新状态和备注；
- 工作台统计在提交后 5 秒内更新；
- 日报预览在提交后 30 秒内反映最新进度；
- 不发生人工反馈覆盖 AI 评分、AI 三态或证据的情况；
- 不发生已人工处置候选人被自动重复沟通的情况。

## 3. 非目标

第一阶段不包含：

1. 在工作台中启动、停止或续跑手机采集；
2. 在工作台中直接调用猎聘 App 打招呼；
3. 自动发送飞书日报或测试日报；
4. 修改已经发送的飞书 Webhook 卡片；
5. 复杂组织架构、绩效排名和排班系统；
6. 候选人端门户、面试邀约日历或 offer 审批；
7. Redis、Celery、WebSocket 或微服务拆分；
8. 覆盖或重算历史 Coze 结果。

## 4. 用户与权限

| 角色 | 权限 |
|---|---|
| HR | 查看授权岗位候选人、提交审核和招聘进度、查看本人及候选人审核历史 |
| 招聘负责人 | 查看全部岗位、全部 HR 进度、调整候选人负责人、查看日报预览 |
| 管理员 | 管理用户、角色、岗位权限和系统配置 |
| 只读用户 | 查看候选人、统计和日报预览，不可修改 |

第一阶段可以使用本地账号登录；应预留后续接入企业 SSO/OIDC 的能力。

## 5. 核心业务口径

### 5.1 AI 原始事实

AI 三态继续使用主项目统一规则：

| `match_result` | 中文状态 | 自动沟通授权 |
|---|---|---|
| `relevant` | 匹配 | 允许，但仍需通过身份、历史沟通和页面校验 |
| `needs_review` | 待复核 | 禁止 |
| `not_relevant` | 不匹配 | 禁止 |

工作台不得修改以下 AI 事实：

- `match_result`；
- `analysis_status`；
- `match_score`；
- `score_breakdown`；
- `analysis_reason`；
- `evidence_summary`；
- `analysis_version`。

### 5.2 默认可行动审核队列

默认进入 HR 待审核队列的候选人：

```text
全部 relevant
+ needs_review 且 match_score >= 90
- Coze API 临时异常产生的伪待复核
- 已完成 HR 处置的候选人
```

`not_relevant` 和 `needs_review < 90` 不进入默认待审核队列，但有权限的用户可以在“全部候选人”中查询。

### 5.3 身份与去重

- 候选人主身份使用 `candidate_fingerprint`；
- 相同简历的辅助归一使用 `experience_hash`；
- 姓名不能作为唯一键；
- 页面展示时可以显示姓名，但所有更新接口必须使用候选人指纹；
- 同一候选人在多个搜索词或批次中命中，只生成一个当前审核状态，保留多条来源和命中历史。

## 6. HR 招聘状态

### 6.1 状态定义

| 状态代码 | 页面名称 | 含义 | 是否属于进行中 |
|---|---|---|---|
| `pending_review` | 待审核 | 尚未有 HR 人工结论 | 是 |
| `recommended_contact` | 建议沟通 | HR 判断值得进一步联系 | 是 |
| `contacted` | 已联系 | 已通过猎聘、电话或其他渠道联系 | 是 |
| `interviewing` | 面试中 | 已进入面试流程 | 是 |
| `on_hold` | 暂缓观察 | 暂不推进，但保留后续可能 | 是 |
| `resume_rejected` | 简历淘汰 | 简历阶段不再考虑 | 否 |
| `interview_rejected` | 面试淘汰 | 面试后不再考虑 | 否 |
| `hired` | 已录用 | 已确认录用 | 否 |

### 6.2 推荐状态流转

```text
待审核
  ├─ 建议沟通 → 已联系 → 面试中 → 已录用
  │                         └─ 面试淘汰
  ├─ 暂缓观察
  └─ 简历淘汰
```

系统允许负责人纠正误操作，但每次纠正必须新增审计事件，不能删除旧记录。

### 6.3 自动化抑制规则

- 候选人一旦产生正式 HR 处置，后续自动化默认不再自动沟通，避免重复联系；
- `resume_rejected`、`interview_rejected`、`hired` 从 AI 可行动候选人列表和待办中移除；
- `recommended_contact`、`contacted`、`interviewing`、`on_hold` 从“待审核”移出，但继续出现在招聘进度统计中；
- 已结束候选人仍保留在累计 HR 进度和历史审计中；
- 人工状态不得把 `needs_review` 转换成 AI 的 `relevant`，两套状态独立展示。

## 7. 页面信息架构

页面视觉可参考现有“工作台”截图，采用顶部导航、左侧筛选、顶部指标卡、中间列表和右侧详情抽屉。

### 7.1 顶部导航

- 产品名称：候选人审核与招聘进度工作台；
- 搜索批次选择；
- 当前登录人；
- 日报实时预览入口；
- 退出。

批次选择默认显示“最新完成批次”。不能只按自然日取数，因为双岗位搜索可能跨午夜断点续跑。

### 7.2 指标卡

- 可行动候选人；
- 待审核；
- 建议沟通；
- 已联系；
- 面试中；
- 已淘汰；
- 已录用。

指标支持按批次、岗位和审核人联动筛选。

### 7.3 左侧筛选

- 岗位；
- 搜索批次；
- AI 结论；
- AI 分数范围；
- HR 状态；
- 是否已打招呼；
- 审核人/负责人；
- 候选人姓名、公司、职位或搜索关键词；
- 是否有正式简历链接。

左侧可展示“我的审核进度”，第一阶段不建设公开绩效排行榜。

### 7.4 页签

- 待我审核；
- 全部待审核；
- 推进中；
- 已结束；
- 全部候选人。

### 7.5 候选人列表

| 字段 | 说明 |
|---|---|
| 候选人 | 清洗后的候选人姓名 |
| 岗位 | 达人营销与达播负责人 / 财务共享与管理经理 |
| 年龄 | 已采集年龄；未知时显示“-” |
| AI 结论 | relevant / needs_review / not_relevant |
| AI 分数 | 原始分数 |
| 当前公司/职位 | 从简历摘要提取 |
| 沟通状态 | 未发送、已发送、发送失败、历史已沟通 |
| HR 状态 | 当前人工进度 |
| 负责人 | 当前分配的 HR |
| 更新时间 | 最近一次人工或数据更新时间 |
| 操作 | 查看详情、提交审核 |

列表必须支持服务端分页、排序和筛选。完整简历不直接塞入表格。

### 7.6 候选人详情抽屉

详情至少包括：

1. 基础信息和岗位；
2. 正式猎聘分享链接；
3. 无正式链接时的收藏/定位状态；
4. 完整简历正文；
5. AI 三态、评分、分项评分、分析理由和证据；
6. 搜索关键词、搜索包和来源账号；
7. 猎聘互动提示，明确标注“非候选人姓名”；
8. 历史沟通状态；
9. 当前 HR 状态和反馈；
10. 全部人工操作历史。

### 7.7 提交审核

提交表单字段：

- 新状态，必填；
- 反馈备注，必填；
- 负责人，可选；
- 当前数据版本，隐藏提交；
- 是否确认，结束状态必须二次确认。

提交成功后，列表、指标卡、详情历史和日报预览同时刷新。

## 8. 日报联动

### 8.1 实时含义

第一阶段“实时更新”定义为：

- 工作台日报预览直接读取 MySQL 最新人工状态；
- 页面通过重新聚焦或 15～30 秒轮询刷新；
- 下一次正式生成日报时读取同一套最新统计；
- 已发送的 Webhook 飞书卡片不自动编辑。

若未来需要修改已发送的同一张飞书卡片，需要独立评估飞书应用身份、消息 ID、更新消息权限和后台刷新任务。

### 8.2 日报新增 HR 进度

日报预览和后续正式日报增加：

- 待审核；
- 建议沟通；
- 已联系；
- 面试中；
- 暂缓观察；
- 简历淘汰；
- 面试淘汰；
- 已录用；
- 本统计窗口新增人工反馈人数。

必须明确分开：

1. AI 原始三态计数；
2. AI 可行动待办计数；
3. HR 实际招聘推进计数。

三者不得混用或互相覆盖。

## 9. API 需求

API 统一使用 `/api/v1` 前缀。

### 9.1 认证

```text
POST /api/v1/auth/login
POST /api/v1/auth/logout
GET  /api/v1/me
```

### 9.2 批次与统计

```text
GET /api/v1/batches
GET /api/v1/dashboard/summary
GET /api/v1/reports/live-preview
```

### 9.3 候选人

```text
GET   /api/v1/review-queue
GET   /api/v1/candidates/{candidate_fingerprint}
PATCH /api/v1/candidates/{candidate_fingerprint}/review
GET   /api/v1/candidates/{candidate_fingerprint}/review-history
```

### 9.4 列表参数

至少支持：

- `batch_id`；
- `job_profile_id`；
- `match_result`；
- `min_score` / `max_score`；
- `review_status`；
- `reviewer_id`；
- `communication_status`；
- `has_share_link`；
- `keyword`；
- `page` / `page_size`；
- `sort_by` / `sort_order`。

### 9.5 并发冲突

更新接口必须携带 `revision`。如果数据库版本已经变化，返回 HTTP `409 Conflict`，前端提示用户刷新后重新提交，不允许静默覆盖。

## 12. 安全与隐私

1. 生产环境必须 HTTPS；
2. 登录状态使用安全的 `HttpOnly` Cookie，避免把长期令牌存入 `localStorage`；
3. 必须有 CSRF 防护、登录失败限制和会话过期；
4. API 按角色和岗位鉴权；
5. 完整简历、手机号及正式链接不得写入普通应用日志；
6. 数据库使用独立最小权限账号；
7. 所有查看、导出和修改敏感数据的操作可审计；
8. 正式分享链接只对已登录且有岗位权限的用户返回；
9. 错误信息不得泄露数据库凭据、Coze token 或飞书 webhook；
10. 生产环境关闭或保护 FastAPI OpenAPI 文档入口。

## 13. 非功能需求

- 默认分页每页 20 条，最大 100 条；
- 在 10,000 名候选人规模内，常用列表查询 P95 小于 1 秒；
- 审核提交 P95 小于 1 秒；
- 支持至少 50 名内部用户并发浏览；
- 列表、详情和提交失败必须有明确错误提示；
- 页面适配常见桌面分辨率，第一阶段不要求完整移动端；
- 所有时间使用数据库本地时间存储，API 返回明确时区；
- 关键查询需要索引和执行计划验证；
- 数据库迁移必须支持升级和可验证的回滚方案。

## 15. 验收标准

1. HR 可以登录并只能看到有权访问的岗位；
2. 默认队列准确展示全部 `relevant` 和 `needs_review>=90`；
3. 候选人详情展示正式链接、简历、AI 结论、证据、搜索来源和沟通状态；
4. HR 可以提交所有约定状态和必填反馈；
5. 提交后当前状态和审计历史在同一事务中完成；
6. 提交不改变 AI 三态、分数、证据和分析版本；
7. 两人并发修改时后提交者收到冲突提示；
8. 已人工处置候选人不会再被自动重复沟通；
9. 指标卡和日报预览在规定时间内更新；
10. 已结束候选人从待审核移除，但保留累计进度和历史；
11. 不启动第二个手机实例，不触碰采集 checkpoint；
12. 不发送任何日报；
13. 后端、前端和主项目回归测试全部通过。

1. 第一阶段登录方式：本地账号还是企业 SSO（默认本地账号，预留 SSO）；
2. 是否需要候选人分配给具体 HR（默认第二阶段实现）；

5. “建议沟通”后由 HR 手工联系还是系统后续自动联系（默认 HR 手工推进，自动化保持抑制）；
6. 部署位置：当前 Windows 主机、内部服务器或云服务器（默认内部服务器，RPA 与 Web 服务解耦）。

## 18. 项目约束

- 唯一业务真值仍为 MySQL；
- 唯一采集代码源仍为主项目最新代码；
- 不得从旧会话、旧工作树复制过时代码覆盖主项目；
- 新工作树开发前必须确认基线包含最新 P1/P2 规则、人工审核字段、报表 90 分口径和双岗位主备 Coze 路由；
- 当前主目录存在未提交维护改动时，不能直接从旧 `HEAD` 创建工作树并假设其包含最新状态；
- 实现期间不得启动或续跑采集进程，不得调用 `--no-resume` 或 `--reset-checkpoint`，不得发送或测试日报。

## 19. 工程与代码编写规范

本章属于验收要求，不是建议项。实现者必须以可维护性、清晰边界和可测试性为优先，不得为了快速完成页面而把所有逻辑堆叠在 API、单个 Service 或单个 React 组件中。

### 19.1 总体原则

1. 代码应直接表达业务意图，优先选择简单、明确、可测试的实现；
2. 模块依赖必须单向，禁止循环依赖和跨层调用；
3. 一个函数只处理一个层次的问题，一个模块只承担一类职责；
4. 业务规则必须有唯一实现位置，API、SQL、前端和日报不得各复制一份状态判断；
5. 新代码必须有完整类型标注，禁止用大面积 `Any` 绕过类型系统；
6. 名称使用准确的英文业务术语，注释和面向维护者的说明使用中文；
7. 优先复用项目已有的决策模块、报表规则和数据库能力，不得另建互相矛盾的平行实现；
8. 不为假设中的未来场景提前设计抽象；只有出现明确变化轴或第二个真实实现时才提取通用接口；
9. 不写无业务价值的“兼容一切”代码，不通过静默降级掩盖错误数据；
10. 安全、权限、事务、并发和外部输入校验不属于过度防御，必须完整实现。

### 19.2 后端分层

后端至少划分以下层次：

```text
API / Router
    ↓
Application Service / Use Case
    ↓
Repository / Persistence
    ↓
MySQL

Domain Policy / Shared Rules
    ↑ 由 Service 调用，不依赖 FastAPI、SQLAlchemy 或 MySQL
```

#### API / Router 层

职责：

- 路由和 HTTP 方法；
- 认证用户和权限依赖；
- Path、Query、Header 和 Body 参数解析；
- Pydantic 请求/响应模型；
- 将业务异常转换为明确的 HTTP 状态码；
- 调用一个清晰的 Service 用例。

禁止：

- 在 Router 中直接写 SQL 或获取 SQLAlchemy Engine/Session；
- 在 Router 中编写审核状态转换、报表口径或权限策略；
- 在 Router 中开启多段事务或拼装复杂候选人数据；
- 返回未经响应模型约束的数据库行；
- 用一个数百行接口同时完成查询、更新、审计和报表计算。

#### Application Service / Use Case 层

职责：

- 编排一个完整业务用例；
- 调用领域规则和 Repository；
- 管理事务边界；
- 校验状态转换和乐观锁版本；
- 保证“更新当前状态 + 写审核事件”原子完成；
- 返回与 Web 框架无关的领域结果或 DTO。

禁止：

- 依赖 FastAPI 的 `Request`、`Response`、`HTTPException`；
- 依赖 React、Cookie 表现形式或具体页面字段；
- 拼接 HTML 或飞书卡片；
- 把所有功能集中到一个 `ReviewService` 巨型类中；
- 捕获所有异常后统一返回成功、空列表或 `None`。

Service 按用例拆分，例如：

```text
ListReviewQueue
GetCandidateDetail
SubmitCandidateReview
GetReviewHistory
GetDashboardSummary
BuildLiveReportPreview
```

#### Repository / Persistence 层

职责：

- SQLAlchemy 查询和持久化；
- 数据库行与持久化 DTO 的转换；
- 分页、排序、锁和索引友好的过滤；
- 在 Service 提供的事务中完成读写；
- 隔离 MySQL、SQLAlchemy 和表结构细节。

禁止：

- 在 Repository 中判断 `relevant + needs_review>=90` 等产品规则；
- 在 Repository 中决定哪些角色有权限；
- 在 Repository 中发送日报、调用 Coze 或操作手机；
- 返回一个供上层随意读取任意字段的超大字典；
- 为了“通用”暴露任意表名、任意排序字段或任意 SQL 条件。

复杂 SQL 应放在有明确业务名称的 Repository 方法中，并用中文注释解释查询目的、去重口径和关键窗口函数，不能只把一整段 SQL 塞进 Router。

#### Domain Policy / Shared Rules

职责：

- HR 状态定义和允许的状态转换；
- 自动沟通抑制规则；
- AI 可行动候选人口径；
- 报表选择规则；
- 与框架无关的纯函数。

领域规则不得依赖 FastAPI、SQLAlchemy、文件系统、环境变量或网络。相同规则必须由 API、日报和测试共同引用。

### 19.3 事务与数据一致性

1. “读取当前 revision、校验状态、更新快照、写入事件”必须处于同一数据库事务；
2. 事务由 Service/Unit of Work 控制，Repository 不得各自偷偷提交；
3. Repository 方法禁止内部无条件创建新连接，导致同一用例跨多个事务；
4. 并发冲突必须明确返回领域冲突，由 API 映射为 HTTP `409`；
5. 事务失败必须整体回滚，不允许出现主表已更新但事件表未写入；
6. 只读查询不得产生隐式写入或自动迁移；
7. 数据库 migration 与应用启动分离，生产启动不得擅自执行不可审计的 DDL。

### 19.4 输入校验与“不过度防御”

系统只在明确边界进行必要校验：

- HTTP 请求；
- 登录与权限；
- 数据库读取到的历史兼容数据；
- 外部链接和文件；
- 环境变量与启动配置。

边界校验完成后，内部函数应依赖类型和明确不变量，不得层层重复验证同一个值。

禁止的防御性写法：

- `except Exception: pass`；
- 捕获所有异常后返回空列表、零或成功；
- 对必填字段连续使用 `getattr`、`dict.get` 和多层默认值；
- 未知状态自动当作“待审核”并继续写库；
- 数据结构错误时静默跳过候选人；
- 为理论上不会出现的十几种输入类型编写冗长兼容分支；
- 同一个业务条件在多个层次反复判断；
- 通过 `# type: ignore` 大面积压制真实类型问题。

推荐做法：

- 在边界使用 Pydantic/Zod 一次性验证；
- 非法业务状态立即抛出有名称的领域异常；
- 数据不变量被破坏时快速失败并记录不含 PII 的结构化日志；
- 只捕获能够处理的具体异常；
- 失败响应说明用户下一步应该怎么做。

### 19.5 代码规模和复杂度

以下为审查阈值，不是机械指标；超过时必须说明为什么不能合理拆分：

- 普通函数建议不超过 50 行；超过 80 行必须拆分或在 review 中给出充分理由；
- FastAPI Router 函数建议不超过 30 行；
- 单个 Service 用例建议不超过 150 行；
- 单个 Python 业务模块建议不超过 500 行；
- 单个 React 页面组件建议不超过 250 行；
- 单个可复用 React 组件建议不超过 150 行；
- JSX 嵌套超过 4 层或出现多个独立区域时，应提取语义组件；
- 圈复杂度高、布尔条件超过三个维度或嵌套超过三层时，应提取命名良好的规则函数。

禁止创建 `utils.py`、`helpers.py` 等无边界杂物模块。通用代码应按实际职责命名，例如 `review_status_policy.py`、`candidate_query.py`、`report_preview_mapper.py`。

### 19.6 中文注释与文档

必须添加中文注释的场景：

- 关键业务口径及其原因；
- 身份去重、批次窗口和报表统计边界；
- 复杂 SQL、窗口函数和性能取舍；
- 乐观锁和事务不变量；
- 安全限制、人工抑制沟通等不可见副作用；
- 看起来可以简化但实际上不能修改的兼容逻辑。

不应添加的注释：

- 逐行翻译代码；
- 重复函数名已经表达的内容；
- 过期 TODO；
- 没有原因说明的“临时处理”；
- 大段注释掉的旧代码。

公共 API、Service 用例、Repository 接口和领域规则应有简短中文 docstring，说明职责、输入输出和关键不变量。注释重点解释“为什么”，代码本身解释“做什么”。

### 19.7 Python 代码质量

1. 使用 Python 3.12 类型语法和完整返回类型；
2. Pydantic 模型区分 API 请求、API 响应和内部 DTO，不复用数据库模型直接对外输出；
3. 使用有意义的领域异常，例如 `ReviewConflictError`、`InvalidReviewTransitionError`、`CandidateNotFoundError`；
4. 禁止用布尔参数堆叠产生难以理解的调用；超过两个行为布尔参数时改用明确对象或枚举；
5. 时间必须显式处理时区，禁止混用无时区时间和有时区时间；
6. 日志使用结构化事件名，不记录完整简历、正式链接、手机号或反馈原文；
7. 测试代码也要遵守清晰分层，不用超大 fixture 掩盖业务意图；
8. 引入 Ruff 进行 lint/format，并使用 mypy 或 Pyright 做静态类型检查；
9. 不为通过测试在生产代码中增加测试专用分支。

### 19.8 前端架构规范

前端采用按业务功能组织的结构，避免把整个工作台放进一个页面文件：

```text
src/
  app/                 应用启动、路由、全局 Provider
  features/
    auth/              登录和会话
    review-queue/      审核队列
    candidate-detail/  候选人详情
    review-submit/     审核提交
    dashboard/         指标卡
    report-preview/    日报预览
  shared/
    api/               统一 HTTP Client 和生成的 API 类型
    components/        无业务状态的通用组件
    hooks/             真正跨功能复用的 Hook
    types/             少量共享类型
```

职责划分：

- Page 只负责路由级布局和组合功能组件；
- Feature 组件负责一个完整用户操作；
- 展示组件只接收明确 props，不直接请求 API；
- API Client 只处理 HTTP、鉴权续期和统一错误结构；
- TanStack Query 管理服务端状态、缓存、刷新和 mutation；
- React Hook Form + Zod 管理表单状态和边界校验；
- URL Query 参数保存可分享的筛选、页码和排序条件；
- 短暂 UI 状态使用组件本地 state，不把所有状态放入全局 store。

禁止：

- 在组件中散落裸 `fetch`；
- 同一服务端数据同时保存到 TanStack Query、Context 和本地 state；
- 使用一个巨大 Context 管理整个应用；
- 把后端 snake_case 数据在每个组件里重复转换；
- 在 JSX 中嵌入复杂权限、状态转换或统计表达式；
- 用数组下标作为候选人列表 key；
- 用 `any`、非空断言和可选链掩盖不完整 API 契约；
- 为简单页面引入不必要的全局状态库。

### 19.9 前端交互与视觉一致性

1. Ant Design 通过统一 Theme Token 控制颜色、间距、圆角和状态色，禁止页面内随意写相近但不一致的颜色；
2. 所有列表必须有加载、空数据、错误、无权限和刷新状态；
3. mutation 期间防止重复提交，成功后只失效相关 Query Key；
4. `409` 冲突必须展示“数据已被其他人修改”，并提供重新加载入口；
5. 危险或结束状态需要二次确认，但普通推进不弹出多余确认；
6. 表单错误显示在对应字段附近，不只显示全局 Toast；
7. 键盘焦点、表单标签、颜色对比和抽屉关闭行为满足基本可访问性；
8. 正式链接使用明确按钮打开，不在表格中显示完整 URL；
9. 完整简历使用可阅读的分段和固定最大宽度，不展示成超长单行文本；
10. 页面不得展示数据库 ID、内部堆栈、环境变量或敏感配置。

### 19.10 API 契约规范

1. API 使用统一 `/api/v1` 前缀；
2. 请求和响应必须有 Pydantic Schema，并进入 OpenAPI；
3. 前端类型从 OpenAPI 生成或由唯一契约文件产生，不手写一套容易漂移的重复类型；
4. 错误响应至少包含稳定错误码、用户可读信息和可选字段错误详情；
5. 分页响应统一包含 `items`、`page`、`page_size`、`total`；
6. 排序字段使用后端白名单，不把前端字段直接拼入 SQL；
7. 时间使用 ISO 8601 并携带时区；
8. PATCH 只接收允许修改的人工字段，AI 字段不得出现在写入 Schema；
9. API 变更必须同步更新契约测试和前端生成类型。

### 19.11 测试代码规范

1. 单元测试优先验证领域规则和 Service 用例，不通过 HTTP 才能测试的逻辑应尽量少；
2. Repository 使用独立测试数据库验证真实 SQL、事务、分页和并发；
3. API 测试关注状态码、鉴权、Schema 和异常映射；
4. 前端组件测试关注用户可见行为，不测试内部 state 或实现细节；
5. Playwright 只覆盖关键主路径，不重复所有单元测试；
6. 测试名称应使用可读英文描述业务行为，必要处用中文注释说明特殊样本；
7. 每个缺陷修复必须先补能复现缺陷的回归测试；
8. 禁止依赖测试执行顺序、真实 Coze、真实飞书、真实手机或生产数据库。

### 19.12 Review 检查清单

提交合并前必须逐项检查：

- Router 是否直接访问数据库；
- Service 是否依赖 FastAPI 或 HTTP 类型；
- Repository 是否包含产品决策；
- 是否存在重复实现的可行动候选人口径；
- 是否覆盖或间接修改 AI 历史事实；
- 状态快照与审计事件是否同事务；
- 是否正确处理 revision 冲突；
- 是否存在宽泛异常捕获和静默降级；
- 是否出现过长函数、巨型模块或巨型 React 组件；
- 中文注释是否解释了关键原因和不变量；
- API 类型是否与前端契约一致；
- 是否泄露简历、链接、手机号或密钥；
- 是否补齐成功、失败、无权限和并发测试；
- 是否在未授权情况下触碰手机采集、Coze、飞书或生产数据。
