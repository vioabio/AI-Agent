# 道馆资料查询重复回复修复

## 原因

此前`GymQuestionPolicy.clarification()`将“提到道馆、但当前问题没有成员等级”一律视为需要补充玩家队伍，直接发布固定的“先确认你的冒险进度”文本并结束Run。模型没有参与这段回答的生成，因此不是模型API未配置、网络超时或答案缓存导致。

这项检查适用于针对玩家队伍制定方案，却错误拦截了只读资料问题：

- “我想了解下朱紫中朱版本的几个道馆馆主的队伍情况”
- “目标馆主有哪些啊”

## 修复

新增`GymCatalogAnswer`，在玩家条件校验之前识别只读馆主资料请求；读取现有初战/视察重赛快照并验证SHA-256，不编造玩家队伍或调用模型补写资料。

| 问法 | 现在的行为 |
| --- | --- |
| 目标馆主有哪些 | 展示八位馆主、擅长属性及单双打模式的简洁名单 |
| 馆主的队伍情况 | 展示阵容、等级和王牌太晶属性 |
| 查询奇树初战队伍与招式／那奇树呢 | 展示奇树单馆详情、特性及招式 |
| 未通关，但想看看阿枫重赛阵容 | 可以查阅资料，同时说明查阅不代表已解锁对战 |
| 帮我配个队伍挑战阿枫／计算伤害 | 继续走实际队伍、进度与计算条件校验 |

未指定阶段时明确先展示初战，不混合初战与重赛。资料展示与名单展示不是同一个模板；不同馆主也会读取各自的数据。需要针对玩家配置生成打法时，原有条件校验仍保留。

## 验证

- 整体后端回归1446项，0失败、0错误、3项跳过：`artifacts/gym-catalog-query-all-final.log`。
- 随后补充简短馆主追问等边界，最终构建的相关定向测试54项通过：`artifacts/gym-catalog-query-final-package.log`。
- 对打包应用进行同一会话、连续五次真实HTTP请求验证：阵容概览→馆主名单→奇树详情→未解锁时查重赛资料→定制配队补充条件。五次均通过，前两次内容不同：`artifacts/gym-catalog-query-http.json`。
- 查询路径的代理集成测试断言不调用模型生成接口，同时验证流式片段与最终答案一致。这是资料查询/路由回归，不冒称新的自由问答模型质量验收。
- 本轮运行使用本机JBR，编译目标Java 21。前端没有修改；本地服务切换至`vio-ai-agent-gym-query.jar`，保留原账号与数据存储配置。
