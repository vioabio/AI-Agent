# 配招逐项核对与草稿检查

本批在学习途径和第二来源机制之后，将已有资料用于单个成员的培养配置检查。队伍编辑区新增“检查当前配招”，Agent新增受治理只读工具；检查原配置的缺项、数值/重复招式、特性候选和逐招朱紫学习记录。草稿仍可保存，检查不替用户补填或修改队伍。

## 检查内容与边界

| 检查 | 当前行为 |
| --- | --- |
| 四个招式槽位 | 少于四招显示缺项；超过四招、重复招式返回输入问题 |
| 特性 | 与该成员本次Pokemon快照候选比较；名称未解析、未填写和不在候选中分别显示 |
| 招式 | 每个已填招式读取朱紫版本组的实际学习记录，并与同一成员快照关联 |
| 培养字段 | 检查等级、性格、EV/IV范围和EV总和；记录未提供的字段，不以构造器默认值补齐请求 |
| 参考失败 | 单行失败保留其他已核对行，整体不能显示全部匹配；快照未记录不等于不能学习 |
| 组合与策略 | 未验证四招共同可得、遗传/进化/回忆操作、学习等级相容、特性招式组合、道具性格效果或正式赛制合法性 |

`REFERENCE_MATCHED`只表示已填特性和每招参考逐项匹配且必填字段齐备，界面明确显示“组合仍待审核”。空道具字段与字段未提供分开处理；空字符串只表示保存了空字段，不能证明用户有意不携带。既有表单、存储默认值仍保留，提示其不等于用户明确选择。

来源沿用公开PokéAPI Pokemon/species快照，未把上一批固定Showdown机制文本当作配招联合合法性引擎。中文名称尚未接入统一别名解析，招式和特性需使用英文名或slug；未解析时明确说明，不凭模型猜配。

## 实际实现

`BuildCheckFacts`定义可空原输入、逐行状态、来源锚点和有界报告。`LocalBuildCheckService`先检查已填字段，再读取真实成员和学习记录；成员ID、Pokemon/species组合摘要、特性候选及每行学习快照相互核对。报告摘要覆盖原请求、缺项、来源和结果，回答校验器再与本次实际工具参数逐项比较，拒绝错成员、错配置或被改写的结论。摘要用于内容关联，不是签名或外部数据真实性认证。

```text
POST /api/pokemon/reference/build-check
checkPokemonBuild(request)
```

HTTP严格检查原始JSON类型，拒绝数字字符串、未知字段和未知版本。工具走原治理网关、角色、Run所有者与版本检查；仅本地参考启用时注册，评测只在READ_ONLY_TOOLS开放。原入参证据新增有界request字段，实际完成事件带`build-check-output-evidence-v1`，关联工具版本、参数、成员和报告摘要。取消会在下一次读取前停止。

明确中文“检查/核对配招”请求保留原输入提示，绕过旧单只介绍的提前结束。回答只展示本次核验结果及来源，替换模型自行宣布“全部合法”或“已保存”的说明；失败时显示未取得绑定结果，不用自由生成内容补证据。当前重点为单成员检查；整队逐成员汇总、混合意图和其他语言仍待扩大覆盖，不声称所有规划稳定成功。

前端`BuildCheckPanel`使用当前表单构造请求，检查不发起保存。每次配置变化清除结果并取消旧请求，序号和完整请求身份共同防止迟到响应覆盖新配置；卸载也取消。结果在有界区域展示状态、缺项和逐招来源，不显示原始JSON、UUID或长摘要。桌面及手机适配沿用统一工作区。

原`TeamBuild`、`TeamWorkflowService`、参考仓储、PokeApiClient、伤害引擎与桥接文件保持既有身份；保存审批、并发冲突、恢复门禁不变。HTTP检查为只读公开参考，不需要保存队伍或模型API Key；Agent解释仍依赖配置的真实模型。

## 使用方式与下一步

1. 打开“队伍配置”，选择成员，填写招式、特性及培养字段，点击“检查当前配招”。
2. 按缺项或不一致提示调整，再次检查；本次快照未记录的内容先查可靠来源，不直接断言无法学习。
3. 确认希望保留配置后，使用已有“保存队伍”操作。检查结果不代替保存或Agent修改确认。

对话中可说“请检查杰尼龟的配招”，同时给出真实成员编号、原配置及当前资料/游戏版本；不提供的字段保留缺项。仅说“检查当前配招”但没有可读的保存队伍或明确配置时，仍需先取得原配置。

下一批先补可定位的学习操作与组合约束资料，再做四招/特性/等级联合核对和整队汇总；随后完成人工机制、相关性与策略审核，扩充正式题集并执行独立保留集对照。S2/S3及S5整体仍未验收，正式36题不因本批三条新编写功能题而增加。
