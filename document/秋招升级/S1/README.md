# S1：本地队伍修改闭环

日期：2026-10-23。范围：在现有本地账号、Run 和 HITL 审批上，实现已保存队伍培养配置的读取、追问、查询/计算、修改预览、确认保存与回读。模型建议是否合理仍按 S2 评测，不因为保存成功而视为正确。

## 怎么使用

1. 重启后端和前端，在本地账号中创建并保存队伍；使用与队伍一致的规则和资料版本。
2. 在“我的队伍”点击“让 AI 分析”，助手会先读取账号下的保存配置。点击“AI 修改预览”会把调整问题放入输入框，可补充具体目标再发送。
3. 例如：“请读取队伍编号 1，只把第 1 位成员的等级改为 51，其他配置保留，先生成预览。”编号以自己实际保存的队伍为准。
4. 需要伤害依据时，说明双方、招式、等级、配置和场地条件；助手调用真实计算后才能为明确要求计算的任务生成预览。缺条件时先补充条件。
5. 阅读预览中的成员、修改前后差异、策略理由和计算条件，再点击“确认保存”或“取消修改”。聊天中说“已确认”不具备批准权限。
6. 成功后由程序展示保存回执；列表自动刷新。正在编辑同一支已保存且未改动的队伍时同步配置；有未保存草稿时保留草稿，不静默覆盖。

默认仅在 `local` 且非 `prod/demo`、`vio.run.durable-resume=false`、`vio.agent.v1.enabled=false` 时注册本阶段工具。SQLite、本机 Node 与现有模型配置即可运行，无需服务器。使用 DeepSeek 时沿用主 README 的 `local,deepseek` 配置，不需要将 Key 发到聊天中。

## 具体实现

| 能力 | 实现与约束 |
|---|---|
| 选择队伍 | `listCurrentTeams` 只列出当前主体队伍；未明确队伍/目标时提示模型追问 |
| 读取配置 | `readCurrentTeam` 从认证后的 ToolExecutionContext 获取 owner，读取队伍快照、修订号、全部成员事实和缺少的条件；模型不能传 owner |
| 查询与计算 | 复用图鉴、整队参考和本地伤害引擎；只从实际计算工具响应生成预览中的计算摘要，不接受模型声称“已计算” |
| 生成预览 | `previewTeamChanges` 仅创建服务端候选，不更新队伍；按槽位修改培养字段，未传字段保留，范围/EV/IV/招式重复等由 TeamBuild 校验 |
| 固定确认内容 | owner、Run、teamId、原始队伍/修订号、候选配置、理由共同计算摘要；审批 ID 也是本次确认的幂等身份，同一 Run 不允许替换预览 |
| 用户确认 | 复用 HitlManager、既有审批处理器和 WAITING_APPROVAL；训练家仅通过绑定自己 Run/预览的专用接口确认；通用 `/hitl/**` 仍禁止访问 |
| 保存与回读 | 恢复后的 DefaultRunExecutor 优先应用已确认候选，不再让模型重新决定修改；SQLite 条件更新返回实际保存行 |
| 并发保护 | SQLite 每次普通编辑也递增 revision，确认按 owner/id/revision 原子比较更新；即使配置改动后恢复原样，旧预览仍失效 |
| 取消与超时 | 新增受控 RunMutationBoundary，只有活跃 worker 能进入写入；SQLite 提交前再次检查，失去资格时回滚。独立构造的普通 AgentRunContext 默认禁止写入 |
| 失败与重试 | 过期、拒绝、取消和并发冲突不应用变更；不确定保存结果不自动重放，提示回读核对。重复回执不再次递增修订 |

预览理由仍属于模型提出的策略建议，展示前沿用 S0.1 的有限机制检查；不能代替语义事实核验。计算摘要明确保留实际输入，原配置的计算不能冒充修改后配置的改善证明。

新增本地接口：`GET /api/chat/runs/{runId}/team-change` 返回预览/结果，`POST /api/chat/runs/{runId}/team-change/decision` 处理确认。后者只接受匹配本次服务端预览的审批 ID，内部复用原有审批绑定、过期判断和恢复处理；不能批准其他工具。不改变本地账号对通用 `/hitl/**` 的禁止访问。未知或其他账号资源统一404，重复审批409，预览过期410。根 `/api/teams/**` 同时补齐了领域不存在→404、配置冲突→409、参数错误→400，避免落入通用500。

伤害场地参数中的 `weather/terrain` 改为可选；明确表示“无”的空字符串、`none`、`无` 规范为 null，未知条件继续拒绝。工具 schema 与实际可空输入保持一致，避免模型因 null 被误判为缺少必需参数而反复重试。

## 存储和恢复边界

- 已有 SQLite `local_team` 自动添加 `revision` 列，保留原有 payload 与用户队伍，不要求重建数据库。
- 待确认候选和回执放在有容量/保留期限限制的进程内存；真正的审批决定仍由现有 HITL 管理。保存配置继续进入原有本地数据库。
- 当前交付只修改现有成员的招式、特性、道具、性格、等级、EV/IV；不自动增加/删除成员、不替换物种、不更改版本和归属。
- 不支持跨重启恢复候选，不自动重放保存；进程重启后应重新读取并预览。PostgreSQL、多实例生产写入与版本化知识门面的接线不在本次启用范围。
- 任务期限继续受现有 Run deadline 约束；待确认不是无限等待。过期后需要新建任务，不能批准旧预览绕过期限。
- 未提供对手/招式等条件时的追问仍涉及模型行为，不能保证所有自然语言问法都正确识别；S2 需要进一步统计真实追问和任务完成率。

# 独立本地服务启动并准备好图鉴后；选择新的输出目录，禁止覆盖原证据
