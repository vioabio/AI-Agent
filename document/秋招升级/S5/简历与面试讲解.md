- 实现工具治理及结果证据约束，校验账号归属、版本与实际参数；队伍修改采用预览、用户确认、保存回读与冲突检查，区分任务失败和保存成功。
- 建立真实任务采集和分层回归，记录工具事件、历史、模型用量和失败原因；对明确未填写草稿收紧工具范围并保留成员顺序与空字段，三条固定开发回答在受约束图鉴协议下3/3通过，并获用户总体确认。

最后一条必须补充口径：只有三条开发样本、单轮结果，原三工具协议1/3；不是全量准确率。随后源码又有混合意图修复，历史模型记录适用于所绑定版本，不能直接当当前版本现场成绩。正式题集36题的全量质量/保留集验收仍未完成。

## 60秒项目介绍

“我做的是一个本地运行的宝可梦领域智能体，重点是让工具调用和任务结果可核对。模型负责理解问题与选择工具，Java层负责权限、版本、预算、确定性计算和结果绑定。队伍修改要先出预览，由用户确认后保存并回读。开发中我保留了模型重排成员、缺失字段和误读保存队伍的真实失败，分别用约束、工具范围和展示校验修复，再按原题重测。工程检查和人工评价分别记录，样本不足的地方不会写成整体准确率。”

## 三个可追问的失败复盘

1. **按原顺序核对却被重排。** 自然语言给6→2→4，早期模型自行排序。加强明确顺序提示与展示绑定，原参数仍由模型生成；不能因最后答案完整而忽略中间错误调用。
2. **未填写字段被省略。** 展示层可能理解为缺项，但严格原参数和报告绑定未通过。对有限明确草稿要求显式null，并校验实际输入；不静默代填来刷通过率。
3. **草稿任务先列保存队伍。** 收紧明确草稿的模型工具范围；进一步发现混合“对比旧队伍/推荐配置”不应套用纯草稿限制，新增回归并收窄识别。

以上对应S3原始基线、顺序重测和字段修复记录，以及S2混合意图回归；失败不删除。不要把提示约束、程序展示和模型自主能力混算。

## 面试问答提纲

| 追问 | 应讲清的证据与取舍 |
| --- | --- |
| 为什么需要工具网关？ | 模型可选择不代表有权限执行；原参数、版本、超时、审计与结果状态统一管理 |
| 如何避免幻觉？ | 事实尽量使用结构化工具和原文来源；对支持范围保持有限，不声称完全消除幻觉 |
| 检索为什么不用向量就够？ | 当前本地主链使用SQLite/BM25与主题筛选；向量相关代码存在不等于当前启用或质量通过 |
| 为什么用户确认后还可能保存失败？ | 预览到确认之间可能有并发修改；必须再校验而不能覆盖 |
| 如何验证质量？ | 确定性测试、固定模型集成、浏览器和真实模型采集分层；用户总体确认不伪造逐项评语 |
| 记忆和历史是什么关系？ | 历史持久化、预算内回填和用户显式偏好快照分别说明；不说具备无限长期记忆 |
| 成本与恢复有哪些边界？ | 实际usage与代理估算、参考费用与账单分开；不承诺任意副作用步骤自动重放 |

## 需要诚实说明的协作方式
