> 审查日期：2026-10-22。面向 Java AI 应用开发、智能体应用开发岗位。
> 初始审查基线：`b1555e1`（宝可梦智能体1.0版本）。2026-10-23 已完成 [S0 基线](秋招升级/S0/README.md)、[S0.1 证据约束](秋招升级/S01/README.md)，实现 [S1 本地队伍修改闭环](秋招升级/S1/README.md) 和 [S2 第一批评测工具与种子集](秋招升级/S2/README.md)；[S3](秋招升级/S3/README.md)已接通持久检索和来源登记，[S4](秋招升级/S4/README.md)已接通首批真实用量观测。原始错误记录保留，S2～S4整体验收及S5继续推进；目标值均不是现有成绩。

## 1. 项目定位与升级目标

建议对外名称：**基于 Spring AI 的宝可梦知识问答与队伍分析智能体**。

项目围绕图鉴查询、培养配置、队伍分析和伤害计算展开，重点展示模型如何调用真实工具、使用证据、处理异常并完成任务。当前已经可以作为秋招项目投递；升级目标是增强真实任务闭环和效果证据，使项目能经受技术面试追问。

最终需要交付四类内容：

1. 一条稳定演示的队伍分析任务，从读取配置到确认后保存修改。
2. 一条可引用、可评测的知识检索链路。
3. 可复现的效果、延迟、Token 与成本对比报告。
4. 与实际实现一致的 README、架构图、演示脚本和技术复盘。

不以模块数量、代码行数或单元测试数量作为智能体效果的替代指标。多智能体、微调、多模态和自研协议栈不列为本轮必做项。

## 5. S1：打通队伍分析业务闭环

实施记录：[本地闭环使用、设计与范围](秋招升级/S1/README.md)、[实际验证](秋招升级/S1/验证记录_2026-10-23.md)。当前只修改现有成员的培养配置；语义判断和更广泛的追问/异常覆盖继续纳入 S2，不扩展自动重放范围。

### 目标任务

“检查我的队伍配置，分析需要补齐的部分，对关键对局进行计算，给出修改建议；我确认后再保存。”

建议流程：

```text
读取当前账号的指定队伍
  → 校验版本、成员和培养配置
  → 缺条件时追问
  → 查询图鉴/攻略
  → 对选定对局调用伤害计算
  → 输出建议、证据与假设
  → 展示结构化变更预览
  → 用户确认
  → 校验最新队伍状态并保存
  → 回读结果，展示完成情况
```

### 后端工作

1. 增加当前账号队伍的只读工具；归属来自认证上下文，不接受模型指定其他用户。
2. 将队伍配置与问题上下文结构化传递，避免仅依赖拼接自然语言。
3. 约束计算工具必需条件。条件不足时追问或给出条件性分析，不补造配置。
4. 设计变更预览与确认对象。工具名可暂拟为 `readCurrentTeam`、`previewTeamChanges`、`confirmTeamChanges`，实际名称在实现时冻结。
5. 确认对象至少关联 owner、teamId、原始配置摘要或修订号、变更集合、有效期和幂等键。
6. 保存时重新校验归属、配置边界和当前修订；旧预览、重复确认、队伍被修改等情况必须明确处理。
7. 接入现有审批/运行生命周期能力，避免新增一套互不关联的确认状态。

### 前端工作

- 在对话中展示阶段摘要与最终结果，原始工具过程保持可展开。
- 变更预览展示修改前后差异、理由、证据与计算条件。
- 提供“确认保存”“取消”，处理中防止重复提交。
- 保存成功后回读队伍并同步编辑区；失败时保留用户草稿和重试入口。

### 关键边界与测试

- [x] 未确认不写入队伍；确认后仅执行预览中的变更。
- [x] 账号 B 无法读取或确认账号 A 的队伍与预览。
- [x] 重复确认不会重复产生副作用。
- [x] 预览过期或队伍已变化时拒绝旧确认，要求重新分析。
- [x] 取消、超时与旧 worker 不会产生迟到写入。
- [x] 工具失败时说明哪些结论缺失；计算失败不能输出虚构的伤害数值。
- [ ] 正常、缺条件、查询失败、计算失败、确认冲突均有端到端用例。

S1 已有正常、缺条件和并发冲突的真实模型/HTTP 记录；2026-10-23 补充读取失败与计算失败的 Run/工作流/SQLite/事件/历史受控集成回归。该测试不使用真实模型/HTTP 故障，完整异常端到端矩阵仍需补齐，不将这项覆盖提前勾选。个别回答的术语/策略仍有错误，归入 S2 质量评测。

不要将这一阶段扩展成未经验证的任意工具自动重放；继续保留现有恢复策略的安全边界。

## 6. S2：真实评测与基线对比

第一批实施：[评测集及命令](../evaluation/campus/s2/README.md)、[标注规范](../evaluation/campus/s2/annotation.md)、[阶段验证](秋招升级/S2/验证记录_2026-10-23.md)。首版冻结 36 条来源关联种子题、20 组、14/22 切分；这不是 100 条独立真实用户样本，也未完成人工质量验收。实测已暴露通用攻略过度追问与引用外扩的问题，不能用必要工具调用通过代替答案正确。

后续已实施[来源与配置回答修复](秋招升级/S2/来源与配置回答修复_2026-10-23.md)：引用只展示实际检索原文，保存配置由程序展示并保护性格/数值字段。原错误答案继续保留；专项通过不等于 S2 全量准确率或人工验收已完成。

### 数据集建设

建议新建独立秋招评测目录，例如 `evaluation/campus/`，与已有 v1.0/v1.1 发布门禁分开。不能为了获得通过结果而下调原发布门禁。

首版建议 100 个真实问题：

| 类别 | 建议数量 | 主要判断方式 |
|---|---:|---|
| 图鉴事实 | 20 | 与明确版本和来源比对 |
| 攻略与引用 | 20 | 人工核对答案及引用支持关系 |
| 队伍多步骤任务 | 20 | 任务结果、必要工具和保存状态 |
| 伤害计算 | 15 | 与固定引擎及完整条件程序比对 |
| 追问、拒答与异常 | 15 | 是否正确追问、说明限制、避免编造 |
| 安全与账号隔离 | 10 | 非法操作应被阻止，验证无副作用 |
| 合计 | 100 | 样本量较小，报告必须注明适用范围 |

每个案例记录：caseId、任务类别、输入、前置队伍/资料、版本、期望结果、必要约束、标注依据、标注人和日期。允许多个合理方案，不能把某一句固定措辞当成唯一正确答案。

建议分层划分 40 个开发案例和 60 个保留测试案例；同一事实的高度相似问法按组划分，避免泄漏。真实资料、原始长文本和账号数据的使用范围也应记录清楚。

### 对比实验

在固定案例、模型、参数和版本下比较：

1. 纯模型问答：不提供额外资料与工具，作为问答质量基线。
2. 工具增强：当前真实资料与计算工具链。
3. 检索＋工具：S3 完成后使用同一测试集复测。

业务写入任务单独统计完成率。纯模型没有写入能力，不能将不同能力范围的任务混在一起声称统一“提升百分比”。

### 指标与建议验收目标

| 指标 | 定义 | 建议首版目标 |
|---|---|---|
| 任务成功率 | 完整满足任务约束的案例数 / 该类可执行案例数 | 简单任务 ≥80%，复杂任务报告实测结果 |
| 必要工具覆盖率 | 正确调用必需工具的案例数 / 需工具案例数 | 报告实际值及错误分类 |
| 引用正确率 | 真正支持关联结论的引用数 / 被评估引用数 | ≥90% |
| Recall@5 | 按固定标注定义计算的前五条相关证据召回率 | ≥85% |
| 安全案例通过率 | 正确阻止且未产生副作用的案例数 / 固定攻击案例数 | 该测试集 100%，不代表抵御所有攻击 |
| 耗时与成本 | 首字/总耗时、模型调用次数、Token、费用 | 记录 P50/P95 和真实计费来源，不预填成绩 |

以上数值是建议目标，不是已达到的结果。空答案、依赖失败和运行失败不得从分母中静默删除。LLM-as-Judge 可以辅助标注，不能替代数值计算、安全断言和人工引用核对。

- [x] 有案例级结果及失败原因，不只有汇总百分比；首批六类任务各重复两次，保留采集缺陷和回答质量问题。

## 7. S3：升级知识检索

第一批实施：[本地持久索引、接线和范围](秋招升级/S3/README.md)、[检索开发回归](../evaluation/campus/s3/README.md)。保留原4篇原创资料及S2冻结题集；当前接通SQLite倒排索引、BM25、稳定片段、原文定位和范围/有效期过滤，不宣称已经建立大规模语义知识库或完成S2保留集对比。

### 内容与来源

1. 扩充培养、配队、招式机制和计算解读资料，首轮可先覆盖 30～50 篇有来源的有效文档。
2. 每篇保存标题、来源、作者或发布方、获取时间、适用游戏/赛制、内容摘要与校验值。
3. 区分原创笔记、外部事实、比赛规则和带日期的环境分析；PokéAPI 数据不能替代赛事规则或实时强度榜单。
4. 先使用手动导入和可审查的文件，不把任意网页爬取作为必需项。

### 检索链路

解析与去重 → 按标题/段落切分 → 保存稳定 chunkId 与来源 → 建立关键词/向量索引 → 版本过滤 → 召回 → 融合排序 → 证据组织 → 回答与引用。

优先选择一个可复现方案：可以为现有检索抽象增加本地持久索引适配器，或在本机验证已有 PostgreSQL/pgvector 路径。选择方案时说明 embedding 模型、依赖和费用；DeepSeek 对话 Key 不代表自动具备 embedding 能力。

复用现有 `KnowledgeRetriever` 等抽象，避免建立两套无法评测对齐的问答链。重排模型在基线有证据说明需要后再引入，不作为第一步必做项。

### 验收标准

- [x] 至少一条完整的检索链在指定 profile 下真实运行；已验证local本地攻略工具→SQLite/BM25→原文引用，详见S3首批记录。
- [ ] 向量索引如有使用，可在重启后复用；模型/维度变更能被识别。
- [x] 引用能定位原文片段，且与答案结论对应；本批限实际原文节选，未开放自由生成结论的自动引用。
