## 依据与边界

本计划以 [`企业级智能体架构与技术对照报告.md`](../企业级智能体架构与技术对照报告.md) 为产品和技术依据，以当前仓库源码为事实基线。实现详情和逐项证据见 [M2-M7实施完成记录.md](./M2-M7实施完成记录.md)。文档中出现的“候选目标”“建议新增类”“SLO”仍需对应运行证据，不代表当前已经实现。

报告把能力分成三种状态：

- **当前主链**：用户真实请求已经经过，并有代码调用证据；
- **代码存在但未接入**：类、配置或测试存在，但没有进入正式请求链；
- **v1.0 目标**：本计划要求通过测试、运行和发布证据后才可宣称完成。

## v1.0 首发冻结项

首版只支持一个明确的数据与规则范围：朱/紫主版本、零之秘宝（具体篇章需选择）、`zh-CN` 正式输出，以及已审核的剧情/休闲单打、双打和一个 VGC 规则集。每个答案必须绑定 `game_release_id`、`battle_format_id`、`ruleset_version_id` 和 `data_release_id`。

首版必须可用的闭环是：

1. 图鉴和版本化事实查询；
2. 属性、伤害、速度线和队伍合法性确定性计算；
3. 带引用和版本过滤的攻略 RAG；
4. 受白名单约束的 Agent 工具调用；
5. 持久会话、队伍、反馈、纠错、评测、发布和回滚。

以下能力暂不进入主链：任意终端/文件写入、任意 URL 下载、实时天梯代打、混合世代无版本回答、完整多 Agent 平台、无明确需求的 Kafka/ES/Neo4j/Kubernetes。

## 执行规则

1. 先完成 M0 的可启动和安全门禁，再开始领域功能；任何红灯都不能被“功能已完成”覆盖。
2. 一次只推进一个里程碑；每个里程碑都要留下测试、截图、日志或评测报告。
3. Controller 只做认证、校验、路由和响应适配；业务编排、外部协议、数据访问和展示状态分别下沉到对应层。
4. 所有外部调用都要有超时、取消、有限重试、幂等边界和脱敏日志；高风险写操作默认需要人工审批。
5. 先在独立分支开发，完成验收后再合并；本轮已按请求落地 M2～M7 候选代码与文档，但没有替你创建分支、提交或推送。

## 最短执行路径

```text
M0 可启动/安全基线
  → M1 版本化主数据与确定性计算
  → M2 PGVector 混合 RAG 与引用
  → M3 唯一 Run/事件/持久会话/反馈闭环
  → M4 工具治理、评测与可观测
  → M5 前端场景化产品
  → M6 反馈、评测与可观测
  → M7 容器、恢复、发布与演示
```

开始编码前，请先填写 `_spec.md` 中的冻结表和 `_plan.md` 中的“待决策项”；完成后按手册的 M0 顺序执行。所有实际指标都写入日志和验收清单，不能直接把计划值写进 README 或简历。当前 M2～M7 仍是候选构建，严格 release 门禁和真实依赖验收未通过前，发布状态保持 BLOCKED。
