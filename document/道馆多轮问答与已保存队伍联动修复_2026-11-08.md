# 道馆多轮问答与已保存队伍联动修复

## 复现与原因

同一对话先询问阿枫阵容，再问通用应对，最后问“我当前的 test1 队伍能否应对这个馆主，该如何配置出招”。最后一句被馆主资料快捷路由错误匹配，未解析上文目标，返回了八位馆主总览；旧分析路径也未直接读取已保存队伍。此前通用回答另有“岩石属性抵抗虫招式”的机制错误。

## 修复后的流程

1. 在馆主资料路由之前识别已保存队伍应对请求，优先解析本轮明确指定的馆主，否则从当前账号当前对话的历史中解析唯一目标及初战／重赛阶段。
2. 调用受工具网关治理的 `listCurrentTeams`，按名称或编号选择当前账号的队伍；同名、未找到、目标不明确时只澄清对应缺口，不任意选队，也不退回馆主总览。
3. 调用只读 `analyzeSavedTeamForGym`，使用仓储快照中的成员、真实槽位、等级、特性、持物及招式。逐只检查当前攻击招式对馆主成员的属性覆盖，展示太晶前后差异，不从模型历史补造玩家配置。
4. 同一游戏下已保存队伍与会话资料版本不同时，本次只读自身配置与馆主相性，不跨版本读取种族值或计算伤害；不同游戏或不可查询资料仍拒绝。已有修改／保存流程的严格版本检查保持有效。
5. 通用应对追问使用本地已核验属性表，明确区分进攻克制与防守抗性，例如岩石招式克制虫，而虫招式打单岩石属性为 1 倍。

## 验证结果

- 后端全量离线 Maven 测试：1455 项，0 failures，0 errors，3 skipped。日志：本机 `artifacts/gym-followup-full.log`。
- 新增 9 项测试涵盖原始重复提问、执行器路由与输出、未知／歧义馆主、重赛继承、同名队伍、跨账号读取、不同游戏拒绝及通用相性纠错。
- 使用最终打包 Jar 在隔离端口进行真实 HTTP 连续三轮验证，按正常队伍 API 创建测试队伍，再通过 Run API 提问与读取事件。最后一轮包含 `listCurrentTeams`、`analyzeSavedTeamForGym` 执行记录，读取真实保存快照，未返回八馆主总览；前后队伍业务数据一致。
- HTTP 证据与运行脚本位于本机被忽略的 `artifacts/gym-saved-followup-http.json`、`artifacts/verify-saved-gym-followup.py`。使用独立测试队伍，没有替用户修改实际 test1。
- 本次链路由程序选择已核验资料和工具输出，不调用模型；上述测试不等同于通用模型自由回答质量验收。

## 实际使用与边界

在同一对话中依次询问“看下阿枫的队伍配置”“如何应对这个队伍”“你看下我当前的 test1 队伍能否应对这个馆主，该如何配置出招”。账号中必须确实保存名为 test1 的队伍；分析读取已保存配置，未保存的编辑不会自动代入。

当前结论是招式覆盖与等级差分析，不是完整多回合战斗模拟，不保证一击击倒或必胜。不擅自假定徽章数、捕获等级、服从条件、背包资源或重赛解锁；精确伤害仍须使用现有伤害工具并明确 NPC 未核验数值的假设。没有全地图获取数据时，不将未核验捕获成员拼成“当前可获得”的推荐队伍。
