# N7 供应链静态门禁实施记录

## 本次落地

本次只落地可在源码仓库内复查的静态门禁，不执行 Docker、registry、Trivy、Syft 或 Cosign：

- `tools/validate-docker-base-images.mjs`：按重复 `--file` 读取 Dockerfile/Compose，记录输入文件 SHA-256 和镜像来源/行号，拒绝动态插值、占位符和缺失 `@sha256:<64hex>`（启用 `--require-digest` 时）。
- `tools/validate-release-compose.mjs`：校验 release Compose 的重复输入文件、effective config、项目名、最终 image digest、`build` 禁止策略和 Secret 脱敏；报告不包含配置值。
- `tools/init-vulnerability-exceptions.mjs`：从 canonical `image-refs.json` 读取 backend/frontend 唯一 RepoDigest，生成空 `exceptions` 数组和扫描时间绑定的 `pending` 清单；不会把空数组解释为“无漏洞”。
- `tools/resolve-repo-digests.mjs`：离线解析两份 `docker image inspect` JSON，要求 backend/frontend 各恰好一个 immutable RepoDigest，并绑定 registry 前缀、Git SHA 和输入文件 hash；不调用 Docker/registry。
- `tools/create-provenance.mjs`：以 canonical image refs、lockfile/context hash 和双镜像 SBOM 生成逐镜像 provenance predicate；缺任一输入输出 `blocked`，不把 predicate 当作签名或 attestation。
- `tools/prepare-dependency-inventory.mjs`、`tools/validate-dependency-inventory.mjs`、`tools/finalize-dependency-inventory.mjs`：分别执行 N0 清单与发布 digest 的候选合并、结构/证据校验和现场证据回填；浮动 tag、缺失证据及未执行扫描保持 `environment-pending`。
- `tools/scan-dependency-images.mjs`：静态扫描适配器占位，按 inventory 为每个依赖生成明确的 `environment-pending` 记录；不会用空 `findings` 冒充干净扫描，也不会执行 Trivy/registry。
- `tools/aggregate-supply-chain-evidence.mjs`：只聚合输入文件的相对路径、SHA-256 和状态，并单独生成排除自身的 hash manifest；缺供应链现场证据时保持 pending。
- `contracts/vulnerability-exceptions-v1.1.schema.json`：为上述清单提供结构契约，实际扫描与例外审批仍由后续 validator 负责。
- `contracts/dependency-inventory-v1.1.schema.json`：约束依赖名称、版本/digest、来源、探针、网络边界和状态字段。
- `contracts/vulnerability-validation-v1.1.schema.json`：约束扫描/例外校验报告的 phase、状态、未解决计数和脱敏 finding。
- `tools/validate-vulnerability-exceptions.mjs`：离线读取 Trivy/vendor JSON，按精确 CVE + 精确 image digest + 未过期审批计算未解决 HIGH/CRITICAL；缺报告、digest 不可绑定或审批失效均非零。
- `tools/n7-supply-chain.test.mjs`：覆盖 mutable tag、digest、逗号参数、Compose build/Secret、缺失输入、no-clobber 等负/正例。
- `tools/n7-producers.test.mjs`：覆盖 RepoDigest 唯一性/registry 绑定、provenance 输入血缘、清洁/未解决漏洞、inventory pending 和静态依赖扫描负例。

## 使用示例

```powershell
node tools\validate-docker-base-images.mjs `
  --file Dockerfile `
  --file vio-ai-agent-frontend/Dockerfile `
  --file docker-compose.yml `
  --file docker-compose.release.yml `
  --require-digest `
  --report artifacts/v1.1/release/base-image-validation.json `
  --no-clobber

node tools\validate-release-compose.mjs `
  --file docker-compose.yml `
  --file docker-compose.release.yml `
  --effective-config artifacts/v1.1/staging/release-compose-config-effective.txt `
  --project-name $env:VIO_RELEASE_COMPOSE_PROJECT `
  --require-digests --forbid-build `
  --report artifacts/v1.1/staging/release-compose-validation.json `
  --no-clobber

node tools\init-vulnerability-exceptions.mjs `
  --image-refs artifacts/v1.1/release/image-refs.json `
  --scan-time (Get-Date).ToUniversalTime().ToString('o') `
  --output artifacts/v1.1/release/vulnerability-exceptions.json `
  --no-clobber
```

## 当前边界

1. 仓库当前 `Dockerfile`、前端 Dockerfile 和基础 Compose 仍使用 tag；运行第一条命令应为非零/`blocked`，这是预期的 fail-closed 结果。
2. `validate-release-compose.mjs` 的通过只代表文本层 digest/build/脱敏约束满足；不代表镜像已 push、digest 可从 registry 回读、SBOM/签名/attestation/漏洞扫描或 staging readiness 已通过。
3. `init-vulnerability-exceptions.mjs` 有效输入时输出 `status=pending`、`passed=false`、`scanComplete=false`；必须由后续 `validate-vulnerability-exceptions.mjs` 绑定真实扫描报告和审批后，才可进入签名/release gate。
4. 所有输入/输出路径必须位于仓库内；`--file a,b`、缺少独立第二文件、路径越界、重复文件和 `--no-clobber` 冲突均拒绝。
