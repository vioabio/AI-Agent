## 1. 开发进度与本轮完成范围

本轮推进 R09 的执行提交隔离，为 R07 安全恢复建立前置条件。原实现失去租约后只请求中断，忽略中断的模型执行器仍可能返回答案，并写入检查点、答案投影、消息和完成事件。仅在最后更新 Run 时检查版本，无法撤销此前已经提交的答案事实。

本轮加入真正的租约写入边界：JDBC 在独立事务中锁住租约，按数据库时间检查 owner、token 和有效期，再执行 Run 持久化；失租约的本地执行永久撤销写入资格。答案提交的多个 JDBC 仓储加入同一个事务，CAS 或检查点失败时整体回滚。

## 2. 租约与提交语义

### 2.1 每次执行独立拥有租约

`ExecutionLease` 包含本次执行的 runId、随机 owner/token、物理任务引用和永久 revoked 标志。工具事件 sink 捕获这个对象，不通过 runId 查找后来执行的 token。审批恢复会获得新的执行对象；旧 sink 即使在其他线程上再次触发，也不能借用新租约。

- heartbeat 返回空或抛异常：先永久撤销本次执行资格，再中断其物理任务。
- acquire 被拒绝或结果不可确认：停止本地执行，不擅自发布 FAILED/CANCELLED。
- 每次执行期写入都检查本地 revoked；启用 durable-resume 时还检查数据库租约。
- 执行最终退出后撤销其 sink；旧工具回调不再写入后续审批恢复执行的事件。
- 失租约的 WAITING_APPROVAL worker 物理退出后清理本地任务、名额、定时器和授权引用；持久 WAITING_APPROVAL/PENDING 事实保留。
- 清理发生在物理退出后，忽略 interrupt 的 callback 不会提前释放 R06 配额。

执行期失租约异常使用固定安全消息，不携带 token、owner、SQL 或底层异常详情。普通持久化动作失败与所有权验证失败分开处理；失败状态也必须通过有效租约写入，不能借异常处理绕过隔离。

### 2.2 仓储 fence

`CheckpointRepository.withLease(runId, owner, token, action)` 是受保护的本地存储动作边界。默认实现直接拒绝；新增自定义仓储必须实现原子 fencing，不能用先查租约、再单独写入的方式替代。

| 实现 | 保证 | 限制 |
|---|---|---|
| InMemoryDurableRunStateRepository | 同一 monitor 内检查并执行；acquire/heartbeat/release 使用同一锁 | 不提供多个内存仓储的事务回滚；只适用于本地测试/开发 |
| JdbcDurableRunStateRepository | Spring `REQUIRES_NEW`，lease `FOR UPDATE`，锁后读取 `clock_timestamp()`，核验 owner/token/expiry，所有 JDBC 动作共用事务 | 必须经 Spring 事务代理调用，使用同一 DataSource/事务管理器；调用者不能预持内部事务需要的 DB 锁 |

使用 `REQUIRES_NEW` 是为了确保 fence 返回时提交/回滚已经完成。否则工具回调若加入已有外层事务，外层可能在 JVM Run monitor 释放后才回滚，使本地生命周期状态与数据库不一致。服务内嵌套 helper 复用同一 fence，不重复开启独立事务。

JDBC acquire/heartbeat 使用数据库时钟判定有效期；同 owner 续取有效租约还必须匹配原 token。失效的旧 release 不能删除新 owner 的租约。

fence 只包本地持久化动作，模型、工具网络调用和 answerLineage 扩展计算在事务外执行。服务统一采用 JVM Run monitor → lease 锁的顺序；数据库 conversation/run 的跨控制路径锁顺序尚未完整收敛，真实并发与死锁故障仍需后续验收。

### 2.3 答案原子提交与本地回滚

答案投影 → 答案事件/assistant 消息 → ANSWER_COMPLETED/USAGE → Run 完成 CAS → RUN_COMPLETED/outbox → finished checkpoint 保持原事件顺序，并处于同一个 JDBC fence 事务。

若任一步失败，不会留下已提交的部分答案事务。本地 `AgentRun` 在持有 monitor 时捕获动态生命周期快照；事务代理完成回滚后恢复 status、startedAt、finishedAt、version，避免 Java 对象错误地保持 COMPLETED。冻结的用户归属、Prompt、上下文和血缘保持原值。CAS 冲突后的重新读取发生在 fence 事务外。

模型/工具执行过程中的事件是各自独立的受保护事务；本轮没有把整次模型调用包成一个长事务，也没有声称所有执行过程事实会随最终答案失败而消失。

检查点版本现在按 `(runId, stepNo)` 读取。审批恢复重新进入 step 0 时，不能使用上次 step 1 的版本，否则不同步骤的 CAS 会冲突。最新检查点仍供恢复判定使用，不能代替指定步骤版本。

### 2.4 答案投影的数据库时间精度

本轮真库测试审查发现，答案投影原先把 Java 纳秒时间直接存入 PostgreSQL `TIMESTAMPTZ`，再以完整 record 相等判断不可变冲突。数据库只保留微秒，首次插入后回读也可能与输入不等，导致正常答案被判为冲突。

`AnswerProjection` 在原始时间先后校验之后统一截断到微秒，覆盖直接构造、工厂方法与 JDBC 回读入口。不改 Run 的原始时间，不需要数据库迁移。低于 1 微秒的差异不再参与投影相等比较；内容变化和至少 1 微秒的时间变化仍拒绝覆盖。回归使用真实 save/JSON/mapper 路径与模拟 PostgreSQL 精度的 SQL 替身，真库 round-trip 仍需 IT。

## 3. 配置与兼容边界

本轮没有新增迁移、公开 HTTP 字段或前端接口。沿用 `vio.run.durable-resume`、lease-ttl-seconds、heartbeat-seconds。durable-resume 默认关闭；关闭时保留本地执行撤销与旧 sink 拒绝，但不提供跨实例数据库租约隔离。

启用 durable-resume 却缺少 CheckpointRepository 时，Service 构造直接拒绝，防止静默退回无 fence 执行。生产环境必须使用 Spring 代理的 JDBC 实现；直接构造 JDBC 仓储调用 fence 会安全拒绝，防止无事务的行锁检查被误用。

用户取消、审批决策、会话删除和期限 timer 是独立控制意图，不借用某个 worker 的租约。它们仍使用现有 CAS 与资源归属规则；多仓储控制事务收敛属于 R09 后续内容。

R07 本轮没有放宽 `RunRecoveryPolicy`。当前 checkpoint 不包含完整答案契约，缓存接口 miss 可能执行模型，历史 RUN_CREATED 也不能重建工具权限；因此 execute-answer/commit-answer 检查点不能直接视为可安全重放。

工具事件 sink 拒绝只保证 Run 事件无法落库。现有 ToolExecutionGateway 会捕获事件出口异常，不能仅靠 sink 拒绝阻止后来发起的真实工具 callback。本轮未新增工具的租约执行门禁，工具副作用账本与模型缓存也不属于本轮 Run fence 事务。后续应接入可信 beforeStart 门禁；已在运行的外部副作用仍需 UNKNOWN、外部幂等和人工核对，数据库回滚无法撤回远端操作。

## 6. 项目学习方案

| 顺序 | 阅读入口 | 理解目标 | 练习与验证 |
|---|---|---|---|
| 1 | AgentRun / AgentRunLifecycleSnapshotTest | 冻结上下文与动态生命周期、CAS version | 模拟 COMPLETED 后回滚，检查时间与版本恢复 |
| 2 | CheckpointRepository / RunLeaseLostException | lease ownership 与稳定拒绝契约 | 自定义不支持 fence 的仓储，验证 action 不运行 |

建议先沿「请求创建 → dispatch → acquire → RUNNING → 模型/工具 → fence 提交 → physical exit」画出调用链，再沿「失租约 → revoked → interrupt → 旧返回/旧 sink 拒绝 → 本地清理」画出故障链。两个链路都要标记数据库事实、Java 对象状态和外部副作用，避免把它们当成同一个事务。
