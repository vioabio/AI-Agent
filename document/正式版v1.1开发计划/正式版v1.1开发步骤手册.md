# VIO 成熟宝可梦智能体：正式版 v1.1 开发步骤手册

> **文档定位**：本手册把 v1.0 候选构建推进到“可现场验收、可恢复、可运营、可量化、可回滚”的 v1.1 GA（正式可用）版本。它是下一轮开发计划，不是已完成工作的声明。
>
> **事实基线（2026-09-02）**：v1.0 已落地 M2～M7 的核心代码、配置和测试骨架；后端最新全量结果为 307 tests / 0 failures / 0 errors / 2 skipped，前端契约与隔离构建通过，严格 release gate 仍为 BLOCKED。真实 PostgreSQL/PGVector、外部模型/MCP、Docker/Compose、Prometheus Targets、备份恢复和目标环境发布尚未在当前主机完成现场验收。详见 [M2-M7实施完成记录.md](../正式版v1.0开发计划/M2-M7实施完成记录.md)。
>
> **阅读原则**：任何“有类、有配置、有单元测试”只能证明代码或静态契约存在；只有命令输出、数据库记录、评测报告、镜像 digest、故障演练和签收记录，才能改变阶段状态。

## 0. 怎么使用这份手册

### 0.1 三档阅读路线

| 读者 | 推荐路径 | 目标 |
|---|---|---|
| 🐤 第一次接手项目 | 第 1 节 → N0 → N1 → N2 | 先建立基线，再理解数据和 Run 为什么必须持久化 |
| 🦾 后端开发者 | 第 2 节差距矩阵 → N1/N2/N3 → N6a/N6b | 关注事务、幂等、队列、权限和评测/反馈证据 |
| ⚡ 秋招/面试速查 | 第 1 节 → 里程碑表 → N7/N8 → Q&A | 用“问题—改动—证据—回滚”讲清工程取舍 |

### 0.2 状态标记

- ✅ **代码已具备**：源码和自动化测试可以复查，但仍可能缺真实环境证据。
- 🟡 **部分完成**：主链或安全边界存在，仍缺持久化、跨实例、产品体验或质量数据。
- ⏳ **环境待验收**：需要真实数据库、模型、MCP、Docker、监控或故障演练。
- ❌ **发布阻断**：不满足 v1.1 GA 强制门禁，不能写成“正式上线”。

### 0.3 每个阶段的固定执行顺序

每个 N 阶段都必须依次完成：

1. 读取本阶段输入快照，确认前置阶段已签收。
2. 建立 ADR、接口、迁移草案，先写失败路径和回滚点。
3. 按“代码 → 测试 → 现场验证 → 证据归档”顺序实施。
4. 更新 artifacts/v1.1/staging/ 对应目录和开发日志，不用口头结论代替证据。
5. 只有退出门槛全部通过，才允许进入下一阶段；否则保持 in_progress 或 blocked。

日志格式可复用 [v1.0开发日志模板.md](../正式版v1.0开发计划/v1.0开发日志模板.md)，但证据目录、阶段编号和发布字段必须改为 v1.1。

### 0.4 v1.1 版本策略

- 保留 v1.0 候选构建、旧镜像、旧 active index 和旧迁移作为可回退基线。
- 先准备 v1.0-candidate 标签和独立 v1.1 分支/工作树；创建或签名 tag 前须确认工作树和授权，迁移只前向兼容，不直接改写已发布事实。
- 继续采用模块化单体优先。只有压测和恢复数据证明需要，才引入 Kafka、Kubernetes、Elasticsearch、GraphRAG 或多模型路由。
- 新开关默认安全关闭；关闭远程 MCP、高危工具或长期记忆时，系统必须能启动并明确降级/拒答。
- 不恢复公开密钥 fallback，不把旧兼容链悄悄变成生产主链。

### 2.2 v1.1 非目标

- 不新增第二个世代或让模型自动跨世代猜测。
- 不开放任意 Shell、终端、服务器文件读取、任意下载或无约束网页抓取。
- 不把自研 MCP 协议栈直接升级成生产主链；先隔离到实验模块。
- 不在单 Agent 质量、恢复和安全门禁未达标前引入多 Agent 平台。
- 不因“企业级”名义默认引入 Kafka/K8s/ES；每个基础设施都必须有容量或恢复证据。

### 2.3 统一 Definition of Done

一个步骤只有同时满足以下条件才算完成：

1. 变更位于正确层级：Controller 负责入口，Service 负责编排，Repository 负责存储，Adapter/Gateway 负责外部协议，前端组件不直接承载后端业务决策。
2. 正常、边界、依赖失败、权限失败和重试路径都有测试或现场记录。
3. 代码、迁移、配置、模型、Prompt、数据和索引版本可追溯。
4. 证据包含环境、命令、时间、样本量和 commit，并落到约定目录。
5. 有可执行回滚方案；回滚不恢复不安全旧行为。

> 📦 **额外知识：为什么 v1.1 先做耐久性而不是新功能？**
>
> v1.0 的主要风险是“看起来能跑，但进程重启、数据库故障或两台实例并发时无法证明”。耐久性让同一个 Run、知识发布和审批决定能够被重放、追责和回滚；它比再增加一个工具更直接地提高成熟度。

## 4. N0：冻结基线并准备真实验收环境

### 4.1 目标与前置条件

N0 不扩展 v1.1 新业务，只补建立可验收基线所必需的最小 M1 fixture/事实入口，把“当前工作树能测试”变成“任何人都能复查的 v1.0 候选基线”。输入为 v1.0 手册、实施记录、最终验收清单、当前 HEAD、pom.xml、`vio-ai-agent-frontend/package.json`、`vio-ai-agent-frontend/package-lock.json`、`.env.example`、`src/main/resources/application-local.example.yml`、`src/main/resources/mcp-servers.example.json` 和 docker-compose.yml。

### 4.2 Step 1：建立候选标签和基线 manifest

基线命令统一在 PowerShell 7+（`pwsh`）执行；先把 `$PSVersionTable.PSVersion` 写入 toolchain。所有文本使用无 BOM UTF-8，结构化 JSON 使用固定键序/换行和 producer 序列化，禁止依赖 Windows PowerShell 5 的默认重定向编码。这样同一 commit 在不同主机上才会得到同一 hash。

1. 检查工作树（包括 ignored/untracked 文件、Docker build context 和 CI artifacts）中没有未授权的密钥、个人数据和临时构建产物；发现曾经进入日志、镜像或版本库的凭据必须先轮换，再继续发布，文档和报告只记录变量名/摘要，不打印值。
2. 当前工作树若 dirty，先生成只读快照（`git diff`、未跟踪文件清单和校验 hash），将与本任务无关的改动保留在外部备份/独立 worktree；只有用户确认后才创建候选 commit。禁止把未审计的 dirty HEAD 直接写成 v1.0-candidate。
3. 在干净且已审计的候选 commit 上创建并（可选）签名 `git tag v1.0-candidate`；若 dirty 或没有用户授权，写入 `tagStatus: pending`、原因和快照 hash，不强行打 tag。Step 1 只生成 `artifacts/v1.1/baseline/manifest.draft.json` 及其草稿 hash，写入 commit、Java/Node、Spring Boot/Spring AI 版本、支持矩阵、开关快照、当前测试数字和 `releaseStatus=BLOCKED`；最终 `manifest.json` 必须等所有 N0 输入完成后由 Step 4 的 finalizer 原子生成。
4. 记录 v1.0 旧镜像、旧数据库快照和 active index 位置；若某项从未产生，明确写 `N/A—not produced` 及补救责任人，不填虚构 ID。

同时冻结 canonical 版本键：`game_release_id`、`dlc_id`、`language`、`battle_format_id`、`ruleset_version_id`、`data_release_id`、`knowledge_release_id`、`index_release_id`。将当前 `sv-v1`/`rules-v1`/`data-v1`/`sv-1`/`scarlet-violet` 等别名映射到唯一 ID，并在 fixture、测试、CI、manifest 和 API 契约中统一。建议先由领域负责人评审 registry 候选：本体使用 `pokemon-scarlet-violet`，DLC 总集使用 `the-hidden-treasure-of-area-zero`（或明确拆成碧之假面/蓝之圆盘两个 ID）；当前 UI 的 `scarlet-violet`、`scarlet-violet-teal-mask`、`scarlet-violet-indigo-disk` 在评审前只登记为 alias，不能直接假定为最终 canonical ID。

若仓库存在中文或空格路径，基线脚本必须使用 UTF-8、`core.quotePath=false` 或 `-z` + NUL 解码，并在生成 hash 前校验每个路径能由 `Test-Path -LiteralPath` 复读；Git 的 C 引号/八进制转义不可直接当文件名。公共证据只保留 repo-relative path，不固化本机用户名和绝对路径。

### 4.4 Step 3：准备 staging 依赖

- Redis（队列、租约、全局配额和幂等）；
- 已授权的模型、Embedding 和 Search 服务；

## 5. N1：把知识平面变成可重试、可发布的数据生产线

### 5.1 当前缺口与两阶段门禁

v1.0 已有 source → document → document_version → chunk → knowledge_release → index_release 模型、显式摄取 API 和 READY/effective 过滤；但导入仍主要是同步服务调用，缺持久 Job/Attempt、跨实例 reservation、DLQ、跨表事务和真实 PGVector 证据。

N1 拆为两个不可混淆的子阶段：N1a 只生成可重建、未激活的 candidate index；N6a 在 candidate 上完成真实评测；N1b 读取不可变评测报告后才允许 promotion/atomic publish；N6b 在发布后完成反馈闭环。这样既能让 N4 使用候选数据开发，也不会形成 N1 与 N6a 的循环依赖。

### 5.2 Step 1：补充 Job、Attempt、Outbox 和 DLQ 迁移

建议新增前向迁移（实际编号以当前数据库为准）：

~~~text
V8__knowledge_ingestion_jobs.sql
V9__knowledge_ingestion_outbox.sql
V10__knowledge_ingestion_dlq.sql
V11__knowledge_release_publish_transaction.sql
~~~

以上 `V8`～`V11` 只是示例编号；先执行 `flyway info`/检查当前 migration，再分配下一个未占用版本。N0/M1 的兼容迁移优先占号时，后续文件必须顺延并在所有环境运行 `flyway validate`。

至少包含：

| 表/字段 | 用途 |
|---|---|
| ingestion_job | source、document/version、目标 release、状态、幂等键和租约 |
| ingestion_attempt | 尝试次数、错误分类、开始/结束时间和 worker |
| ingestion_outbox | 让数据库提交与待处理消息同一事务 |
| ingestion_dlq | 保存不可重试输入、最后错误和人工 replay 信息 |
| vector_build_job | 候选 index、Embedding 模型/维度和构建进度 |

为 source+idempotency key、release+chunk、job 状态迁移和 outbox 未发布项建立数据库约束。

### 5.3 Step 2：实现 reservation、worker 和有限重试

1. 在 KnowledgeIngestionService 外增加 Job Service，不把队列循环塞进 Controller。
2. 用数据库原子 reservation 或 Redis lease 保证两实例只有一个 owner；赢家结果必须可被其他实例读回。
3. 将错误分为参数/许可错误（不可重试）、依赖暂时失败（有限退避）和系统错误（转人工）。
4. worker 被杀掉后，租约过期的 Job 可被重新领取；同一 checksum 不重复写入 chunk/vector。
5. outbox publisher 有发送确认、重试和死信指标。

reservation 的唯一键必须覆盖 source、checksum、目标 release 和 ingestion contract 版本；worker 领取、续租、完成和转 DLQ 都要有可查询的状态迁移。Embedding 任务还要把模型名、维度、Prompt/预处理版本和 index profile 写入构建记录，避免“同 checksum、不同向量空间”被误认为可复用。

每次重试要记录 attempt_no、backoff_ms、jitter、error_class、lease_owner 和最终状态；达到 maxAttempts 后只能进入 DLQ。DLQ replay 需要 operator 角色、reason、原始 checksum 和新 idempotency key，并受 retention/告警策略约束。

### 5.4 Step 3：补齐内容校验与冲突审核

~~~text

→ MIME/magic/大小/Schema 校验
→ 游戏/DLC/语言/赛制元数据校验
→ checksum 去重
→ 许可证与可信等级校验
→ 跨来源冲突检测
→ 人工审核或 quarantine
→ chunk/Embedding
→ 候选 index
→ N6a 黄金集与发布门禁
→ 原子发布
~~~

冲突不得静默覆盖；必须产生 quarantine 记录、差异摘要和处理人。

> 📦 **额外知识：Outbox 解决什么问题？**
>
> 如果数据库提交成功但消息发送失败，或者消息发出但数据库回滚，就会出现“记录存在但任务没启动”或“任务启动但找不到记录”。Outbox 把待发送事件和业务状态放在同一事务，之后由独立 publisher 重试，避免双写不一致。

## 6. N2：让 Run、事件和会话真正可恢复

### 6.1 当前缺口

### 6.2 Step 1：建立事务边界和 Checkpoint

模型调用也可能在重启后产生不同输出。对可重放的模型步骤增加 `model_invocation`/response cache（request_hash、model_version、prompt_version、usage、response_digest、encrypted_response/artifact_uri、key_version、expires_at）；缓存按敏感数据策略加密、限权并设置 TTL，恢复命中缓存时不得二次计费/调用。不可重放且没有缓存的模型步骤必须进入人工确认或 FAILED，并附带证据，不能把模型重复调用当作幂等。

`idempotency_key`、`parameter_hash` 和 request hash 必须非空且由规范化输入生成；外部写操作拿不到幂等键时直接 WAITING_APPROVAL/拒绝。ADR-001 固定 Outbox 为 at-least-once（或给出可证明的 exactly-once 边界），publisher/consumer 以事件 ID 去重，登记重试上限、积压恢复和终态不丢失规则。

5. PokemonAgentRunService 保持唯一生命周期拥有者；VioManus 仍是受控执行器。

### 6.4 Step 3：让状态、事件和 outbox 原子提交

状态迁移、终态事件、checkpoint 和 outbox 必须在同一数据库事务中提交；创建 conversation 时，conversation、首个 Run、首条用户消息/事件也必须在同一事务边界内完成或全部回滚。cancel 接口必须同时通过 CSRF/Origin 校验（浏览器会话）和资源授权。故障注入场景至少包括：

- 状态已更新、事件写入前进程退出；
- 事件已写入、outbox publisher 退出；

### 6.5 Step 4：完成事件保留、410 和传输选型

先用 ADR 明确选择：

- 方案 A：Redis Streams + SSE fan-out；
- 方案 B：数据库事件页 + 长轮询；
- 方案 C：WebSocket（只有确有双向需求时采用）。

无论选哪种，必须保留 PostgreSQL 事件事实。实现：

1. afterEventId/Last-Event-ID 校验和分页；
2. 事件过期返回 410，并附最新摘要/重新获取入口；
3. 背压时先降级正文 delta，不丢失终态、引用和审批事件；
4. 断线不取消 Run，显式 cancel 才改变状态；
5. 跨实例订阅和关闭连接有指标。

事件 envelope 固定包含 `schemaVersion`、`sessionId`、`runId`、`eventId`、`traceId`、`timestamp`、`type` 和 `payload`。创建接口必须返回 HTTP 202、`runId` 和 `eventsUrl`；事件接口必须同时支持 `afterEventId` 与 `Last-Event-ID`，并对非法游标、跨用户 run 和过期游标返回明确错误/410。当前 `parseCursor` 对非法 header 的静默 fallback 必须改为 400 + 结构化错误，不能把客户端错误当作从头读取。模型调用、工具调用和整体 Run 分别配置 timeout 与 cancellation token；终态写入后由数据库约束/服务守卫禁止 `answer.delta`、`tool.started` 等后续事件。

禁止用 unknown 伪装完整血缘。反馈契约和 answer_projection 可以在 N6a 期间实现，但完整反馈闭环必须在 N1b 已发布一个 candidate 后执行，不能让“publish”反向成为 N6a 的前置条件：

~~~text
submit → triage → review → correction
→ reindex → targeted eval → publish
→ re-answer/notify → verify → close
~~~

### 10.4 N6a Step 2：接入首 delta TTFT、Token、成本和 OTel

1. 在第一条 answer.delta 发出时记录 TTFT，而不是在完整答案结束时估算。
2. 从模型响应/回调读取 prompt token、completion token、重试和降级信息。
3. 按 scenario、model、prompt、data_release、knowledge_release、index_release 分桶。
4. 让 W3C `traceparent`/`Correlation-ID` 从 browser→API 注入并贯穿 HTTP → Run → outbox/worker → route → retrieval → model → tool → DB → feedback；SSE/事件 envelope 回传 traceId，Playwright、数据库审计和 OTel trace 要能交叉核验同一 Run。
5. 敏感参数只记录摘要和 digest，不记录密钥原文。

将 dashboards、Prometheus rules、告警路由和配置快照纳入版本库并记录 commit/hash。N6a 只导出可版本化的指标查询和 OTel schema，不访问实时监控端点，也不执行故障注入；这样评测阶段不会提前生成 N7/N8 的生产观测证据。

实现待新增的 `tools/export-metric-queries.mjs`、`tools/export-otel-contract.mjs` 和 `tools/validate-otel-trace-sample.mjs`，仅输出 schema/query 契约（`artifacts/v1.1/eval/metric-queries.json`、`otel-queries.json`、对应 schema 与 SHA-256）。脚本必须带 schemaVersion、commit、query owner 和 redaction 规则，并在输出已存在时失败；未落地时保持 pending。

实时 Prometheus/Alertmanager/Grafana 探针、四类故障注入（模型超时/5xx、数据库不可用、MCP 断开、候选索引查询失败）、Alertmanager 原始事件、触发延迟、责任人和恢复动作全部由 N7 的 `collect-observability-probes.ps1`/`aggregate-observability-evidence.ps1` 负责。N7 执行时按 staging 实际 URL（必要时使用 `docker compose exec`）采集，N6a 只在 gate 中检查 N7 证据是否存在，不能把 N6a 的 schema/query 文件当作现场通过。

### 10.5 N6a Step 3：冻结指标字典和门槛

每个指标登记公式、分母、排除项、窗口、最小样本、版本、负责人、阈值和回滚条件。候选门槛沿用 v1.0 规格，实际数值只能来自报告：

| 指标 | 候选门槛 |
|---|---:|
| 固定事实成功率 | ≥98% |
| 版本/规则约束成功率 | ≥98% |
| 确定性计算正确率 | 100% |
| RAG Recall@5 | ≥90% |
| 引用正确率 | ≥95% |
| Groundedness | ≥95%（N0 可经 ADR 调整并版本化）；报告必须输出，未达阈值即阻断 |
| 无答案处理率 | ≥90% |
| 工具参数正确率 | ≥95% |
| 首 Token P50 | 观测项；必须输出分桶值，阈值由 N0 dictionary 冻结（没有阈值不得触发自动回滚） |
| 首 Token P95 | ≤2.5s（按 scenario/model 分桶） |
| Run 完整耗时 P50 | 观测项；必须输出分桶值，阈值由 N0 dictionary 冻结（没有阈值不得触发自动回滚） |
| Run 完整耗时 P95 | ≤30s（按 scenario/model 分桶） |
| 取消生效 P95 | ≤2s |
| Token/成本 | 相对已批准基线不超过 20%，按 metric-dictionary 公式计算 |

N6a 还必须把“指标定义可读”变成机器证据：实现待新增的 `tools/validate-metric-dictionary.mjs` 和 `tools/export-metric-queries.mjs`，校验每个指标的 formula/denominator/window/minRequests/query/thresholdVersion/owner，并输出 `artifacts/v1.1/eval/metric-schema.json`、`metric-queries.json` 及 SHA-256。仅把字段写在 Markdown 或 dashboard YAML 中不算通过；脚本未落地时该项保持 pending。

OTel 同样要有版本化契约：实现待新增的 `tools/export-otel-contract.mjs`，固定 span 名、必需 attributes、sampling、redaction 和 trace-to-run 关联，输出 `artifacts/v1.1/eval/otel-schema.json`、`otel-queries.json` 及 SHA-256；N6a gate 显式校验这两份文件与运行时 Trace 样本的 schemaVersion 一致。

### 10.6 N6a Step 4：让 CI 和 Release Gate 真正阻断

推荐流水线：

~~~text
compile/test
→ frontend lint/typecheck/unit/build
→ contract/security scan
→ real Golden Set
→ OTel/metric schema check
→ release report
~~~

镜像构建、SBOM/签名、Compose/staging smoke、readiness、业务探针和灾备只由 N7 负责；N6a 只产生候选评测与质量证据。这样不会在 N6a 提前生成一份未经过 staging 的“发布镜像”，也不会出现两个 producer 写同一 release 证据。

当前 `quality_gate.mjs` 主要是 scaffold/结构性检查，不能把它当成已具备的生产 release gate。v1.1 需要新增或改造：`--mode=ci` 只检查结构；N6a 的 `--mode=release` 检查真实样本、不可变报告 hash、版本血缘、阈值、契约和安全证据；N7/N8 的最终发布 gate 再叠加 staging readiness、实时观测、回滚和 N6b 反馈证据。任何红队失败、跨用户泄漏、确定性错误或缺失 release 绑定都直接阻断。

当前脚本固定读取 `evaluation/manifest.json`，不读取 metric-dictionary，默认报告路径仍是 `artifacts/v1.0/eval`，因此直接运行它会验收 v1.0 scaffold。v1.1 开工时先扩展 CLI（或增加 wrapper）支持 `--manifest`、`--dictionary`、`--metrics`、`--run-manifest`、`--run-hashes`、`--metric-schema`、`--metric-queries`、`--otel-schema`、`--otel-queries`、`--otel-trace-sample`、`--security-report`、`--contract-report`、`--readiness-evidence`、`--feedback-report`、`--report/--output`，并把默认路径切到 reviewer 签收后的 `evaluation/v1.1/manifest.ready.json`、`evaluation/v1.1/metric-dictionary.json` 与 `artifacts/v1.1/eval`；也可以让 manifest 引用这些证据，但 gate 必须解析并校验其 hash、schemaVersion 和 releaseId。N6a 命令只把质量、红队和契约证据作为前置；N7/N8 的最终 gate 再传入 readiness 和 N6b feedback。扩展前命令只能记为 pending。gate 必须校验 manifest 与 dictionary 的 hash/threshold 完全一致，拒绝报告自行携带另一套阈值；任何已传入的 readiness/反馈证据缺失或不匹配都必须非 0。`evaluation/v1.1/manifest.json` 是 draft source，`evaluation/v1.1/manifest.ready.json` 是 ready canonical，状态只允许 `draft|ready|blocked`；`artifacts/v1.1/release/release-manifest.json` 是发布 manifest，状态只允许 `BLOCKED|RC|DEMO_ONLY|GA`，两者不能互换传给 gate。

### 11.4 Step 3：灰度、探针和自动回滚

~~~text
签名镜像
→ staging smoke
→ 小流量 canary
→ readiness + 业务探针
→ 观察错误预算/质量指标
→ 扩大流量或自动回滚
~~~

失败时不切流；切流后若 Run 失败率、跨用户错误、TTFT、成本或工具拒绝异常超过阈值，恢复上一 digest，并按 Run/data/index 粒度回退。

在 ADR-007 中选定唯一回滚载体并实现可审计命令。计划采用“发布脚本适配器”作为最小实现（当前 `ops/release/` 尚不存在，属于待实现）：`ops/release/promote.ps1` 只接受已验签的后端/前端 digest，`ops/release/rollback.ps1 -Manifest <previous>` 执行上一 manifest 的 digest、配置和 release 指针回退；如果目标平台已有 Kubernetes/云发布器，可由适配器调用该平台 API，但不得同时维护第二套未审计手工流程。执行身份只授予发布服务账号，开发账号无生产回滚权限。

上一版本不能靠手工复制。待新增 `tools/resolve-previous-release.mjs` 从受信 release registry/已签名制品解析当前生产 active pointer 指向的唯一上一 manifest，校验 schema、hash、`releaseClass=GA`、`status=GA`、环境为 prod、`generatedAt` 早于当前 candidate、releaseId 不同、镜像签名、migration/data/knowledge/index 指针和有效期，输出 `release/previous-manifest.json` 及来源报告（含 registry URI/不可变 digest、pointer version、resolvedAt、previousReleaseId/currentReleaseId）；解析失败或 previous 为 RC/DEMO_ONLY 时禁止 canary/rollback。

~~~powershell
node tools\resolve-previous-release.mjs --registry $env:VIO_REGISTRY --environment prod --active-pointer --require-status GA --require-release-class GA --schema contracts/release-manifest-v1.1.schema.json --output artifacts/v1.1/release/previous-manifest.json --report artifacts/v1.1/release/previous-release-resolution.json --no-clobber 2>&1 | Tee-Object -FilePath artifacts\v1.1\release\previous-release-resolution.log
if ($LASTEXITCODE -ne 0) { throw 'previous release resolution failed' }
~~~

## 12. N8：GA 候选、观察期、演示与签收

### 12.1 Step 1：做 72 小时观察期（演示候选可先做 24 小时）

GA 默认连续观察 72 小时，并至少覆盖 500 个业务请求、20 个真实领域场景和每个 P0 工具路径；仅用于秋招演示的 RC 可先完成 24 小时且不少于 100 个请求，但状态必须标记为 `DEMO_ONLY`，不能写作 GA。在有限流量下持续观察：

- Run 成功/失败/取消/超时比例；
- 首 delta TTFT、完整耗时和错误预算；
- Token、成本、重试和降级；
- 检索空结果、引用错误、工具拒绝和审批等待；
- JVM、数据库、Redis、连接池和队列积压；
- 日志脱敏、审计完整性和备份可读性。

由发布负责人每天签收观察报告。每个 5 分钟窗口只有在请求数达到 N0 冻结的 `minRequestsPerWindow` 时才计算比例；观察期总量使用 `minRequests`（GA 500、DEMO_ONLY 100），低流量窗口合并到 1 小时并标注分母，不得用小分母制造稳定假象。指标来源必须写 Prometheus query/Trace 聚合和 thresholdVersion。Run 失败率、TTFT、队列积压和 P0/P1 触发条件均从同一份 metric-dictionary/ADR-007 读取，并由 collector 记录 thresholdVersion；文档中的 5%/2.5s 仅为示例，不是第二套阈值。任一有效窗口触发冻结阈值，立即暂停扩容并回滚；观察期内出现 P0 问题，不以“样本少”忽略。

每个窗口由待新增的 `ops/release/collect-observation.ps1` 写入 release-scoped 的 `observation-windows/<windowId>.jsonl`（GA 在 `prod/<prodReleaseId>/`，DEMO_ONLY 在 `staging/<demoId>/`），以 checkpoint/append-only 方式支持中断续采；同一 run 不覆盖已有窗口文件。观察期结束后由 `tools/aggregate-observation.mjs` 按序合并为 `observation-72h.jsonl` 或 `observation-24h.jsonl`，再由待新增的 `tools/validate-observation.mjs` 校验窗口连续性、总分母、签名和阈值，生成 validation JSON 与 hash。三分钟演示保存 `demo-script.md`、截图/录像、Trace/Grafana 链接，并在 release manifest 的 evidence 中引用。collector/aggregator/validator 任一未落地时观察期保持 pending：

观察证据的机器门禁必须只信任**可回读的窗口序列**：至少两条带唯一 `windowId` 的记录，时长从 `windowStart`/`windowEnd` 计算而不是从单条 `observationHours`、`durationHours` 或汇总 `requestCount` 推断；窗口按时间排序、不得重叠，允许最多 60 秒的采集调度边界抖动但窗口覆盖时长仍须达到门槛。每条通过记录还必须声明至少两个独立 telemetry source（当前 collector 为 HTTP readiness + Prometheus metrics；`sourceEvidence` 描述应带 `observedAt`，若提供 metrics 分母则须与窗口 `requestCount` 一致），并拒绝 `not-executed`、手工/合成、跨环境复制来源。该结构规则同时适用于 GA（72 小时/500 请求）和 DEMO_ONLY（24 小时/100 请求），只改变阈值，不允许用 DEMO_ONLY 规则绕过序列或来源校验。

GA 的观察文件和现场证据必须在真实生产切流后由生产 collector 直接写出，不能把 `release/` 或 `staging/` 文件复制/改名成 `prod/`。实现待新增的 `ops/release/collect-prod-evidence.ps1`，它必须读取 N0 environment contract、当前 prod active release 和唯一 `releaseId`，拒绝 localhost/ staging URL、拒绝 `Copy-Item` 伪造证据，并在输出 JSONL/JSON 中写 `environment=prod`、releaseId、git/image digest、采集时间和来源。它负责 readiness、Compose/config 脱敏快照、SPA/Run/SSE/cancel/429/410 业务探针、Prometheus/Alertmanager/Grafana 原始探针及已批准的生产回滚 drill 证据；每个文件采用 no-clobber + 原子写入。观察 collector 同样必须以实际 prod URL 和 releaseId 采集，不接受从 staging 输入补齐分母。

release manifest 只登记 pointer 路径和 registryVersion，不把 pointer 自身的 SHA-256 回填进 manifest；否则 manifest → pointer → manifest hash 会形成循环。pointer、旧 pointer、注册/验证报告的 hash 统一写入 release-pointer-evidence-hashes.json（DEMO_ONLY 写入 demo-final-evidence-hashes.json），由 gate 在 manifest 封存后校验。模板中的尖括号和 null 仅是 schema 示例，producer 必须替换为真实 releaseId、环境、数字 embedding.dimension 和对应 evidence hash，校验器拒绝任何占位值。
当前 `evaluation/create-release-manifest.mjs` 输出的是 schemaVersion `1`、`releaseId`/`images`/`modelVersion`/`evaluationRunId` 等基础字段；v1.1 使用前必须升级脚本到上述 `schemaVersion: v1.1`，或增加显式转换器并在报告中保存映射。模板中的 `repoRoot` 固定为 Git 根目录，`artifactRoot` 是相对于该根目录的目录；所有 evidence path（例如 `eval/...` 实际位于 `artifacts/v1.1/eval/...`）先用 `--repo-root`/Git 根解析，再做 canonical path 越界检查，禁止按当前 cwd 或 manifest 所在的 release 子目录重复拼接。校验器必须覆盖从仓库根、子目录和 CI 工作目录运行的路径测试。未测量的 RPO/RTO 用 JSON `null`，不能把占位字符串或 `0` 送入机器门禁；`embedding.dimension` 必须是与数据库 vector 列和实际模型一致的数字（当前配置候选值为 1536，不能盲抄）。

环境证据必须与 release 环境一致：`releaseClass=GA` 的 manifest 只能引用 `artifacts/v1.1/prod/` 下由生产探针直接采集的 readiness、Compose/config、观测、业务探针、配置快照、回滚和 72 小时观察文件；`staging/` 证据只能支持 RC/DEMO_ONLY preflight，不能复制后冒充 prod。若项目暂不具备生产环境，最终状态保持 `RC`/`DEMO_ONLY`，不要把 `--environment prod` 当作字符串开关。

`RC/DEMO_ONLY` 可以暂存 `null` 的 RPO/RTO，但必须明确“未完成灾备验收”，且仍需通过 Secret/权限、release gate、镜像完整性和最小受控回滚证据；申请 GA 时必须替换为 number，并由 `drill-rpo.json`/`drill-rto.json` 的 hash 和 `actual <= target` 机器校验（Markdown 只作解释）。GA 的 `releaseClass=GA`、`status=GA` 只允许在最终 gate 通过后写入；模板和 preflight 先保持 `status=BLOCKED`。仅演示时 preflight 使用 `releaseClass=DEMO_ONLY,status=BLOCKED`，最终 DEMO gate 才原子生成 `releaseClass=DEMO_ONLY,status=DEMO_ONLY` 的独立 manifest，同时把 `observationWindowHours/minRequests` 改为 24/100，且 `environment=staging`、RPO/RTO 明确为 `null/NOT_MEASURED`；绝不能用 DEMO_ONLY 冒充 GA。evaluation report、双镜像 SBOM/签名/provenance、依赖 inventory、漏洞例外、观察期和演示证据的 hash/路径也必须在 manifest 中可回读。`evaluationRunId` 是包含所有套件的 aggregate id，`evaluationRunIds` 用于逐套追溯；任一套件缺失不得用 aggregate id 掩盖。

`evidence.observation` 是按 releaseClass 条件校验的联合字段：GA 只要求并校验 `ga`（72 小时/500 请求），DEMO_ONLY 只要求并校验 `demoOnly`（24 小时/100 请求），另一分支可省略；RC/BLOCKED 不得伪装成已完成观察期。Schema 必须允许 `releaseClass=GA,status=BLOCKED` 的生成中模板，但不允许它进入发布或签收状态。

最小映射关系：`release`→`releaseId`，`model`→`modelVersion`，`evaluationReportSha256`→`evidence.evaluationReport.sha256`，`sbom/signature/provenance`→`evidence.images.<backend|frontend>`，原单 `imageDigest`→`images.backend/frontend`；`supportMatrix`、`embedding`、`environment`、`rollback`、dependency inventory、漏洞例外和 RPO/RTO 由 v1.1 扩展写入。CI 必须只读取 v1.1 schema，不得把 v1.0 生成器的默认 `artifacts/v1.0` 路径当作发布产物。

## 16. 面试与实操 Q&A

### Q1：v1.1 和 v1.0 最大区别是什么？

v1.0 解决“核心骨架是否存在”，v1.1 解决“在真实依赖、跨实例、故障和发布条件下能否证明它可靠”。

### Q2：为什么不直接把 v1.0 标成正式版？

因为真实 PGVector、外部模型/MCP、Docker、监控、评测和恢复尚未有现场证据；代码测试通过不能替代这些验收。

### Q3：为什么 N0 要补 M1 fixture？

没有真实版本键、事实查询和队伍资源，N1 的过滤、N4 的表单和最终演示都只能展示空契约，无法形成产品闭环。

### Q4：为什么先做 Outbox？

知识 Job、Run 状态和事件都涉及数据库与异步消息。Outbox 保证状态和待发送任务可追溯，失败后能重试而不是静默丢消息。

### Q5：Checkpoint 如何避免重复调用工具？

Checkpoint 保存步骤和上下文，effect ledger 以 Run、幂等键和工具版本唯一记录副作用；恢复时先查 ledger，再决定是否重放。

### Q6：SSE 断线为什么不等于取消？

断线只是传输层变化，Run 是业务层任务。只有显式 cancel 才改变 Run 状态，客户端用 eventId/Last-Event-ID 补读。

### Q7：为什么当前 snapshot SSE 不够？

它能展示已有事件，但不能证明长连接 fan-out、背压和跨实例实时订阅；N2 必须选择并验证明确的传输方案。

### Q8：MCP 为什么不能绕过 Gateway？

MCP 解决发现和传输，不解决身份、Schema、风险、超时、审批和审计。所有运输方式都必须经过同一治理边界。

### Q9：为什么长期记忆要晚于会话？

会话是用户可查询的事实，长期记忆是从事实推断出的二次数据；后者必须有授权、TTL、来源、删除和用户隔离。

### Q10：为什么 unknown 不能作为反馈 release？

它会掩盖答案无法追溯的事实，导致纠错无法定位到数据、知识或索引版本。无法关联时应拒绝或标记不可追溯。

### Q11：为什么 307 个测试不能写成业务准确率？

单测数量只能说明代码路径被执行；业务准确率需要固定题集、人工答案、样本量、模型/Prompt/数据/索引版本和不可变报告。

### Q12：什么时候值得引入 Kafka？

当 DB Job/Redis Streams 在有真实吞吐、积压、恢复或跨团队边界证据的情况下成为瓶颈，再用容量和故障数据支撑升级。

### Q13：如何证明回滚真的有效？

发布单元绑定镜像 digest、迁移、数据/知识/索引、模型和 Prompt；故意制造故障，验证 readiness 阻断、上一版本探针和 RPO/RTO。

### 最终状态规则

> 任意一个 P0 强制项没有证据，v1.1 状态必须保持 BLOCKED。只有把证据路径、实际输出、镜像 digest、评测 hash 和 RPO/RTO 回填到验收清单，才能写作 GA。

> **下一步建议**：先执行 N0，不要直接从 N1 写业务代码。N0 的基线 manifest、M1 fixture、staging 依赖和支持矩阵一旦冻结，后续每个阶段才有可比较、可回滚的起点。

> 💡 **一句话记住**：v1.1 的核心不是让宝可梦智能体“知道更多”，而是让每次回答、每个工具动作和每次发布都能被验证、恢复、追责和安全回退。
