| 模块 | 改动前的问题 | 本轮实现 | 剩余门槛 |
|---|---|---|---|
| Run 调度 | cached pool 可随请求增长，缺少排队上限 | 固定 worker、有界队列、总量/主体/租户准入 | 压测与多实例共享准入 |
| HTTP 过载 | 执行资源不足没有稳定契约 | 429/503、稳定错误码、Retry-After、OpenAPI | 网关与调用方的真实重试验收 |
| 幂等创建 | 先占幂等键再发现容量不足会污染重试 | 容量拒绝发生在 claim/资源持久化之前；满载可重放旧 Run | 创建存储中途失败的跨仓储原子性 |
| 排队时限 | 排队与执行之间没有清晰时限 | queue TTL、总 deadline、worker 启动时补查 | 真实慢模型/慢库场景 |
| 取消 | Future 已取消不代表回调已经停止 | 物理退出前保留 worker 和 Run 配额；排队取消立即出队 | 外部进程/远端服务取消协议 |
| 审批 | 等待审批可能绕过容量和清理路径 | WAITING_APPROVAL 保留准入票据，恢复复用同一票据 | 多实例审批/权限重新获取 |
| 工具执行 | 独立 cached pool 与超时重试有并发风险 | 有界工具池、排队计入超时、停止重试、UNKNOWN 防重复 | 生产账本与外部副作用人工核对 |

## 2. Run 容量模型

`PokemonAgentRunService` 的现代 Run 路径使用 `RunAdmissionProperties` 和 `RunAdmissionController`。worker 使用 `ThreadPoolExecutor`、`ArrayBlockingQueue`、`AbortPolicy`；queue-capacity 为 0 时使用 `SynchronousQueue`。不会让请求线程代替 worker 执行模型，也不会静默丢弃已接收任务。

默认单实例最多登记 24 个 Run（8 worker + 16 queue），同一租户最多 16 个，同一租户下的主体最多 4 个。排队、执行以及 WAITING_APPROVAL 都计入登记总量。等待审批不占用 worker，但保留票据；因此 worker 空闲也可能因审批积压达到准入上限。

租户取自服务器已认证的 PrincipalPolicy 或 TokenBinding；本地无绑定模式使用 `local`。主体沿用 Controller 已绑定的 userId。请求头不能直接决定租户配额。恢复没有请求身份，使用服务器拥有的 `recovery` 范围和持久化 owner；这保证恢复不绕过实例总量，并限制 `(recovery, owner)` 的登记量，但尚未重建原始租户准入归属或与原租户的主体配额合并计数，需在 R07 的授权恢复中补齐。

### 2.1 创建、拒绝与重放

1. 校验请求和幂等键，先只读查询现有有效幂等记录。
2. 已存在的同语义请求直接返回原 Run；满载也可回放，不重复占配额。
3. 新请求先检查运行时可用性并获取票据，再 claim 幂等键、写会话/Run/checkpoint/事件/消息。
4. 排队成功后完成幂等响应。已提交 worker 时，即使幂等 complete 出错，也保留已有执行，避免 CREATED Run 被遗留。
5. dispatch 前的 checkpoint/事件/消息/调度失败，显式失败 Run 并回收本地状态；事件存储异常仍向调用方暴露，不能伪称事件已可靠落库。

| HTTP | code | 含义 |
|---|---|---|
| 429 | RUN_PRINCIPAL_LIMIT | 当前主体的登记限额已满 |
| 429 | RUN_TENANT_LIMIT | 当前租户的登记限额已满 |
| 429 | RUN_CAPACITY_EXCEEDED | 当前实例总登记量已满 |
| 503 | RUN_EXECUTION_UNAVAILABLE | 运行时关闭或调度不可用 |

上述响应包含 JSON `code`/`message` 和秒数 `Retry-After`，默认 1，支持 1～3600。错误正文不包含账户、租户、Prompt 或队列内部状态。

429 在资源持久化与幂等 claim 之前产生，可以用原键原请求重试。关闭检查产生的 503 也不创建资源；极窄的「票据已获、资源已存、worker/scheduler 随后拒绝」503 可能留下 FAILED Run，原键重放可读回它，不能承诺所有 503 都没有 Run。HTTP 请求失败不能推导外部副作用一定没有发生。

本轮没有增加数据库迁移。`IdempotencyStore.find` 的内存/JDBC 实现只读，不修改 claim。创建前半段的多仓储事务与 IN_PROGRESS claim 故障回收协议仍属 R09，当前不通过无条件删除 claim 来冒险绕过跨实例所有权。

### 2.2 TTL、取消与任务所有权

- queue-wait-ms 默认 30000，只限制每次 dispatch 的排队等待；审批恢复重新计算一次排队时限。
- 总 deadline 从创建计算，包含排队、执行和审批等待；审批不会延长原总期限。
- timer 到期主动取消排队任务；worker 实际获得任务时也核验 TTL 和总 deadline，模型调用前及答案提交前再次核验总期限，避免 timer 调度延迟导致逾期调用或提交答案。
- 排队任务取消后从实际队列移除，同时取消关联 timer，释放票据。
- 已进入 worker 的任务在物理 callback 和 lease cleanup 完成之前保留任务所有权。`Future.isDone()`/`isCancelled()` 不用作物理退出依据。
- 单个任务只取消自己拥有的 queue timer，避免旧 worker 退出时取消审批恢复任务的新 timer。
- cancel、timeout、审批拒绝和会话删除使用 finally 清理；即使终态事件写入失败，本地票据也不会永久遗留。
- 关闭时停止接收新任务，取消排队/执行任务并清除 timer；已有持久 WAITING_APPROVAL/PENDING 审批保留供重启恢复。旧审批 worker 实际退出后清除本地票据；协作中断抛出 InterruptedException 也不会误把待审批事实改为 CANCELLED。

RUN_QUEUE_TIMEOUT、RUN_EXECUTION_UNAVAILABLE、RUN_AUTHORIZATION_EXPIRED 作为事件 errorType，分别表示排队过期、dispatch 不可用、执行前捕获授权快照已到期。授权检查失败不会进入模型回调。

## 3. 有界工具执行

`ToolExecutionGateway` 使用独立 `BoundedToolExecutor`，默认 8 worker 与 32 queue，避免模型 worker 和工具 callback 共用一个池产生相互等待。

工具能力卡的 timeout 包含排队等待；worker 执行前检查原始时限并再次验证授权，结果实际完成时间也参与超时判断。准入阶段的过载/关闭返回 REJECTED，稳定前缀为 TOOL_EXECUTION_OVERLOADED / TOOL_EXECUTION_SHUTDOWN；已启动 callback 因关闭而中断则返回 FAILED，写结果可能为 UNKNOWN。timeout/cancel 结束本次尝试，不继续自动重试。

取消是 Java 的协作中断：不响应 interrupt 的 callback 仍占用原 worker。执行器不会因为 Future 已完成取消就再创建补充线程；后续请求按照固定池与队列上限拒绝。开始执行的写 callback 无法确认结果时，副作用账本记 UNKNOWN，禁止自动重放；本地无账本模式同样保留不确定执行标记，拒绝同键重试。进程内标记不能跨重启，生产写工具仍需持久账本与人工核对流程。

工具关闭先拒绝新调用并取消待执行任务，等待有界 grace，再请求中断运行任务。它不能强杀 Java 回调，也不宣称回滚远端副作用。

UNKNOWN 标记在审批逻辑之前检查，并在同键锁内复查，避免审批过期后重新发起审批来绕过不确定执行事实。写 callback 已执行而审计失败时，即使审计出口配置允许读调用降级，写调用仍返回 FAILED 并保留 UNKNOWN。标记在 Gateway 实例生命周期内不自动删除，也不提供本轮管理清除接口；长期结果缓存与 UNKNOWN 标记的容量/保留策略应结合 R07/R09 和持久账本治理。
