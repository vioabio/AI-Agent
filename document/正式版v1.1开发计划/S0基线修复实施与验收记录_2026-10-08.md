## 4. 改动清单与设计取舍

### U01 · F01 启动契约

- **`src/main/resources/application-demo.yml`（新增）** —— demo 作为 prod 的受限覆盖层，
  显式成对设置 `oidc.enabled=false` + `oidc.required=false`。
  之所以必须成对：`OidcProperties.validationErrors()` 在
  `enabled=false && required=true` 时返回错误，`OidcSecurityConfiguration.@PostConstruct`
  随即抛出，Bean 初始化阶段直接阻断启动——这正是 F01 描述的启动阻断。
  没有选择“把 required 全局改成 false”，因为那会让共享 API Key 也能冒充生产身份契约。
- **`application-prod.yml`** —— 通过 `spring.profiles.group.demo=prod,demo` 让 demo 自动
  叠加 prod，避免“只激活 demo、丢掉生产硬约束”的半配置环境；补注释说明 enabled/required 语义边界。
  游标签名密钥保持无默认值。
- **`StartupContractValidator.java`（新增）** —— 启动早期一次性收集**全部**缺失必需项，
  输出字段级清单（变量名 + 服务哪个配置项 + 用途），且**不回显任何变量值**。
  校验逻辑与 Spring 解耦为静态方法，便于离线单测。
- **`docker-compose.yml`** —— profile 改为 `demo`；补齐 `VIO_RESOURCE_CURSOR_SECRET`
  （此前完全没传入容器）与 OIDC、配额、事件通道等显式映射。
- **`.github/workflows/ci.yml`** —— 补 `VIO_RESOURCE_CURSOR_SECRET` 与 `SPRING_PROFILES_ACTIVE=demo`，
  否则 Compose smoke 会（按设计）被启动契约拒绝。
- **`tools/s0-deployment-contract.test.mjs`（新增）** —— compose↔启动契约的交叉校验（见 3.3）。
  本机无法运行容器，这是对 F01 唯一可行的自动化防线。

- **`src/test/.../run/RunTestAwait.java`（新增）** —— 条件轮询工具，取代各测试里
  重复且易错的“轮询状态再断言事件”写法。
- **`src/test/.../run/PokemonAgentRunServiceAnswerProjectionTest.java`** —— 改为等待终态事件。
- **`src/test/.../run/PokemonAgentRunServiceRecoveryTest.java`** —— 同上。
- **`src/test/.../run/PokemonAgentRunServiceIdempotencyTest.java`** —— 修复“循环外只读一次快照”
  导致轮询永不生效的缺陷，改为按幂等键条件轮询。

> 注意一个反直觉点：`StartupContractValidator` 承担 prod/demo 的必需项门禁，
> 但两条 profile 的失败顺序不同：
> - **prod** 的 `vio.resource.cursor.secret` 是 `${VIO_RESOURCE_CURSOR_SECRET}`（无默认值），
>   缺失时 Spring 在**属性解析阶段**就抛 `PlaceholderResolutionException`，早于 Bean 初始化；
> - **demo** 用的是 `${VIO_RESOURCE_CURSOR_SECRET:}`（空默认值），属性总能解析成功，
>   因此确实由 `StartupContractValidator` 给出字段级错误。
>
> 两者都 fail-closed 阻止启动，结果一致，但错误信息的来源和可读性不同。
> 这一点已写入 `application-prod.yml` 注释，并由 3.3 的契约测试断言注释不得写反。

### U02 · F02 身份接线

- **`SecurityConfig.java`** —— 路径列表抽为 `AUTHENTICATED_PATH_PATTERNS` 与
  `PUBLIC_PATH_PATTERNS` 两个公开常量，作为身份接线的**唯一事实来源**；
  补齐 `/conversations/**`、`/teams/**`、`/favorites/**`，并补上遗漏的 `/ready` 公开探针。
- **`ResourceController.java`** —— 补 `RunNotFoundException` 处理器。
  这是实施中发现并顺带修复的真实缺陷：`@ExceptionHandler` 只作用于声明它的控制器，
  `AgentRunController` 上的 404 映射不会覆盖 `ResourceController`，导致跨主体访问
  `GET /conversations/{id}` 返回 **500** 而非 404。现统一返回 404，且刻意不区分
  “不存在/无权访问”，避免用状态码差异探测他人资源是否存在。

回归测试分三层，互补而非重复：

| 测试 | 层次 | 作用 |
|---|---|---|
| `SecurityRouteCoverageTest` | 静态契约 | 从控制器源码枚举全部 59 条映射，逐条要求“明确受保护/明确公开”；新增控制器忘记接线直接红灯 |
| `ResourceIdentityHttpTest` | 真实 HTTP | `RANDOM_PORT` 真实容器，请求穿过过滤链与 MVC 拦截器；匿名 401、跨主体 404、伪造头无效、`/chat/runs` 不退化 |
| `DeploymentProfileContractTest` | 配置契约 | 锁定 prod fail-closed 默认、demo 成对放开、profile group 存在、公开白名单最小化 |

`ResourceIdentityHttpTest` **没有**手工写 `RequestContext`——这正是审查报告明确禁止的做法。
两个测试凭据（`application-f02-identity.yml`）派生两个不同主体，隔离断言才有意义。

## 5. 未验证项（不得当成已通过）

### 5.0 为什么 Docker 类验证在本机无法完成

本次**尝试启动 Docker 后确认这是环境硬限制，不是配置问题**：

```text
C:\Program Files\Docker\Docker\Docker Desktop.exe  存在，但启动后立即退出（exit code 1）
Get-Process *docker*                              无任何进程
Get-Service com.docker.service                    Stopped / Manual
wsl --status                                      Wsl/EnumerateDistros/Service/E_ACCESSDENIED
```

WSL 后端返回 `E_ACCESSDENIED`，Docker Desktop 依赖它，因此本机无法运行任何容器。
仓库自带的说明文档《公司电脑跳过WSL与Docker环境准备》正是针对这种情况。
**结论：下文的容器类验收必须在 CI 或具备 Docker 的机器上执行，本机无法替代。**

1. **未实测 `docker compose up`**：F01 的“干净环境按文档启动、readiness 与业务探针通过”
   **未验证**。缓解：3.3 的 compose 契约测试已从静态层面闭合“必需变量漏映射”这一 F01 本体，
   但它不能证明容器真的能起来。CI 的 Compose smoke 仍是唯一真实验证途径。
2. **数据库 IT 未真实执行**：`PostgresRunPersistenceIT` 的 4 个用例在本机全部 skipped。
   迁移链、终态唯一约束、幂等语义尚未在任何真实 PostgreSQL 上跑过。
3. **staging 真实 OIDC 未接入**：demo 只是说明“演示怎么起”，不代表生产身份已可用。
   生产仍需 `VIO_OIDC_ENABLED=true` 并补齐 issuer/JWKS/audience/回调契约。
4. **角色不足 403 矩阵未覆盖**：本轮覆盖会话/队伍/收藏三组根资源的身份与归属，
   答案、反馈、审批、记忆端点的逐一真实 HTTP 覆盖待补。
5. **U01 的“字段级错误”只在单测层面验证**：`StartupContractValidatorTest` 覆盖了缺项、
   空白值、profile 语义与不回显密钥；未在真实容器启动失败场景中截图留证。
6. **既有偶发测试（本轮已定位并修复）**：整包运行偶发失败，先后命中两个不同用例
   （`PokemonAgentRunServiceAnswerProjectionTest`、`PokemonAgentRunServiceRecoveryTest`），
   单独运行均稳定通过。根因不是被测代码，而是**测试轮询了错误的信号**：
   服务端写入顺序是「先推进 Run 状态并落库，再追加终态事件」
   （`PokemonAgentRunService.failIfActive`：`run.fail()` → `save()` → `emitLocked()`），
   因此“状态已终态”并不蕴含“终态事件已写入”。测试先轮询状态、再断言事件，
   就会命中这个极窄窗口；机器越忙越容易复现。

   处理：新增 `RunTestAwait`（条件轮询，非固定 sleep——固定 sleep 只缩小窗口不消除，
   且拖慢快路径），改为直接轮询测试真正关心的那个条件。同时顺带修正
   `PokemonAgentRunServiceIdempotencyTest` 的一个真实缺陷：
   原循环条件使用的 `persisted` 只在循环外读一次，导致循环永不满足、空转到超时，
   断言实际依赖“读快照时 worker 恰好已完成”的时序巧合。

   此类问题的价值在于：它说明**“单元测试全绿”本身也可能是时序巧合的产物**，
   与 F14 的主旨（绿灯不等于门禁有效）一致。
