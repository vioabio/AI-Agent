# ADR-002：内部主体键与租户身份边界（R02）

> 日期：2026-10-16。状态：**已决策，待实现**。
> 关联：[当前开发进度与剩余开发计划](./当前开发进度与剩余开发计划_2026-10-09.md) R02、[升级方案 F11](../项目全面审查与企业级升级方案_2026-09-17.md)。

## 1. 背景与问题

当前资源归属直接使用认证主体的 `principalId`：

```java
// ResourceController.owner()
String principal = RequestContext.getPrincipalId();
if (principal != null && !principal.isBlank()) return principal;
```

而 OIDC 路径下 `principalId` 就是 ID token 的 **`sub`**（`ApiKeyAuthInterceptor` 第 119 行
`RequestContext.setPrincipalId(policy.principalId())`，policy 由
`OidcPrincipalPolicyAdapter` 从 subject claim 解析）。

### 1.1 真实风险（已核对代码，按实际影响排序）

**风险 A（已确认，当前部署即受影响）：tenant 不参与归属判定。**
`ResourceController.owner()` 只读 `principalId`，全文没有 `getTenantId()` 的参与。
`PrincipalPolicy` 虽然携带 `tenantId`，但 owner 计算忽略它。后果是：
**同一 issuer 下同一 `sub` 属于两个 tenant 时，两者的会话、队伍、收藏、Run 落到同一个 owner**，
彼此完全可见。多租户一旦启用，这就是直接的越权。

**风险 B（已确认，属配置风险）：owner 直接是明文 `sub`，且与 issuer 绑定关系隐式。**
`JwtDecoder` 用 `JwtValidators.createDefaultWithIssuer(properties.issuerUri())` 固定校验单一 issuer，
因此当前**单实例不会**接受第二个 IdP 的 token，"跨 issuer 同 sub 撞键"在现部署下并不成立。
但 `sub` 只在 issuer 范围内唯一，而数据库里存的是裸 `sub`：
一旦后续改为多 issuer（或运维变更 `VIO_OIDC_ISSUER_URI`），
既有行会被静默重新解释到另一套身份上，且无法从数据本身发现。

因此本 ADR 的目标不是修一个当前的漏洞，而是**在启用多租户/多 issuer 之前，
先把归属键的形状定下来**，避免届时做一次无法回退的数据重解释。

### 1.2 为什么现在就要做

升级方案 F11 把它列为"多组织上线前为 P0"。等到真实出现第二个租户再改，
需要同时对既有生产数据做归属重写，风险与成本都远高于现在形状未定型时先留好维度。

## 2. 决策

引入**内部主体键**同时承载 issuer、tenant 与 subject 三个维度，并让它成为
所有归属判定、索引、缓存键与审计键的统一来源。

```text
internalPrincipalId = "oidc" + "\u001f" + issuer + "\u001f" + tenant + "\u001f" + sub
ownerColumnValue    = "p-" + sha256Hex(internalPrincipalId)   // 定长、非 PII、稳定
```

设计要点：

| 决定 | 理由 |
|---|---|
| issuer 进入键 | 消除跨 IdP 的 `sub` 碰撞，这是本 ADR 的核心 |
| tenant 进入键 | 同一 issuer 下同一 `sub` 在不同租户必须是不同主体 |
| 存储哈希而非明文 | `user_id` 是 `VARCHAR(128)` 且大量出现在索引/日志/事件 payload 中；哈希避免把 issuer/sub 等标识铺到各处，同时保持定长 |
| 前缀 `p-` | 与现有 API Key 派生键（纯数字字符串）和旧 OIDC 键（裸 sub）在形态上可区分，便于迁移期识别与双读 |
| 哈希用 SHA-256 | 已有 `TokenBinding.sha256Hex`，不引入新依赖；此处不涉及口令，无需加盐（键本身不是秘密） |

### 2.1 与既有键的关系

| 身份来源 | 当前 owner 值 | 决策后 |
|---|---|---|
| API Key | `stablePrincipalId(binding.tokenId())`（数字字符串） | **保持不变**，API Key 是本地唯一主体，无 issuer 维度 |
| OIDC | 裸 `sub` | `p-<sha256(oidc\u001fissuer\u001ftenant\u001fsub)>` |
| 本地安全关闭（`security.enabled=false`） | `X-User-Id` 头或 `anonymous` | **保持不变**，仅限离线开发 |

## 3. 实现步骤（每个 PR 一个闭环）

1. **扩展策略快照**：`PrincipalPolicy` 增加 issuer 维度（或等价的
   `internalPrincipalId` 字段），由 `OidcPrincipalPolicyAdapter` 从已验证的
   `iss` claim 填充。构造器必须拒绝空 issuer，避免"静默退回裸 sub"。
   同步 `TokenBinding` 与 `AuthorizationSnapshot`（V28 表已存 principal_id）。
2. **统一 owner 计算**：把 `owner()` 的取值逻辑收敛到单一处
   （建议 `RequestContext.internalOwner()` 或独立组件），使
   `ResourceController`、`PokemonResourceController`、Run 创建、幂等 scope、
   `AuthorizationSnapshot` 全部使用同一函数，杜绝各入口各算一遍。
3. **迁移**：新增 `V30__internal_principal_owner.sql`，为
   `conversation`、`agent_run`、`favorite`、`saved_team`、`chat_message`、
   `answer_projection`、`user_memory` 等 owner 表加
   `owner_key VARCHAR(96)` 列与索引；回填**只能**对可确定 issuer 的行执行，
   无法确定的行保持 NULL 并显式列出。
4. **双读期**：读取时 `owner_key` 命中优先，回退到 `user_id` 旧值；
   写入统一写新键。双读必须有明确截止条件（见 §5 风险）。
5. **切换与清理**：确认无旧键读取后，删除回退分支与旧列。

## 4. 首发范围（需负责人签字冻结）

升级方案 §1 指出"单企业私有部署未必需要复杂多租户"，因此本 ADR 明确：

- **首发按单 issuer + 单租户冻结**：`tenant` 维度仍进入键（保证未来可演进），
  但不实现组织模型、租户管理界面与 RLS。
- **多租户明确列为未支持**，并在支持矩阵、开关与文档中一致声明；
  不得在对外材料中声称"已具备多租户隔离"。
- 一旦出现第二个 issuer 或第二个租户的真实需求，必须先把
  §3 步骤 1–4 全部落地并完成隔离矩阵验证，再开放。

## 5. 风险与验收

| 风险 | 处理 |
|---|---|
| 迁移期新旧键并存导致同一用户看到两份数据 | 双读期必须显式且短；回填后先跑对账（同主体新键行数 = 旧键行数） |
| issuer 缺失时静默退回裸 sub | 构造器 fail-closed 拒绝空 issuer；`OidcProperties.validationErrors` 已要求 issuerUri |
| 回填错误的 issuer 造成数据被划给错误主体 | 只回填能确定 issuer 的行；其余显式列出人工核对，不做猜测 |
| 哈希键不可人工排查 | 审计侧保留 issuer/tenant/sub 的非 PII 摘要字段（哈希），不提供反查 |

验收条件（对应 R02 完成定义）：

1. 两个**不同 issuer**、相同 `sub` 的用户，会话/队伍/收藏/Run 完全互不可见。
2. 同一 issuer 下同一 `sub` 在两个 tenant 下互不可见。
3. 同用户在不同租户、不同用户同资源 ID、同幂等键、检索结果的隔离矩阵全部通过。
4. 既有 API Key 路径行为不退化（含 `/chat/runs` 与资源 API 的现有回归）。
5. 迁移后对账通过，且不存在的旧键读取路径可证明已关闭。
