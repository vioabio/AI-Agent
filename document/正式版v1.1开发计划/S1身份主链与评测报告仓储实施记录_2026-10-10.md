## 2. 本轮修复的身份主链问题

### 2.0 demo 的数据源配置不等于仓储装配

最后核对发现，S0 提交将 demo 改为自包含配置，只激活 `demo`，但 JDBC 仓储依然是 `@Profile("prod")`，内存实现依然是 `@Profile("!prod")`。打开 DataSource/Flyway 并不会改变这些 Bean 的 profile 条件；原 `DemoProfileActivationTest` 只断言 ConfigData 属性，因此没有发现实际使用内存仓储。

本轮将持久化组件纳入 `prod` 或 `demo`，相应内存/本地 fixture 配置排除这两个 profile；不通过重新叠加 prod 来影响 demo 的 OIDC 配置。新增 Spring Bean 装配测试，直接检查核心仓储的类型，而非只检查 datasource 属性。真实连接、迁移与重启仍须真库验证。

实际修正 50 个 profile 选择点：26 个持久化/审计/配额组件支持 `prod` 或 `demo`，24 个内存/fixture/旧内存 RAG 组件同时排除二者。`JdbcKnowledgeCatalog` 有两个 public 构造器，给带 ObjectMapper 的构造器增加 `@Autowired`，确保真正注册时可实例化；工具网关缺耐久审计出口时，demo 同样拒绝回落本地 JSONL。

`DemoPersistenceWiringTest` 的 13 项用例加载真实 ConfigData 并注册组件，检查 20 个仓储边界、outbox appender、审计和配额的实际类型；同时确认 test 保留离线内存实现、demo/prod 禁止内存配额及 fixture、Redis 缺适配器时抛出不可用异常并拒绝消费。JdbcTemplate 为 mock，仅允许 Spring 的 `afterPropertiesSet` 生命周期调用，任何查询、更新或 datasource 访问均使测试失败；验证的是配置选择与构造器，不能代替连接、迁移或重启验收。

真实组件扫描还暴露了原有审计兜底的条件装配缺陷：`FailClosedToolAuditSink` 本身是 `ToolAuditSink` 的组件，`@ConditionalOnMissingBean(ToolAuditSink.class)` 会使其在注册时匹配自身并被排除。改为独立的 `ToolAuditSinkConfiguration` 在 Bean 方法上评估缺失条件。扫描测试确认存在 JDBC 时唯一选择 JDBC，缺 JDBC 时注册唯一 fail-closed 出口且写入必然抛出审计异常；网关的缺出口拒绝仍作为第二道保护。

### 2.1 主体策略没有注入运行时

`SecurityConfig` 以前直接构造 `ApiKeyAuthInterceptor`，却没有设置 `OidcPrincipalPolicyAdapter`。策略类和单测虽然存在，HTTP 主链仍落入 `notApplicable` 分支，缺少租户、角色和工具策略快照。

本轮通过 Spring provider 注入适配器。OIDC 打开时，缺少/不匹配的租户或角色在业务入口拒绝；API Key 兼容路径继续使用原有身份。

### 2.2 浏览器角色缺少映射

默认 OIDC 浏览器主体仅有 `OIDC_USER`、`SCOPE_*` authority，现有策略要求签名 claim 与 `ROLE_*` authority 求交，因此正常浏览器主体会被拒绝。

新增 `OidcRoleAuthoritiesMapper`，只从 Spring 已验证的 `OidcUserAuthority` 有效 claims 映射角色。直接使用其 `getAttributes()`，保留 ID token 覆盖 UserInfo 的真实优先级；任意 incoming `ROLE_*` 和普通 OAuth2 属性不能自行授予应用角色。

### 2.3 SPA 无法使用默认 CSRF cookie

后端 context-path 为 `/api`，前端页面在 `/`，默认 cookie path 使页面读不到 token；Spring Security 6 默认 XOR handler 和 deferred token 又使原始 cookie header 路径不可用。

本轮将 `CSRF-TOKEN` cookie path 设为 `/`，GET 强制生成 token；`X-CSRF-TOKEN` 按原始 cookie 值校验，表单继续使用 XOR。Cookie 的 Secure/SameSite 与 OIDC 配置对齐，业务状态变更仍需通过 Origin 与 CSRF 校验；登出沿用既有的 CSRF 豁免与 Origin 边界。

### 2.4 Session 属性此前只做配置校验

新增 Servlet factory customizer，把 `cookie-name`、Secure、HttpOnly、SameSite、cookie-only tracking 和 idle timeout 应用到实际容器。OIDC 关闭时不改变默认部署。绝对时限和跨实例会话仍未实现。

### 2.5 刷新请求误使正在执行的 Run 授权失效

OIDC 每次 HTTP 请求会刷新相同 policy token 的到期时间。原先完整 record equality 使 Run 捕获的旧快照被误认为已撤销。

本轮仅允许完全相同的 OIDC 主体、租户、角色、工具、policyVersion、protocol 与配额，存在 expiry 续期差异时继续使用旧快照；旧快照自身过期、当前绑定过期、权限改变或注册表撤销仍拒绝。API Key 保持完整 equality，不新增 tokenMap 条目，不重置限额。

## 3. R03 的实际报告链路

```text
evaluation/run-v1.1-eval.mjs 的 metrics.json 原始 UTF-8 字节
  → 有权限的运营主体显式导入
  → 原文 SHA-256 / 严格 JSON / 服务端冻结规则与样本校验
  → evaluation_report 追加保存（BYTEA + hash + source + imported_by）
  → 按 evaluationRunId 回读、重新计算摘要及验证历史基线
  → ReleaseQualityGate 核对 reportHash 和 data/knowledge/index 血缘
  → 原有审批与 promotion
```

### 3.1 存储与完整性

- `V26__immutable_evaluation_reports.sql` 创建 `evaluation_report`；evaluationRunId 唯一，原文最多 1 MiB。数据库触发器拒绝 UPDATE/DELETE。
- `JdbcEvaluationReportRepository` 在 `prod` 和 `demo` 装配。同 ID 相同字节可重放；不同字节返回冲突，首次来源/导入主体不被覆盖。
- 保存 BYTEA 保留原始字节，避免 JSONB 重排导致哈希失真。每次读取重算摘要并检查存储键与原文 ID。
- 生产仓储不接受 `save(EvaluationReport)` 直接写布尔投影；只有原始 producer 报告导入入口。
- 损坏或读取失败由现有门禁转换为稳定拒绝码，不把数据库堆栈、连接串或原文回显给客户端。

### 3.2 服务端冻结规则

Maven 将仓库的 `evaluation/v1.1/manifest.json` 和 `metric-dictionary.json` 打包进 classpath。解码器验证七类 suite、完整唯一指标集合、样本分母、阈值版本、模型/代码/发布版本及来源哈希字段。发布通过要求安全失败数显式为 0；没有安全观测的 pending 报告可保留 null 并归档为 `passed=false`，不会制造零失败证据。安全失败数不得少于安全样本中的未通过数量。

上传者不能降低阈值或删除指标来让报告通过。字典里的报警边界转换成通过边界，例如 `< 0.98` 转成 `>=0.98`、`>2500ms` 转成 `<=2500`；N6b 指标不计入 N6a 发布。JSON 重复键、尾随内容、非法 UTF-8 和不完整的 ready 声明拒绝。

九项成功率、准确率、召回率和引用/依据比率按冻结字典的公式限定在 `[0,1]`，ready 与 pending 都不能提交 `2.0` 等无效观测来通过阈值。Token、费用和延迟独立保留非负有限数规则；归档失败的预算观测不会被错误按比率限制。新增行为测试覆盖全部九项的 1.0 边界与刚超过 1.0 的数值。

**预算必须绑定独立历史报告。** runner 新增 `--baseline-evaluation-run-id` 和 `--baseline-report-hash`，二者必须同时给出，不能引用自身。仓储回读该基线并校验模型/suite/摘要，按存储中的 tokens/cost 观测计算 `baseline +20%`，不相信上传的 `baselineValue`。

首份没有独立预算基线的报告可以归档，但在线投影 `passed=false`，不能自行证明发布通过。基线引用限制最大深度 8 并拒绝循环。后续参考一个模型与 suite 匹配、具有真实预算观测的已归档基线，再运行新的 evaluationRunId。

### 3.3 接口与调用方式

| 方法与路径（含 context-path） | 权限与行为 |
|---|---|
| `POST /api/knowledge/evaluation-reports` | OPERATOR/QUALITY；Content-Type 为 application/json，body 为原始 metrics.json |
| `GET /api/knowledge/evaluation-reports/{evaluationRunId}` | OPERATOR/QUALITY/REVIEWER/PUBLISHER；返回校验后的投影，不返回原始 bytes |

导入需要 `X-Evaluation-Report-Hash: sha256:<64位小写摘要>` 和 `X-Evaluation-Source: <CI运行/制品标识>`。认证主体由服务端上下文提供，不接受 `X-Role`、`X-User-Id` 伪装权限或审计人。实际请求流读取也有 1 MiB 限制，支持 chunked 请求的上限控制。

响应：成功/相同重放 200；无身份 401；角色不足 403；错误报告/摘要/基线 400；不同原文占用同 ID 409；超限 413；仓储缺失/损坏 503。普通 local/test 内存仓储不支持此导入入口，会明确返回 503；demo 与 prod 使用相同 JDBC 仓储。

读取原文摘要的例子（不修改源报告）：

```powershell
$artifactHash = 'sha256:' + (Get-FileHash -LiteralPath 'artifacts/v1.1/eval/<run-id>/metrics.json' -Algorithm SHA256).Hash.ToLowerInvariant()
```

浏览器调用先登录，GET 获得 `CSRF-TOKEN`，之后 POST 发送会话 cookie 和 `X-CSRF-TOKEN`，body 直接提交原始文件字节，不重新序列化 JSON。当前 Bearer POST 也受 CSRF 保护；服务账号需维护本次 GET 返回的 CSRF cookie/header。尚未设计只对明确无会话的 Bearer 请求豁免 CSRF。

### 3.4 接口契约与前端接入准备

Controller 的 Swagger 注解、`tools/generate-openapi-v1.1.mjs`、`contracts/openapi-v1.1.json` 与前端 `src/api/openapi.json` 已同步登记上述两个接口。导入模型为 `string/binary`，明确原文 body、摘要/来源 header、CSRF、返回投影和失败状态。生成器中原有 `Idempotency-Key` 的四处本地引用指向错误组件，已统一映射到实际 `IdempotencyKey`；HTTP header 名不变。

新增五项 OpenAPI 回归验证本地 `$ref` 闭合、读写契约、Swagger 原文声明，并在临时目录用现有前端 codegen 生成客户端，确认参数类型是 Blob、Axios 保留每一个原始 UTF-8 字节及摘要。测试使用本地 adapter，没有发送网络请求。v1.0→v1.1 兼容检查无 breaking change 或 warning。

现有前端 `src/api/generated/` 尚未扩展报告 UI；本轮只同步其输入契约，并以临时生成验证后续传输能力。完整客户端更新与登录/报告页面一并实施，避免本轮混入约百个无关 DTO/service 的全量生成变动。CI 在前端 `npm ci` 后再执行报告契约测试，确保干净 runner 上原文字节验证实际运行；此前的 producer 测试步骤仍保留。

### 3.5 信任边界

原文摘要能证明保存/回读内容一致，不能独立证明生产者实际跑过模型、dataset 中的答案真实或观测数值可信。本轮没有下载来源文件；manifest/dictionary/dataset 哈希字段核对格式与契约，未逐一重算外部文件摘要。导入依赖受信任运营人员，尚无签名/attestation 来证明 CI producer 来源；生产部署仍需受控流水线、制品来源/审核、真实数据和独立评测执行证据。报告属于全局知识发布的运营域，当前没有租户过滤，不能将其称为多租户报告仓储。

冻结规则来自本次部署的 classpath。未来修改规则时须同步 suite/threshold 版本并保留旧版本读取策略；当前不支持任意多个 suite 版本，不能把旧报告重新解释成新规则的通过证据。
