## 2. 数据与安全语义

`RunStepOutput` 只包含 `runId`、`stepNo`、`executorVersion`、`contextHash`、`payloadDigest`、`encryptedPayload`、`keyVersion`、`createdAt` 与 `expiresAt`。上下文和明文 payload 使用 64 位 SHA-256；时间统一截断到 PostgreSQL 微秒精度，并要求 `expiresAt > createdAt`。

数据库表 `agent_run_step_output` 以 `(run_id, step_no)` 为主键，外键绑定 `agent_run`，按 `expires_at` 建索引。`encrypted_payload` 是不透明密文或受控 artifact 引用，密钥版本随记录保存，解密必须使用持久化版本。没有 codec 时不能回退到明文或普通 Base64。

仓储保存采用 append-only 语义：首次插入成功后回读 canonical 行；同一主键和相同完整内容返回既有记录；任一字段变化抛 `RunStepOutputConflictException`。这保证重试不会覆盖先前步骤事实，也避免把修改后的答案伪装成同一执行结果。

## 3. 服务接入要求

服务启用 `vio.run.durable-resume=true` 且装配 `RunStepOutputRepository` 时，`commit-answer` 必须按以下顺序处理：

1. 组装稳定、可排序的 AnswerContract artifact JSON，至少包含 schema/version、Run/step、答案状态、游戏版本与规则版本、引用、限制、traceId 和 lineage。
2. 用受控 `ModelInvocationCacheCodec.encode()` 加密 canonical JSON；记录 codec 返回的 `keyVersion`。
3. 对加密前 UTF-8 canonical JSON 计算 `payloadDigest`，对恢复上下文计算 `contextHash`。
4. 通过租约 fence 保存 `RunStepOutput`。artifact 写入失败时，答案投影、assistant message、完成事件和 Run 完成 CAS 不得对外发布。
5. 提交后校验 artifact 与 AnswerProjection/AnswerLineage 的摘要和上下文一致；不一致固定失败并保持 fail-closed。

过期 artifact 清理由 `RunStepOutputRetentionService` 提供定时和手动入口，批量上限由 `vio.run.step-output-retention-cleanup-batch-size` 控制；默认 `VIO_STEP_OUTPUT_RETENTION_CLEANUP_ENABLED=false`。清理异常只记录异常类型，不能把连接串、SQL 或密文写入日志。

重试相同步骤时，服务会先读取既有记录并比较上下文、摘要、执行器元数据和解密后的 canonical 明文，再决定幂等复用或冲突失败；不会因为 AES-GCM 随机 nonce、`createdAt` 或密钥轮换而生成第二份事实。密文解码失败、摘要/上下文/`runId`/`stepNo`/`executorVersion` 篡改均固定 fail-closed。递归或并发写入只有在 canonical 明文完全一致时才可复用。

## 4. 恢复边界

本轮明确不把“存在 artifact”当作“允许恢复”。当前 `RunRecoveryPolicy` 仍只允许尚未开始执行的 `step=0 / nextAction=dispatch` 继续；execute-answer/commit-answer checkpoint 继续 fail-closed。原因包括：

- `PrincipalPolicy`、`TokenBinding` 和 allowedTools 目前主要是 JVM 内存状态，重启后无法从 Run 事件完整重建；
- 现有 `contextHash` 尚未绑定 principal、tenant、授权来源、allowedTools digest 和 token binding digest；
- 既有模型/工具调用可能已产生外部副作用，数据库回滚不能撤回远端动作；
- 恢复重新调用模型会重复计费，缓存 miss 不得隐式生成新响应。

快照缺失、过期、撤销或策略漂移全部拒绝。工具副作用需使用 effect ledger、外部幂等键和人工 UNKNOWN 处置。当前恢复扫描仅在快照完整、未过期、未撤销且与当前策略一致时恢复 dispatch，任何校验失败都保持安全失败。

## 6. 学习路线

1. 阅读 `RunStepOutput`、`V27__immutable_run_step_outputs.sql` 和 `RunStepOutputRepositoryTest`，理解 append-only、摘要和数据库时间精度。
2. 阅读 `ModelInvocationCacheCodec` 与 `ModelInvocationCacheService.lookupForRecovery`，练习密钥版本选择、cache miss 与解密失败的区别。
3. 跟踪 `PokemonAgentRunService` 的 `commit-answer → workerWrite → fence` 调用链，画出模型调用、artifact 写入和答案投影的边界。
4. 为同一 `(runId, stepNo)` 设计相同输出重试、不同输出冲突和 artifact 写失败用例，确认不会发布半套完成事实。
5. 阅读 `RunRecoveryPolicy` 与身份策略实现，说明为什么仅凭 checkpoint、历史角色或 RUN_CREATED 事件不能恢复工具权限。
6. 在可用 PostgreSQL/Docker 后运行迁移和 IT，分别记录“编译通过”“测试执行通过”“环境跳过”，不要混为单一绿灯。
