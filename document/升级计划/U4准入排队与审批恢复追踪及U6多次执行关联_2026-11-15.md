# U4 准入、排队与审批恢复追踪及 U6 多次执行关联

## 本轮交付

补齐 Run 服务创建入口、排队中止和审批恢复的追踪，随后扩展 U6 的 Run 与 Trace 关联器，使其能够核对同一 Run 的多次执行。

最终后端整体回归为 1,791 项，0 失败、0 错误、3 跳过。定向回归 129 项和脚本测试 51 项通过。

## Run 准入观测

`createRun` 通过 `AgentRunObservation.admission` 包装，产生 `agent.run.admit`。

- 范围包含幂等查询、容量准入、Run 创建与任务提交。
- 返回实际 `RunView` 后绑定 Run ID。
- 准入拒绝记录固定错误 `RUN_ADMISSION_FAILED`。
- 创建 Run 之前的拒绝记录保留为空 Run ID，通过收集器中的阶段名称查询。

测试验证容量拒绝没有额外创建任务，观测错误不会重放业务操作。HTTP 身份认证过滤链位于此范围之前。

## 排队任务的追踪

每个 `ManagedRunTask` 分配随机执行批次标识，通过 `agent.run.attempt.id` 关联本次调度和 Worker 执行。

任务创建时启动 `agent.run.dispatch`，排队期间保持其观测对象。实际 Worker 执行前结束该阶段，结果为 `STARTED`。取消、超时或调度失败时，由任务清理路径结束该阶段，记录受限结果值。

`Dispatch.finish` 使用原子关闭标志，重复清理只结束一次。排队期间没有打开线程作用域，后续任务继续绑定各自的 Run。

新增回归覆盖以下情况。

1. 队列中取消后结束调度观测，执行器调用次数保持为正在运行的任务数量。
2. 排队期限到达后产生失败终态，队列任务未调用执行器。
3. 正常执行的调度与 Worker 具有相同执行批次标识。
4. 现有租约、审批容量、取消和提交测试继续通过。

## 审批恢复与 U6 关联修复

审批恢复会保留 Run ID，并创建新的执行任务。之前关联器要求唯一 `agent.run.execute` 根节点，会将正常恢复判为 `AMBIGUOUS_RUN_ROOT`。

现在按执行批次标识分组，每批核对调度阶段和 Worker 阶段。

- 已进入 Worker 的批次需要匹配的调度记录及 `STARTED` 结果。
- 排队中止的批次允许缺少 Worker，保留实际取消或失败结果。
- 重复批次标识、混用新旧记录、缺失调度和损坏父链继续拒绝。
- 同一 Trace 中存在准入祖先或多个批次时，核对连通性、循环和所属 Run。
- 返回每批的 `dispatch`、`execution` 和具体 Span ID，便于分别打开原 Trace。
- 批次列表按标识稳定排列，流程先后可对照原始 Trace 时间及 Run 事件。

单次执行保留顶层 Trace 链接；多次执行的链接位于 `attempts` 中。历史单根记录继续按其原有范围读取。

## 真实 HTTP 接线故障与修复

首轮四道 HTTP 冒烟题的正文正常，但关联结果均为 `INCOMPLETE_ATTEMPT`。实际查询发现仅有 Worker 记录，准入和排队阶段没有导出。

原因是请求线程携带未采样的外部 Span。领域 SDK 创建新根节点时受该上下文影响，即使本地验收采样率设置为 1，也会被父采样策略抑制。

新增回归在未采样外部 HTTP 上下文以及框架 NOOP 处理器共存时执行准入和调度，验证领域 Span 导出、父子关系以及外部上下文恢复。

`DomainTracingObservationHandler` 现对新的领域根节点使用领域 SDK 的采样策略，已有领域父节点继续关联。该处理器提取为具名类，并加入构建指纹。构建清单升级为 `u6-runtime-components-v6`，共 33 个组件。

初次失败记录保存在 `artifacts/u4-dispatch-live-traces-20261115.json`，修复后的结果使用 `u4-dispatch-final-live` 前缀。
