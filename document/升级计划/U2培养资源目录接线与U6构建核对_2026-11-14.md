# U2培养资源目录接线与U6构建核对

## 本轮补齐

保存队伍的培养路线“步骤四”接入已有学习器编号、配方和获取区域目录。现在可以展示本次成员学习记录与固定公开目录交叉核对的编号、社区配方和共同大区域，而不再一律只提示“需要另查”。

这是**目录参考与获取条件核对**，不是自动获取物品或进度判定。实际剧情解锁、背包数量、精确坐标、NPC及操作条件仍未核验；材料来源存在差异时不选择其中一份当成确定答案。

## 来源链路

`readCurrentTeam`保存快照 → 受治理的整队配置检查 → 参数/报告/资料checksum绑定 → `SavedTrainingResources`提取RECORDED且含machine方式的学习记录 → `MachineReferenceFacts.create`核对固定编号 → 既有配方与获取区域目录。

- 沿用已验证整队结果，不新增外部API或模型调用，也不伪造`lookupPokemonMachine`执行事件。
- 仅处理成员/招式/游戏/数据版本及来源通过校验的记录。参考来源不在时不列编号、材料或地点。
- 有学习器记录但编号未收录，明确标注未收录；不能解释为不能学习或没有资源。
- 固定目录仍只有4个招式，不扩大成完整图鉴覆盖；正文标明随包资料、社区参考、核对日期和待游戏内核验范围。
- 每次最多展开4条成员—招式记录，优先展开目录已收录记录，其余数量明确显示，允许用户指定成员和招式继续核对。
- 复用`MachineRecipeCatalog.answer`和`MachineAcquisitionCatalog.answer`的差异与共同区域判断，不新增材料、数量或位置推断。
- 太晶、已有队伍及本地草稿不变，不产生写入或审批。

## U6构建证据补齐

此前构建核对只覆盖六个核心类和检索组件，单独更新培养辅助类可能漏检。本轮：

1. `/chat/runtime.implementationSha256`登记`SavedTrainingRoadmap`与`SavedTrainingResources`。
2. `runtime-build-check.mjs`保留原六类报告，并在additionalComponents中检查检索与两个培养组件。
3. 任一组件缺失或不一致，整体为`STALE_OR_DIFFERENT_ARTIFACTS`，不能因核心类一致而通过。
4. 真实Spring HTTP测试核对两个培养类实际资源摘要；Node CLI使用隔离HTTP/类文件替身覆盖全部匹配、缺失和过期。

摘要比较的是资源文件，不能据此认证JVM热替换、业务质量或供应商输出。旧报告仍按原范围理解，不能当作本次新增组件已验证。

## 本地更新

停止常用后端，执行`ops/local/rebuild-backend.ps1 -Offline`后再启动，用原模型配置即可；本轮没有新增Key或默认启用其他功能。示例：`请为我的队伍ID 你的实际ID 制定培养计划，不保存、不修改。`

构建核对可使用：

```powershell
node tools/campus/runtime-build-check.mjs http://127.0.0.1:8123/api artifacts/u2-resource-final-isolated/classes artifacts/新的构建核对报告.json
```

仅在后端已重建启动后执行；此CLI会创建本地专用验证账号并退出登录，不会自动删除该账号；不记录Key，报告不是发布验收。
