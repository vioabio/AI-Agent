# 单主 Agent、结构化对话状态、专用工具与回答校验

## 目标与实施范围

保留一个主 Agent，先解决任务理解、上下文指代与证据使用的问题，再评估是否需要多个 Agent。本次先完成道馆领域的第一阶段。图鉴、OU、攻略检索等已有路径保持各自工作方式，尚未全部迁移到统一任务计划；不能把本次提交称为全场景 Agent 重构完成。

## 阶段一：道馆任务计划与发布前校验（本轮实现）

执行顺序：`DefaultRunExecutor → GymDialogueRouter → GymTurnPlan → 已有资料/相性/已保存队伍专用路径 → GymAnswerReview → answer.delta`。

- `GymTurnPlan` 用明确的枚举区分资料查询、推荐队伍、通用应对、已保存队伍分析、伤害计算与修改任务，携带 owner、conversation、游戏和目标馆主/挑战阶段。
- 状态从现有持久消息库中按账号、会话和当前 Run 创建时间重建，每次 Run 生成独立快照，不使用静态全局聊天状态，也没有新建第二套会话数据库。`AgentRunContext.dialogueHistory()` 保留当前会话已完成的完整对话配对，独立于模型使用的 `history()`；后者仍受 token、字符与轮数预算限制，不能把完整历史再次塞入模型提示。两个视图来自同一次仓储读取，排除其他账号/会话、当前 Run、未来消息以及孤立或重复配对。跨重启依赖原有持久仓储，仍不代表无限范围、无删除生命周期约束的记忆。
- 目标和阶段以用户历史选择为准，助手输出不能自行设定馆主、已解锁重赛或玩家进度；切换馆主清除原阶段，多个候选没有明确选择时澄清。默认初战会明确标注。
- 序号由 `GymOrdinalReference` 解析：只认最近确实展示过、并经程序校验的完整编号馆主名单及名称映射，不从模型自由叙述或单个目录请求猜测名单。数量查询应答 8 位并提供编号名单；“第四位”“第六位”仅代表该名单顺序，不代表朱紫固定挑战顺序。没有可信名单、序号越界或目标歧义时澄清，不退回八馆主总览。
- 分类规则集中维护，资料快捷路径必须先检查任务类型，不能仅因包含“馆主”“队伍”就返回目录。新协调入口仅承接明确道馆请求和有指代的追问，避免上一轮谈阿枫后把新的 OU 推荐也当作道馆任务。
- 已保存队伍仍通过治理工具 `listCurrentTeams`、`analyzeSavedTeamForGym` 获取真实快照。通用相性仍使用已有本地计算器和校验过的馆主资料，不让模型猜测倍率。
- 推荐路径增加只读 `recommendGymTeamCore`：当前仅支持莱姆的 3 人理论核心，沿用当前 Run 资料版本核验已收录招式与学习记录；结果始终标记 `PARTIAL`。这不是完整六人队伍，也不证明玩家当前可以捕获、已拥有、满足资源条件或必胜；不自动保存。其他馆主不能套用莱姆核心，全面候选与完整配置推荐仍未完成。
- `GymAnswerReview` 在发布本轮确定性回答前检查空答、用馆主总览替代推荐/分析、带标题的回答目标不符，以及推荐请求没有回应成员/队伍主题等错误；失败输出明确提示，不将错误答案先流出去。这是首版任务匹配校验，不是通用语义评审器或事实正确性的充分证明。
- 目前意图判定仍是集中规则，没有引入额外模型分类调用。伤害与修改任务继续走原有受控工具/HITL流程，不能由新的推荐入口直接写库。

### 本轮解决的复现

先问“看下阿枫的队伍配置”，再问“有什么很好克制该馆主的队伍吗”。应识别为推荐任务，承接阿枫并给已核验相性方向与具体配置缺口；不能输出八馆主总览。由于尚无覆盖全地图进度的获取数据，不会把未核验的新成员拼成声称当前可执行的完整队伍。

本次继续覆盖原始四轮：①“咨询下朱紫有几位馆主”；②“看下第四位馆主的队伍配置”；③“我的 test1 队伍的配置可以应对这个馆主吗”；④“基于朱紫的图鉴给我一个应对第六位馆主队伍的队伍配置”。在上一轮可信名单顺序下，第二轮应选海岱，第三轮读取当前账号真实保存的 test1 并对海岱分析，第四轮切换莱姆并明确仅提供部分核心与缺口。测试不得把合成 test1 冒充真实用户队伍验收。

## 阶段二：有证据的具体成员与队伍推荐（已启动，尚未全面完成）

1. 建立候选数据契约：成员形态、版本、招式及学习条件、特性/持物、获得途径、进度要求、来源、核验状态。
2. 先覆盖有限且可核验的早期馆主场景，不把图鉴存在等同于该进度可捕获。缺少某项只提示该项，不让玩家重新填写已知信息。
3. 已开始以 `recommendGymTeamCore` 提供莱姆 3 人 `PARTIAL` 核心；下一步扩展有证据的候选检索与组合评估，返回候选、证据和缺口。与已保存队伍读取共享配置模型；没有用户确认不自动保存。
4. 对未被规则明确识别的表达，引入同一主模型的结构化意图输出；校验枚举、目标 ID、缺失项、允许工具后执行。超时或结构无效时澄清，不默认为目录查询；记录分类用量与耗时。
5. 具体阵容输出必须含成员和配置证据；证据不足返回“部分建议/尚未完成”，不能包装成完整推荐。

## 阶段三：扩展回答契约与全链路状态

- 将图鉴、攻略、OU、队伍分析与配置修改逐步迁入统一的任务计划；优先复用当前事实与工具证据契约，避免新建相互冲突的版本系统。
- 为复杂任务提供类型化 outcome：已完成、部分完成、需澄清、工具失败；携带事实证据、策略假设和缺失项。
- 当前已用完整 `dialogueHistory` 从持久消息重建道馆状态，独立模型裁剪；后续评估是否需要单独的版本化会话投影，以降低长会话重建成本。无论采用哪种存储，均需与账号/会话、资料版本、用户修改及删除生命周期一致，并补齐重启恢复和并发更新测试。
- 模型生成部分在发布前验证必要字段、来源、目标、用户实际配置；可以先发布“正在读取资料”等状态事件，未经核验的事实不先以回答增量发送。

## 阶段四：独立质量验收与材料更新

- 冻结未参与调试的自然表达和多轮测试集，覆盖指代、改口、转话题、同名队伍、缺失资料及工具失败；调试集和验收集分开。
- 分别报告意图准确率、上下文目标正确率、工具选择与参数正确率、回答切题率和无依据配置比例；不以单元测试数量代替回答质量。
- 在本机模型配置下进行真实模型复测，人工抽查策略、机制解释和来源有效性，再更新 README、架构与演示材料。
- 只有任务确实需要独立并行检索或隔离评估、且单主 Agent 已稳定时，才评估拆分检索/规划/核验 Agent，并比较质量、延迟、成本和故障率。

## Embedding 攻略检索接入（本地优先）

新增路径：攻略原文与确定性分块 → 显式调用 Embedding 接口 → SQLite 向量缓存 → 查询向量 → 游戏/语言/赛制/规则/有效期/适用范围过滤 → 余弦相似度 → 与 BM25 使用 RRF 融合 → 原文片段引用。Agent 继续通过现有 `searchPokemonGuides` 工具调用，不直接读取向量库，也不把语义相似度当作事实证据或强度排名。

### 本机配置步骤

1. 准备支持 OpenAI 兼容 `/embeddings` 协议、返回浮点向量的服务。聊天 Key 不等于已经配置 Embedding；需确认服务地址、模型标识和输出维度。本次没有预置真实服务凭证或替用户选择付费模型。
2. 在 IDEA 后端运行配置中设置以下环境变量；Key 仅留在本机，不提交到 Git：

   | 变量 | 含义 |
   | --- | --- |
   | `VIO_GUIDE_SEMANTIC_ENABLED=true` | 开启可选语义检索 |
   | `VIO_GUIDE_EMBEDDING_ENDPOINT` | 完整 Embedding URL，包含 `/embeddings` 路径；云端必须 HTTPS，本机服务允许 loopback HTTP |
   | `VIO_GUIDE_EMBEDDING_API_KEY` | 服务凭证；本机无鉴权兼容服务可使用其约定的占位值 |
   | `VIO_GUIDE_EMBEDDING_MODEL` | 服务实际支持的模型名 |
   | `VIO_GUIDE_EMBEDDING_DIMENSIONS` | 实际输出维度，默认1536；不匹配时拒绝使用该批向量 |
   | `VIO_GUIDE_VECTOR_PATH` | 可选，本地缓存文件，默认 `.local-data/guide-vectors.sqlite` |
   | `VIO_GUIDE_SEMANTIC_MINIMUM_SIMILARITY` | 可选，最低余弦相似度，默认0.55，须按实际模型评测调整 |

3. 重启后端。在项目根目录运行 `powershell -File .\ops\local\build-guide-semantic-index.ps1`，按提示输入本地账号。脚本仅连接本机，使用独立会话、CSRF 令牌与密码隐藏输入，结束时退出该会话。构建动作会把现有公开攻略片段发送给配置的服务；普通问题不会自动触发整库上传。
4. 确认构建结果 `ready=true`。之后现有攻略查询和 Agent 工具即可使用混合检索。开启后符合范围且索引就绪的问题会发送给 Embedding 服务生成查询向量；不上传账号密码或聊天历史。
5. 未配置、未构建、服务失败或向量校验失败时保持 BM25，使用 `GET /api/pokemon/guides/semantic` 查看模式与安全状态码。`POST /api/pokemon/guides/semantic/index` 是显式构建接口，需要正常身份认证；本地账号模式需要 CSRF。

### 数据与边界

- 默认关闭，不改变已有本地启动。启动与状态查询均不发起 Embedding 请求。构建最多512个片段、每批最多16条，设置单次请求及构建时间边界；完整批次校验成功后才事务发布，不自动重试失败付费请求。
- 缓存绑定端点、模型标识、维度及整个源索引指纹；来源变化需重新构建，已有有效缓存直接复用。缓存损坏时回退，显式构建可修复。同名模型的上游权重变化无法自动感知，应使用明确版本标识或新的缓存文件。
- 文档仍以原始库的版本、校验和和片段位置为准；向量不成为新的事实来源。模型返回顺序、条数、维度、数值有效性与零向量均校验。
- 当前处理本地公开项目攻略，不是账号私有文档的多租户向量库；没有新增上传文件或互联网自动采集功能。索引构建与 Embedding 请求用量尚未并入聊天模型 Token/费用账本。
- 本地小语料用 SQLite 持久化与内存余弦检索，不需要额外服务器。生产 `VersionedPgVectorStoreConfig` 及其1536维表保持独立；扩大语料时优先迁入已有版本化 pgvector 摄取链路，不能直接拿不同维度模型写入旧表。
- 本轮协议与失败测试使用受控本地 Embedding 服务，不等同于真实模型 Recall@K 或回答质量验收。真实服务配置后还需使用独立问题集评估召回、错误命中、延迟及费用，再决定是否拆资料检索 Agent。

## 首个协作 Agent：只读资料检索角色

`GuideResearchAgent` 是单独的角色、私有提示词和受限模型决策步骤，由主 `VioManus` 监督。第一版只接管 `ProjectGuideRequest` 明确识别的项目资料说明问题，例如“说明当前项目种族值和努力值的区别”。图鉴、道馆、配队和计算任务没有自动全部拆成子 Agent。

链路：主执行器维护账号、会话与目标 → 检索 Agent 最多一次私有模型决策 → 最多一次治理后的 `searchPokemonGuides` → 结构化原始证据 → 来源/引用校验 → 主 Agent 再校验并发布答案。检索角色与主角色可复用同一个已配置的 ChatModel，不需要再申请一个 Key；它们是不同的执行上下文，不代表两个不同基础模型或多个并行模型进程。

- 在 IDEA 后端环境变量设置 `VIO_AGENT_GUIDE_RESEARCH_ENABLED=true` 并重启即可开启；默认关闭，设回 false 可回退。无需修改聊天入口。
- 子 Agent 只有一个只读攻略工具，没有队伍写入、终端、下载或 MCP 权限，也不能自行再次委派。必须保持原始问题和游戏标识，不能自行改写成另一任务；成员与资料版本的进一步约束由原工具和 Run 范围继续检查。
- 子 Agent 的规划文字不进入用户流，也不作为事实证据返回。只将实际工具读取、通过现有 `GuideAnswerEvidence` 校验的结构化来源交给主 Agent；主 Agent 的最终输出仍走原有证据展示流程，避免把子 Agent 自由生成的话当成引用。
- 无工具、无上下文或不属于支持场景时跳过；非法选择、改题、服务异常或读取失败时回退原单 Agent 路径。取消、超时和全局模型额度异常继续向上传播，不能伪装成成功回退。
- 额外模型调用共享当前 Run 的用量、上下文与任务额度统计，不单独绕过成本/调用次数限制。当前私有规划最多256输出Token，至多增加一次模型调用；是否值得开启仍应比较延迟、质量与费用。
- 委派开始、完成和回退以 `route.selected` 事件记录 `agentRole=GUIDE_RESEARCH` 和 `delegationEvent`；真实工具事件带同一角色标识。`GET /api/chat/runtime` 的 `agentCollaboration` 字段可检查开关、角色与边界。
- Embedding 与此开关相互独立：未配置 Embedding 时，检索 Agent 仍可使用现有 BM25；配置后同一只读工具自动复用混合检索，不重复建设第二套文档库。
